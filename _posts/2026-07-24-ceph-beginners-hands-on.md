# 1. Introduction and core terminology

Ceph is a distributed storage system that exposes three user-facing
interfaces — block, file and object — all built on a single internal
object store called **RADOS**. This post walks a complete loop for
newcomers: assemble a real five-node cluster daemon by daemon, read
back what it is made of, use all three interfaces, then trace one
written object down through placement, across three machines, and onto
a raw disk — verifying every hop with checksums. The target reader is
an engineer who wants to *use* Ceph now and *hack on* Ceph later.

The vocabulary you need before anything else, in five small groups.
Skim them now, and come back as the terms start appearing in
commands — every one of them shows up later in real output.

**The cluster and its unit of storage** — what Ceph fundamentally is:

| Term | Meaning |
|------|---------|
| cluster | one Ceph deployment: the MONs, MGRs, OSDs, ... acting as one |
| fsid | the cluster's UUID — stamped into maps, stores, device labels |
| RADOS | Reliable Autonomic Distributed Object Store — the core cluster |
| object | RADOS's unit: name + bytes + xattrs + omap (key/value pairs) |

**Daemons, and the maps that describe them** — the processes
Section 3 starts one by one (the maps are what the MON exists to keep):

| Term | Meaning |
|------|---------|
| OSD | Object Storage Daemon — one per disk; stores objects (BlueStore) |
| BlueStore | the OSD's storage engine: raw device, no filesystem below |
| BlueFS | BlueStore's tiny internal FS, only to host its own RocksDB |
| MON | Monitor — keeps the authoritative cluster maps, forms quorum |
| quorum | the MON majority that must agree before a map change commits |
| monmap | the map of the MONs themselves: who they are, where they listen |
| osdmap | the map of OSDs (which exist, up/in state) — versioned by epoch |
| epoch | a map's version number, bumped on every change (`osdmap e186`) |
| MGR | Manager — metrics, orchestration modules, balancer, dashboard |

**Placement** — how an object finds its disks (Section 6 traces
this live), and the PG states you will see in `ceph -s`:

| Term | Meaning |
|------|---------|
| Pool | a namespace of objects with a replication/EC policy |
| PG | Placement Group — a shard of a pool; unit of replication/recovery |
| CRUSH | the placement function: PG → list of OSDs, computed, not looked up |
| failure domain | the level CRUSH spreads replicas across: OSD, host, rack |
| device class | `hdd`/`ssd`/`nvme`, auto-detected; CRUSH rules can select on it |
| up set | the OSDs CRUSH says should hold a PG right now |
| acting set | the OSDs actually serving it — differs from `up` during recovery |
| primary | the first OSD of the acting set; all client I/O for the PG goes there |
| active+clean | PG state: serving I/O, every replica current — the goal |
| degraded | PG state: at least one object has fewer copies than it should |
| undersized | PG state: the acting set is smaller than the pool's `size` |
| peering | PG state: replicas reconciling history before serving I/O |

**Authentication** — the cephx cast, used from the first key in
Section 3.2 and unpacked fully in Section 7:

| Term | Meaning |
|------|---------|
| cephx | shared-secret auth: the MON stores all keys and issues tickets |
| principal | a named identity in cephx: `mon.`, `client.admin`, `osd.0` |
| key | a principal's secret — in a keyring file and the MON's database |
| caps | a principal's rights, per daemon type: `osd 'allow rwx'`, ... |
| profile | a canned cap bundle: `allow profile osd`, `profile mds`, ... |
| ticket | Kerberos-style token: identity + caps + session key (Sec 7) |
| session key | fresh per-login secret both sides share to key the talk |
| authenticator | timestamp sealed with the session key, proving key receipt |

**Interfaces and deployment** — what users actually touch
(Section 5 uses all three):

| Term | Meaning |
|------|---------|
| RBD | RADOS Block Device — virtual disks striped over RADOS objects |
| CephFS | POSIX filesystem on RADOS; an MDS daemon serves the metadata |
| MDS | Metadata Server — CephFS's directory tree and inode authority |
| RGW | RADOS Gateway — S3/Swift-compatible HTTP object storage |
| cephadm | production deployment tool — daemons as podman containers |

The key architectural idea: **clients compute data locations instead of
asking a central server**. An object name is hashed to a PG, and CRUSH
maps the PG to a set of OSDs using only the compact cluster map that
MONs distribute. There is no lookup table in the data path, which is
what lets Ceph scale out without a metadata bottleneck (CephFS being
the exception: POSIX semantics need a real metadata server, the MDS —
but file *data* still goes straight from client to OSDs).

```
   +-----------+    +------------+    +---------------------+
   |    RBD    |    |   CephFS   |    |    RGW  (S3 API)    |
   |  (block)  |    |   (file)   |    |      (object)       |
   +-----+-----+    +-----+------+    +----------+----------+
         |                |      \               |
   krbd or librbd   kernel client \_ MDS      radosgw daemon
         |          or libcephfs  (metadata)     |
   +-----v----------------v-----------------------v---------+
   |              librados  /  RADOS protocol               |
   +----------------------------+---------------------------+
                                |
                object name --hash--> PG --CRUSH--> OSDs
                                |
     +-------------+------------+------------+-------------+
     |             |                         |             |
 +---v----+   +----v---+   +--------+   +----v---+   +-----v--+
 |  c22   |   |  c23   |   |  c24   |   |  c25   |   |  c21   |
 | OSD 0-3|   | OSD 4-7|   |OSD 8-11|   |OSD12-15|   |MON,MGR |
 | MON    |   |        |   |        |   | MDS    |   |MDS,RGW |
 +--------+   +--------+   +--------+   +--------+   +--------+
   \____________ replicas land on three distinct hosts ____/
```

Every interface at the top decomposes user data into RADOS objects
(typically 4 MiB) at the bottom. That single fact is what Section 6
exploits to trace a file's bytes to a physical disk offset on a named
machine.

# 2. The lab: five nodes, sixteen OSDs

## 2.1 The cluster

Everything below runs on a small private lab: **five Fedora 44 virtual
machines** on one virtual network (`10.0.0.0/24`), named `c21`–`c25`.
Ceph comes from ordinary Fedora packages and every daemon runs as a
plain **systemd service on the host** — not in containers, and with no
orchestrator. That choice is the point: every file, unit and command
below is visible with `ls` and `systemctl`, with nothing hidden inside
`ceph orch` or a container image. It is the [manual deployment
procedure][doc-manual] upstream documents, carried out across five
machines.

Roles are spread the way a small production cluster would spread them:

| Node | Ceph roles | Storage |
|------|-----------|---------|
| `c21` | MON, MGR, MDS, RGW, and the admin/client host | none |
| `c22` | MON, 4 OSDs | 4 × 6 GiB |
| `c23` | 4 OSDs | 4 × 6 GiB |
| `c24` | 4 OSDs | 4 × 6 GiB |
| `c25` | MDS, 4 OSDs | 4 × 6 GiB |

Sixteen OSDs, 96 GiB raw. Every `ceph` command in this post is run on
`c21`, which holds no data at all — so when Section 5 maps an RBD image
and mounts CephFS there, the I/O really does cross the network to the
storage nodes. That is the arrangement a real client sees, and it is
the reason a multi-node lab is worth the trouble: on a single machine,
"the client computes placement and contacts the right OSD directly" is
a claim you have to take on faith.

Each storage node's four disks are deliberately attached over different
emulated buses — virtio, SCSI and NVMe — because that is what decides
the **device class**:

```
[c24]# for d in vdb sda sdb nvme0n1; do
         printf "%-10s rotational=%s\n" "$d" "$(cat /sys/block/$d/queue/rotational)"
       done
vdb        rotational=1
sda        rotational=1
sdb        rotational=1
nvme0n1    rotational=0
```

Ceph reads that flag and labels each OSD `hdd` or `ssd`, giving three
HDD-class and one SSD-class device per host. Nothing here is really
rotating rust — but the *classes* are real as far as CRUSH is
concerned, and that is enough to do what production clusters do: put
CephFS metadata on the fast class and bulk data on the slow one
(Section 5.2), with CRUSH rules that select on it (Section 4.2).

## 2.2 What this lab is not

Three honest caveats, because they show up in the output:

- **Two monitors is worse than one.** A MON quorum needs a strict
  majority, and the majority of two is two — so this cluster tolerates
  zero MON failures, exactly like a single MON, while needing two
  machines up to work at all. Production runs 3 or 5. The pair here
  demonstrates *how* a monitor joins an existing quorum (Section 3.5),
  which is worth showing; it buys no availability.
- **The disks are virtual.** Underneath the guests, all sixteen "disks"
  are files on one laptop SSD, so the cluster permanently reports
  `BLUESTORE_SLOW_OP_ALERT` — BlueStore noticing that operations take
  longer than it expects. It is a true observation about slow storage,
  not a Ceph problem, and it is the only health warning left standing
  in every `ceph -s` below.
- **One network.** Ceph can separate a *public* network (clients ↔
  OSDs) from a *cluster* network (OSD ↔ OSD replication and recovery);
  here both are `10.0.0.0/24`.

If you want to follow along without five machines, two documented paths
give a real RADOS cluster on one host: `cephadm bootstrap
--single-host-defaults` ([docs][doc-cephadm]) for the containerized
production tool, or Ceph's own [`vstart.sh`][vstart] for a throwaway
cluster of plain processes out of a build tree (Section 8.1).
Sections 5–7 are identical on all three.

# 3. Bootstrapping the cluster by hand

There is no `ceph orch`, no reconciliation loop and no container image
in what follows — just the commands, in order, that turn five bare
Fedora machines into a Ceph cluster. This is the section worth reading
even if you will only ever run cephadm, because cephadm does exactly
these steps for you and knowing them turns "mysterious distributed
system" into "a sequence you could have typed".

The packages, installed per role:

| Package | Role | What it provides |
|---------|------|------------------|
| `ceph-common` | everywhere | `ceph`, `rbd`, `rados`, `ceph-authtool`, `mount.ceph` |
| `ceph-base` | (dependency) | `monmaptool` and the other offline map tools |
| `ceph-mon` | monitors | the monitor daemon |
| `ceph-mgr` | managers | the manager daemon and its Python modules |
| `ceph-osd` | storage | `ceph-osd`, `ceph-objectstore-tool`, `ceph-bluestore-tool` |
| `ceph-volume` | storage | provisions OSDs onto devices — **not** pulled in by `ceph-osd` |
| `ceph-mds` | metadata | the CephFS metadata server |
| `ceph-radosgw` | gateway | the S3/Swift HTTP daemon |

## 3.1 The config file

A brand-new cluster needs a `fsid` (any UUID) and a first monitor.
`/etc/ceph/ceph.conf` on the bootstrap host, and nothing more:

```
[global]
fsid = 8830b0e0-0d9f-4729-b01d-73c5dcda498e
mon initial members = c21                                          (1)
mon host = 10.0.0.21                                               (2)
public network = 10.0.0.0/24
auth cluster required = cephx                                      (3)
auth service required = cephx
auth client required = cephx
osd memory target = 1073741824                                     (4)
```

1. The quorum expected at startup. This stays pinned to the bootstrap
   set as monitors are added — growing it mid-rollout would briefly
   declare an even-numbered expected quorum, which is exactly the
   configuration that cannot form a majority.
2. Where to *find* monitors. This one does have to track the live set,
   and updating it on every host is the one piece of distributed state
   you maintain by hand (Section 3.8).
3. cephx on for daemons authenticating to the cluster, for services,
   and for clients. It is the default, and Section 7 explains what it
   buys.
4. Each OSD is told to aim for 1 GiB of memory instead of the 4 GiB
   default — four OSDs to a small VM.

Everything else these daemons need is learned from the monitor after
connecting, or lives in the MON's config store (Section 4.2), which is
why the file is short and rarely changes.

## 3.2 Three keys before the cluster exists

cephx is Ceph's shared-secret authentication: named principals, keys,
and Kerberos-style tickets that let daemons verify callers locally
(Section 7 unpacks the machinery). What matters for bootstrap is one
fact: the **MON is the key authority**. Every later command and every
daemon authenticates against it — but the tools that normally create
keys need a running, authenticated cluster themselves. That circle is
broken by minting a few keys *offline*, as plain files, before any
daemon starts.

```
[c21]# ceph-authtool --create-keyring /tmp/ceph.mon.keyring \
           --gen-key -n mon. --cap mon 'allow *'                   (1)
creating /tmp/ceph.mon.keyring

[c21]# ceph-authtool --create-keyring /etc/ceph/ceph.client.admin.keyring \
           --gen-key -n client.admin \
           --cap mon 'allow *' --cap osd 'allow *' \
           --cap mds 'allow *' --cap mgr 'allow *'                 (2)

[c21]# install -d -o ceph -g ceph /var/lib/ceph/bootstrap-osd
[c21]# ceph-authtool --create-keyring /var/lib/ceph/bootstrap-osd/ceph.keyring \
           --gen-key -n client.bootstrap-osd \
           --cap mon 'profile bootstrap-osd' --cap mgr 'allow r'    (3)

[c21]# ceph-authtool /tmp/ceph.mon.keyring \
           --import-keyring /etc/ceph/ceph.client.admin.keyring     (4)
[c21]# ceph-authtool /tmp/ceph.mon.keyring \
           --import-keyring /var/lib/ceph/bootstrap-osd/ceph.keyring
```

1. **`mon.` — the authority's own identity.** The monitor validates
   everyone else's keys, but with `auth cluster required = cephx` it
   needs a key of its own before it can start. In a multi-monitor
   cluster this same shared key is also how monitors trust each other
   in quorum — note in Section 3.5 that the second monitor is given
   *this* key, not one of its own.
2. **`client.admin` — your identity.** This is the principal you act as
   for the rest of the post: every `ceph`, `rbd` and `rados`
   invocation, and both kernel mounts. It too must exist before the
   cluster does: the moment the MON is up with cephx required, even
   `ceph auth get-or-create` — the command that creates keys — demands
   an authenticated caller. Without a pre-seeded admin key you would be
   locked out by the very auth you just enabled.
3. **`client.bootstrap-osd` — a deliberately weak key.** Its single cap
   lets it register new OSDs and do nothing else. This is what a
   storage host is given so it can create its own OSD identities
   (Section 3.6) without ever holding an admin key. Generating it by
   hand is in fact belt and braces: the monitor mints the whole family
   itself the first time the cluster comes up
   (`AuthMonitor::_generate_bootstrap_keys` in [`src/mon/`][src-mon],
   reached from `create_initial()`), so `bootstrap-osd`, `-mds`,
   `-mgr`, `-rgw`, `-rbd` and `-rbd-mirror` all appear in Section 4.3's
   listing even though only this one was ever used here.
4. `--import-keyring` merges the other two into the mon keyring,
   because `ceph-mon --mkfs` seeds its auth database from exactly one
   file. After mkfs, the MON's own store is the source of truth and
   these files are just client-side credentials.

Everything else in the cluster — `mgr.c21`, `osd.0`–`osd.15`,
`mds.c21`, `mds.c25`, `client.rgw.c21` — is minted **online** with
`ceph auth get-or-create` or by `ceph-volume`, authenticated as
`client.admin`. Watch for those calls in the sections that follow.

## 3.3 The first monitor

A monitor cannot ask a monitor where the monitors are, so the very
first one is built from a **monmap constructed offline**:

```
[c21]# monmaptool --create --fsid 8830b0e0-0d9f-4729-b01d-73c5dcda498e \
           --addv c21 '[v2:10.0.0.21:3300,v1:10.0.0.21:6789]' /tmp/monmap
monmaptool: monmap file /tmp/monmap
setting min_mon_release = tentacle
monmaptool: set fsid to 8830b0e0-0d9f-4729-b01d-73c5dcda498e
monmaptool: writing epoch 0 to /tmp/monmap (1 monitors)
```

Use `--addv` with **both** addresses, not `--add` with a bare IP. A
bare IP records only the legacy msgr1 address (port 6789), so the
bootstrap monitor comes up without msgr2 — a permanent
`MON_MSGR2_NOT_ENABLED` warning, and, worse, `rbd map` fails outright
because krbd defaults to msgr2. Monitors that join later inherit both
addresses from the live monmap, so **only the first monitor can have
this defect**, which is precisely what makes it easy to miss.

Then build the store and start the daemon:

```
[c21]# install -d -o ceph -g ceph /var/lib/ceph/mon/ceph-c21          (1)
[c21]# sudo -u ceph ceph-mon --mkfs -i c21 \
           --monmap /tmp/monmap --keyring /tmp/ceph.mon.keyring       (2)
[c21]# systemctl enable --now ceph-mon@c21                            (3)
[c21]# rm -f /tmp/monmap /tmp/ceph.mon.keyring                        (4)
```

1. The directory name is `<cluster>-<id>`; the daemon derives it from
   its own id, which is why one templated unit file serves every
   monitor.
2. mkfs builds the monitor's private store — a small RocksDB — and
   seeds it with the monmap and the three keys. Run it **as the `ceph`
   user**: a root-owned store leaves the daemon unable to open its own
   files, and the resulting error names permissions on a path, not the
   mistake.
3. `ceph-mon@c21` — the templated unit instantiated for this id.
4. Staging files, done with. That keyring holds the `mon.`, admin and
   bootstrap secrets in one world-visible path; nothing needs it after
   mkfs.

The monitor is now the cluster. It holds the authoritative, versioned
maps — monmap, osdmap, CRUSH map, MDS map, and the cephx key database —
and distributes them to every client and daemon, which *subscribe* to
updates rather than poll. Every `ceph` command in this post is a
conversation with it. What never touches it: your data. It knows where
everything *may* be placed and stores none of it.

## 3.4 The manager

```
[c21]# ceph auth get-or-create mgr.c21 \
           mon 'allow profile mgr' osd 'allow *' mds 'allow *'        (1)
[c21]# install -d -o ceph -g ceph /var/lib/ceph/mgr/ceph-c21
[c21]# ceph auth get mgr.c21 > /var/lib/ceph/mgr/ceph-c21/keyring     (2)
[c21]# chown ceph:ceph /var/lib/ceph/mgr/ceph-c21/keyring
[c21]# chmod 600 /var/lib/ceph/mgr/ceph-c21/keyring                   (3)
[c21]# systemctl enable --now ceph-mgr@c21
```

1. The first *online* key mint — the pattern promised in 3.2: an
   authenticated `client.admin` asks the MON to create `mgr.c21`.
   `allow profile mgr` is a canned cap bundle meaning "what a manager
   legitimately needs", maintained upstream; hand-writing the
   equivalent rule set would be both verbose and a security bug waiting
   to happen.
2. The MON is now the source of truth for that key; `ceph auth get`
   exports a copy in keyring format for the daemon to read.
3. Not optional. A shell redirection creates the file at `0666 & ~umask`
   = `0644`, so without this the manager's key is world-readable on the
   host. The same applies to every `ceph auth get > ...` below.

Why a second brain? The MGR exists to keep the MON's Paxos path lean:
everything that is *reporting* rather than *authority* moved there.
OSDs stream their PG and performance statistics to the MGR, so the
`data:` section of `ceph -s`, `ceph df` and `ceph fs status` are
answered from it — with no active MGR the cluster still serves I/O, but
those numbers freeze and health complains. It also hosts the Python
modules: the PG autoscaler, the balancer, progress bars, the dashboard,
the Prometheus exporter, and the orchestrator API that cephadm plugs
into (absent here, which is why Section 5.2 creates CephFS pools by
hand instead of using `ceph fs volume create`). Production runs one
active MGR plus standbys.

At this point the cluster is alive and completely empty: `ceph -s`
already answers, reporting a one-member quorum, an active manager and
`0 osds: 0 up, 0 in`. Two daemons on one machine are enough to be a
Ceph cluster — there is simply nowhere to put anything yet.

## 3.5 A second monitor joins

The difference between bootstrapping a monitor and adding one is the
whole lesson: **a joining monitor is built from the running cluster's
monmap, not a new one.**

```
[c21]# ceph mon getmap -o /tmp/monmap                                 (1)
[c21]# ceph auth get mon.                                             (2)
[mon.]
	key = <the shared mon. secret>
	caps mon = "allow *"
        ... copy both files to c22 ...

[c22]# install -d -o ceph -g ceph /var/lib/ceph/mon/ceph-c22
[c22]# sudo -u ceph ceph-mon --mkfs -i c22 \
           --monmap /tmp/monmap --keyring /tmp/ceph.mon.keyring       (3)
[c22]# systemctl enable --now ceph-mon@c22
```

1. Not `monmaptool --create`. The live monmap already carries the fsid,
   the existing member and its v2/v1 addresses, so the new monitor
   knows who to contact and joins the quorum on start. This is also why
   only the first monitor can be missing its msgr2 address.
2. All monitors share the single `mon.` key from 3.2 — it is how they
   authenticate to *each other*, so a joining monitor gets a copy of it
   rather than an identity of its own. It is the one principal in the
   cluster that is not per-daemon.
3. Same mkfs as before, same `ceph` user, same reasons.

Once quorum has two members, every host's `ceph.conf` needs the new
`mon host` line (Section 3.8), or its daemons will keep dialling a
one-member list.

## 3.6 Sixteen OSDs

An OSD host is given the weak `client.bootstrap-osd` key from 3.2 and
nothing else:

```
[c23]# install -d -m 750 -o ceph -g ceph /var/lib/ceph/bootstrap-osd
        ... copy client.bootstrap-osd's keyring here, mode 600 ...
```

Then one command per device does everything:

```
[c23]# ceph-volume lvm create --data /dev/vdb
[c23]# ceph-volume lvm create --data /dev/sda
[c23]# ceph-volume lvm create --data /dev/sdb
[c23]# ceph-volume lvm create --data /dev/nvme0n1
```

That single invocation, per disk:

1. creates an LVM volume group and one logical volume spanning the
   device, tagged with the cluster fsid and the OSD's uuid;
2. asks the monitor — authenticating as `client.bootstrap-osd` — for
   the next free OSD id and registers a freshly generated cephx key for
   it;
3. writes the BlueStore label onto the volume and formats it
   (Section 6.4 reads that label back);
4. creates `/var/lib/ceph/osd/ceph-N` with the identity markers and the
   `block` symlink;
5. adds the OSD to the CRUSH map under this host, with a weight derived
   from its capacity and a class derived from `rotational`;
6. enables `ceph-osd@N` and starts it.

Two things worth knowing when you script this. The host's CRUSH bucket
does not appear in `ceph osd tree` until its *first* OSD reports in —
so a host looks absent for a while even though the command succeeded.
And `ceph-volume` returns once the daemon has been started, but an OSD
takes another 25–35 seconds to boot into the osdmap; "the command
printed success" and "the OSD is up" are half a minute apart. Poll
`ceph osd stat` rather than assuming.

  ...
-10         0.02356      host c24

  9    hdd  0.00589          osd.9       up   1.00000  1.00000

1. The CRUSH hierarchy built up by those sixteen commands: a `root`
   containing four `host` buckets, each containing its OSDs. This shape
   is the whole reason CRUSH can promise "three replicas on three
   different machines". Weight is capacity in TiB (≈ 0.00589 for a
   6 GiB device).
2. `osd.3` is the NVMe device — `rotational=0`, so Ceph filed it under
   class `ssd`.

Note what did **not** happen: no filesystem was made on any of those
devices, and no data directory holds any data. Section 4.4 shows what
an OSD directory actually contains.

## 3.7 Two MDS daemons

```
[c21]# ceph auth get-or-create mds.c21 \
           mon 'profile mds' mgr 'profile mds' mds 'allow *' osd 'allow *'
[c21]# install -d -o ceph -g ceph /var/lib/ceph/mds/ceph-c21
[c21]# ceph auth get mds.c21 > /var/lib/ceph/mds/ceph-c21/keyring
[c21]# chown ceph:ceph /var/lib/ceph/mds/ceph-c21/keyring
[c21]# chmod 600 /var/lib/ceph/mds/ceph-c21/keyring
[c21]# systemctl enable --now ceph-mds@c21
        ... and the same on c25 ...
```

`profile mds` rather than `allow *` on mon and mgr: the profile grants
exactly what an MDS needs — notably the right to add itself to the MDS
map — and nothing else.

Both daemons come up in **standby** and stay there, because there is no
filesystem yet. That is not a failure state; an MDS holds no durable
data of its own, so starting one costs nothing and moves nothing. It is
`ceph fs new` (Section 5.2) that promotes one of them to serve rank 0 —
which is why that command appears to conjure a working metadata server
out of nowhere.

## 3.8 What you maintain by hand

Without an orchestrator there is no reconciliation loop, and exactly
one piece of state has to be pushed around by hand: **`mon host` in
`/etc/ceph/ceph.conf`, on every host, whenever the monitor set
changes**. A host left with a stale list cannot find quorum, and the
symptom — daemons that start and then hang — names nothing useful. So
after each monitor is added, the file is regenerated from the live
`ceph mon dump` and written to every member:

```
[global]
fsid = 8830b0e0-0d9f-4729-b01d-73c5dcda498e
mon initial members = c21                                          (1)
mon host = 10.0.0.21,10.0.0.22                                     (2)
public network = 10.0.0.0/24
auth cluster required = cephx
auth service required = cephx
auth client required = cephx
osd memory target = 1073741824
```

1. Still pinned to the bootstrap set, as in 3.1.
2. Now both monitors.

The other manual step is credential distribution, and it is worth being
deliberate about: the admin keyring goes only to hosts that are meant
to administer the cluster. `c21` and `c22` have it; `c23`, `c24` and
`c25` store and serve real user data — each of them is the primary for
a share of the cluster's PGs — and hold no admin credential at all.
Section 4.3 shows the difference on disk.

Two habits this kind of by-hand deployment teaches, both of which cost
real time to learn: `systemctl enable --now` returns when systemd has
*forked* the daemon, not when the daemon has registered with the
cluster — so an MDS that never joins looks exactly like success. And
more generally, "the command printed success" is not "the state is
correct": check `ceph -s`, `ceph osd stat`, `ceph node ls` afterwards.
This is the entire job cephadm's orchestrator exists to do for you.

## 4.2 The maps

Each map has an **epoch** that bumps on every change. The **monmap**
first, the one map that must be known before anything else can be
learned:

```
[c21]# ceph mon dump
epoch 2
fsid 8830b0e0-0d9f-4729-b01d-73c5dcda498e
last_changed 2026-07-28T03:43:07.068818+0000
created 2026-07-28T03:43:03.174021+0000
min_mon_release 20 (tentacle)
election_strategy: 1
0: [v2:10.0.0.21:3300/0,v1:10.0.0.21:6789/0] mon.c21                    (1)
1: [v2:10.0.0.22:3300/0,v1:10.0.0.22:6789/0] mon.c22                    (2)
```

1. Both addresses, as Section 3.3 insisted: **msgr2** (`v2:`, port
   3300, the modern protocol with framing and CRC or AES-GCM modes) and
   legacy **msgr1** (`v1:`, port 6789). Clients prefer v2 and fall back.
2. Epoch 2 — the map changed once, when `mon.c22` joined.

Device classes are implemented with a trick worth seeing, because it
explains why selecting on them costs nothing at placement time. CRUSH
does not filter by class while computing; instead the monitor maintains
a **shadow tree per class**, and a class-aware rule simply starts from
a different root:

```
[c21]# ceph osd crush tree --show-shadow
ID   CLASS  WEIGHT   TYPE NAME
 -6    ssd  0.02356  root default~ssd                                   (1)
 -5    ssd  0.00589      host c22~ssd
  3    ssd  0.00589          osd.3
 -9    ssd  0.00589      host c23~ssd
  7    ssd  0.00589          osd.7
-12    ssd  0.00589      host c24~ssd
 11    ssd  0.00589          osd.11
-15    ssd  0.00589      host c25~ssd
 15    ssd  0.00589          osd.15
 -2    hdd  0.07068  root default~hdd                                   (2)
 -4    hdd  0.01767      host c22~hdd
  0    hdd  0.00589          osd.0
  1    hdd  0.00589          osd.1
  2    hdd  0.00589          osd.2
  ...
 -1         0.09424  root default                                       (3)
  ...
```

1. `default~ssd` is a synthetic root holding only the SSD-class OSDs,
   with the same host structure — so a rule over it still spreads
   replicas across four machines.
2. Likewise `default~hdd`, with three devices per host.
3. The real tree, unchanged, for rules that do not care.

The rules themselves are tiny programs. Two are added here, one per
class:

```
[c21]# ceph osd crush rule create-replicated hdd-rule default host hdd
[c21]# ceph osd crush rule create-replicated ssd-rule default host ssd
[c21]# ceph osd crush rule ls
replicated_rule
hdd-rule
ssd-rule
[c21]# ceph osd crush rule dump ssd-rule
{
    "rule_id": 2,
    "rule_name": "ssd-rule",
    "type": 1,
    "steps": [
        { "op": "take", "item": -6, "item_name": "default~ssd" },       (1)
        { "op": "chooseleaf_firstn", "num": 0, "type": "host" },        (2)
        { "op": "emit" }
    ]
}
```

1. `take` the shadow root — the entirety of "only use SSDs".
2. `chooseleaf_firstn 0 type host`: pick as many hosts as the pool's
   `size` requires, one leaf OSD from each. **This is the failure
   domain**, and it is why a pool with `size 3` on this cluster
   survives losing any one machine. On a single-host cluster this must
   be lowered to `type osd`, which quietly gives up that property.

Finally, the **config store**. Modern Ceph keeps most configuration in
the monitor rather than in `ceph.conf`, so changing an option does not
mean touching every host:

```
[c21]# ceph config dump
WHO             MASK  LEVEL     OPTION                                 VALUE            RO
mon                   advanced  auth_allow_insecure_global_id_reclaim  false
osd.3                 basic     osd_mclock_max_capacity_iops_ssd       10209.030373
osd.7                 basic     osd_mclock_max_capacity_iops_ssd       11026.548956
osd.11                basic     osd_mclock_max_capacity_iops_ssd       6224.827446
osd.15                basic     osd_mclock_max_capacity_iops_ssd       11231.329389
client.rgw.c21        basic     rgw_frontends                          beast port=8000  *
```

The `osd_mclock_max_capacity_iops_ssd` entries were not set by hand:
each SSD-class OSD benchmarks itself on first start and stores the
result, which the mClock QoS scheduler then uses to divide throughput
between client I/O and background work like recovery and scrub. A good
illustration of the config store's purpose — daemons write to it too,
not just admins. (A practical consequence: OSD ids are reused, so
purging an OSD without also clearing its config section leaves a
measured capacity that the *next* osd.N will silently inherit.)

## 4.3 Identity: who exists, and who holds which key

The monitor's auth database is the only authoritative answer to "who
may do what":

	caps: [mgr] allow profile osd
	caps: [mon] allow profile osd
	caps: [osd] allow *
...                                       # osd.1 .. osd.15, identical

	caps: [mds] allow *
	caps: [mgr] profile mds                                          (1)
	caps: [mon] profile mds
	caps: [osd] allow *
mds.c25
	...
mgr.c21
	caps: [mds] allow *
	caps: [mon] allow profile mgr
	caps: [osd] allow *
client.admin                                                             (2)
	caps: [mds] allow *
	caps: [mgr] allow *
	caps: [mon] allow *
	caps: [osd] allow *
client.bootstrap-osd                                                     (3)
	caps: [mgr] allow r
	caps: [mon] profile bootstrap-osd

	caps: [mon] allow profile bootstrap-mds

	...
client.rgw.c21                                                           (4)
	caps: [mon] allow rw
	caps: [osd] allow rwx
```

1. `profile mds` and `allow profile osd` are the same construct written
   two ways — the bare form is what Section 3.7 typed, the `allow`
   prefix is what `ceph-volume` emits. Both parse identically.
2. `client.admin` is the superuser. **Treat its keyring like a root SSH
   key**: it can destroy, reconfigure or read anything in the cluster.
   It belongs on monitor nodes, dedicated admin/bastion hosts, and
   orchestration hosts, and nowhere else.
3. The `bootstrap-*` principals from Section 3.2 — deliberately weak,
   and all six minted by the monitor itself at cluster creation, so
   `-mds`, `-mgr`, `-rgw`, `-rbd` and `-rbd-mirror` exist here despite
   only `bootstrap-osd` ever being used.
4. RGW is just another client from RADOS's point of view: `rw` on the
   monitor, `rwx` on OSDs, no admin rights.

Where those keys actually sit is the part a single-machine lab cannot
show. Compare the admin node with a pure storage node:

```
[c21]# ls -l /etc/ceph/ceph.conf /etc/ceph/ceph.client.admin.keyring

-rw-r--r-- 1 root root 259 Jul 28 08:32 /etc/ceph/ceph.conf

[c23]# ls -l /etc/ceph/
-rw-r--r-- 1 root root 259 Jul 28 08:32 ceph.conf
-rw-r--r-- 1 root root  92 Jun 23 00:00 rbdmap
```

What does `c23` actually hold? Ask the PG map rather than guessing:

```
[c21]# ceph pg dump pgs_brief --format=json | python3 -c '
import json,sys
pgs = json.load(sys.stdin)["pg_stats"]
c23 = {4,5,6,7}
print("total PGs           :", len(pgs))
print("with a copy on c23  :", sum(1 for p in pgs if c23 & set(p["acting"])))

```

1. Not all 87. With `size 3` and a failure domain of `host`, CRUSH
   picks **three of the four** storage hosts for each PG — so every
   host sits out roughly a quarter of them. No single machine in this
   cluster holds a copy of everything, which is rather the point.
2. And for 24 PGs `c23` is not a passive copy but the **primary**:
   clients send their reads and writes for those straight to it, and it
   is the OSD that orders the write and replicates onward. "Storage
   node" does not mean "backup node".

That machine nonetheless has **no admin keyring at all**. Its daemons
authenticate with their own per-OSD keys, kept beside their data:

```
[c23]# cat /var/lib/ceph/osd/ceph-4/keyring
[osd.4]
key = <osd.4's secret>

[c23]# ls -l /var/lib/ceph/bootstrap-osd/
-rw------- 1 ceph ceph 129 Jul 28 03:43 ceph.keyring                    (1)
```

1. The only other credential the host ever received — the weak
   bootstrap key of Section 3.6.

That is least privilege made concrete: compromising `c23` yields "the
ability to be `osd.4`–`osd.7`", never "the ability to be admin".

Two properties of keyrings are worth stating explicitly, because they
are commonly misread. A keyring is **not authorization**: the `caps`
lines you sometimes see in a keyring file are a cached, human-readable
note, and the monitor's database alone decides what a principal may do.
And it is **not state**: lose a daemon's keyring and its data is intact
— the daemon simply cannot log in until an admin re-exports the key
with `ceph auth get osd.4`, since the MON's copy is authoritative.

Under `/var/lib/ceph`, each role gets a directory named
`<cluster>-<id>`. The monitor's is the cluster's memory:

```

created_at                 kv_backend  store.db

[c21]# du -sh /var/lib/ceph/mon/ceph-c21/store.db/

```

A few one-line text markers so tools can identify the directory, plus
an ordinary **RocksDB** — what `ceph-mon --mkfs` created in Section 3.3.
Inside it: the full history of every cluster map (that is what the
epochs count), the cephx key database of 4.3, and the Paxos transaction
log that makes quorum work. Why a transactional KV store — a map update
must commit atomically or not at all, the same reasoning that gives
BlueStore its embedded RocksDB.

An OSD's directory is the most instructive listing, because of what is
*missing*:

```
[c24]# ls -l /var/lib/ceph/osd/ceph-9/
lrwxrwxrwx 1 ceph ceph 93 block -> /dev/ceph-70e99fa3-.../osd-block-9398eea9-...  (1)

-rw------- 1 ceph ceph 37 fsid                 (this OSD's uuid)
-rw------- 1 ceph ceph 55 keyring              (osd.9's key only)
-rw------- 1 ceph ceph  6 ready

-rw------- 1 ceph ceph 10 type                 ("bluestore")

TARGET                    SOURCE  FSTYPE

```

1. There are **no data files here**. The `block` symlink — pointing at
   the LVM logical volume `ceph-volume` created in Section 3.6 — is the
   entire storage configuration: everything, data and metadata and
   BlueStore's own RocksDB, lives inside that volume. Section 6.4 reads
   its label.
2. And the directory itself is a **tmpfs**, rebuilt at every boot from
   LVM tags on the volume. The tiny markers exist only so `ceph-osd`
   (and the offline tools of Section 6) can confirm "this is osd.9 of
   cluster X, BlueStore, fully formatted" *before* opening the device.

The rest of the tree follows the same pattern —
`/var/lib/ceph/{mgr,mds,radosgw}/ceph-*/`, each holding little more
than the keyring written in Sections 3.4 and 3.7 — plus
`/var/lib/ceph/crash/` and the `bootstrap-*` directories. Logs land in
`/var/log/ceph/`, one file per daemon, with the cluster-wide
`ceph.log` and `ceph.audit.log` on the monitor.

The punchline: apart from sixteen block devices, this cluster is a
handful of INI files, tiny text markers, and two kinds of RocksDB. Your
*data* appears in none of those paths — it exists only inside the OSDs'
volumes.

## 4.5 How a client finds its data

A client bootstraps exactly the way Section 3.1's config file implies:
read `mon host`, connect, complete the cephx handshake with the
keyring, and receive the current **monmap** — so even a stale address
list repairs itself as long as one listed monitor answers. (Modern Ceph
can also discover monitors via DNS SRV records, making the file
optional.)

With a session established the client subscribes to the **osdmap**,
which carries the OSD list and the CRUSH map. From then on, locating an
object is pure local computation — no network lookup, ever:

1. **Hash the object name.** The name is the only input; nothing about
   the file, image or bucket it came from matters.
   `hash("rbd_data.626e2b7e024e.0000000000000000") = 0x9d9d67ac`
2. **Mask to a PG.** The hash is reduced modulo the pool's PG count
   (a power of two, so it is a mask): with 32 PGs,
   `0x9d9d67ac & 0x1f = 0x0c` → PG `14.c` in pool 14.
3. **Run CRUSH.** Feed the PG id and the current CRUSH map to the
   algorithm; out comes a deterministic, ordered list of OSDs.
   `CRUSH(14.c, map, hdd-rule) = [9, 13, 2]`

Because the name is the only input to placement, an object name must be
unique within its pool; two objects with the same name in different
pools are unrelated.

The list is ordered, and the first entry is the **primary**: barring
the replica-read options of Section 4.6, that is the one the client
talks to. So this object's I/O is destined for `osd.9`.

But `9` is an **integer**, and you cannot open a TCP connection to an
integer. So there is a fourth step, and it is the osdmap's other job:
the same map that feeds CRUSH is also the `osd id → address` table.

```
[c21]# ceph osd find 9
{
    "osd": 9,
    "addrs": {
        "addrvec": [
            { "type": "v2", "addr": "10.0.0.24:6815", "nonce": 1589244358 },  (1)
            { "type": "v1", "addr": "10.0.0.24:6818", "nonce": 1589244358 }
        ]
    },
    "osd_fsid": "9398eea9-6ba2-490d-b664-cda03a075324",
    "host": "c24",
    "crush_location": { "host": "c24", "root": "default" }                    (2)
}
```

1. There is the resolution the client needed: **`osd.9` →
   `10.0.0.24:6815`** over msgr2, or `:6818` for a legacy client. The
   **nonce** distinguishes this incarnation of the daemon from a
   restarted one at the same address.
2. And its place in the CRUSH tree, which is what let CRUSH pick it in
   the first place.

Note what the client did *not* do to obtain that: no name service, no
lookup RPC, no broker. The address table arrived once with the map and
is refreshed only when the map changes. That is the whole reason the
osdmap is worth distributing to every client — it collapses discovery
and placement into a single cached object.

## 4.6 How a client talks to an OSD

Nothing in Section 4.5 needs a kernel. The ordinary Ceph client is a
**userspace library**, `librados` — it is what RGW is built on, what
QEMU links against to give a VM a virtual disk, and what the `rados`
CLI is. krbd and the CephFS kernel client are a *second*, independent
implementation of the same protocol that happens to live in the kernel.
So the clearest way to watch a client work is with no kernel Ceph code
in the picture at all: fetch the object this post traces with
`rados get`, and raise the messenger's log level.

```
[c21]# rados -p rbd --debug-ms=1 get \
           rbd_data.626e2b7e024e.0000000000000000 /tmp/x.bin
```

**A word on what `--debug-ms=1` is, because the distinction matters for
everything below.** It is a *log level*, not an interface. It makes the
messenger print each message it sends and receives; it does not add,
remove or alter a single one of them. The message *set* is identical
with logging off — only the timings pick up the cost of writing each
line down. (The knobs that genuinely do perturb the wire are separate
options nobody sets by accident: `ms_inject_socket_failures`,
`ms_inject_delay_type`, `ms_dump_on_send`.) Nothing in this section
describes a debug facility; the debug facility is only how the
mechanism is made visible. The mechanism is the messages.

        [read 0~4194304] snapc 0=[]
        ondisk+read+known_if_redirected+supports_pool_eio e198)             (7)
 1 -- ... <== osd.9 v2:10.0.0.24:6815/1589244358 1 ==== osd_op_reply(1
        rbd_data.626e2b7e024e.0000000000000000
        [read 0~4194304 out=4194304b] v0'0 uv71 ondisk = 0)
        ==== 182+0+4194304 (crc 0 0 0)                                      (8)
```

1. It dials **both** monitors from `mon host` at once and races them —
   `--2-` is msgr2. Nothing has been looked up yet; these two addresses
   are the only thing the client knew when it started.
2. `10.0.0.21:0/2081066956` is now the client's `entity_addr_t`: its
   address, port 0 because it is not listening, and a random **nonce**
   so two clients on one host are never confused. Then it *subscribes*
   rather than polls — the monitor will push updates for the life of
   the session.
3. `(secure 0 0 0)` — this connection is **encrypted**. See below.
4. A second subscription, this time for the osdmap.
5. And there it is: 13 KB carrying the OSD list, their addresses and
   the CRUSH map. `198..198 src has 1..198` — the client asked for the
   latest and got epoch 198; the monitor advertises that it can supply
   the full history back to epoch 1 for anyone who needs incrementals.
6. **The whole point.** Having received the map, the client computed
   `14.c → [9,13,2]`, resolved `osd.9` to `10.0.0.24:6815`, and
   connected *directly*. It never asked anybody where the object was.
   No lookup message appears in this trace because none exists.
7. The read request. Dissected below.
8. The answer, straight from osd.9 — `182+0+4194304` is front, middle
   and 4 MiB of data — and `(crc 0 0 0)`, **not** encrypted, unlike the
   monitor traffic. Also below.

Contrast that with `ss`, and the userspace/kernel split becomes visible:

```
[c21]# ss -tnp state established | awk 'NR==1 || $4 ~ /10.0.0.2[2-5]:68[0-9][0-9]/'
Recv-Q Send-Q  Local Address:Port   Peer Address:Port  Process
0      0        10.0.0.21:42718      10.0.0.24:6800                            (1)
0      0        10.0.0.21:55634      10.0.0.25:6802
0      0        10.0.0.21:34910      10.0.0.23:6800    users:(("ceph-mgr",...)) (2)
0      0        10.0.0.21:51000      10.0.0.22:6801    users:(("radosgw",...))
```

1. Sockets with **no owning process**: these belong to the kernel
   client, opened by `net/ceph/messenger.c`, which no task owns.
2. Sockets with a process: `librados` inside the manager and the
   gateway. Two implementations, one protocol. OSDs bind upward from
   `ms_bind_port_min` (6800; ceiling `ms_bind_port_max`, 7568), and
   each OSD takes **eight** ports — public, cluster, and two heartbeat
   endpoints, each in a msgr2 and a msgr1 flavour. So the four OSDs on
   one host cover 6800–6831, and every host repeats the same range
   rather than sharing one well-known port.

Sessions are lazy and per-OSD in both implementations: a client
connects to an OSD the first time it has an op for one of its PGs, so a
client touching a few objects holds a few connections, not one per OSD
in the cluster.

**The request.** That `osd_op(...)` line is the entire client/OSD
interface. Its exact shape is `MOSDOp::print` in
[`src/messages/`][src-messages], and it is worth taking apart field by
field:

| Field | Meaning |
|-------|---------|
| `unknown.0.0:1` | the request id: entity name, client incarnation, transaction id — see below |
| `14.c` | the target PG, exactly as the client computed it in 4.5 |
| `14:35e6b9b9:::...:head` | the full object identity — see below |
| `[read 0~4194304]` | the **op vector**: one read, offset 0, length 4 MiB |
| `snapc 0=[]` | snapshot context: which snapshots a write must be preserved against |
| `ondisk+read+known_if_redirected+supports_pool_eio` | flags: durability, this is a read, the client believes its map is current, and it understands the pool-EIO flag |
| `e198` | the osdmap epoch the client used. **This is the safety interlock** |

Five of those deserve more than a table row.

**The request id** `unknown.0.0:1` reads as *entity name*, *client
incarnation*, *transaction id* — and the `unknown` is not what it
looks like. The client is fully authenticated and holds a global id;
run the same command with `--debug-monc=10` and
`monclient: authenticate success, global_id 25806` is logged well
before this line, as it must be, since the osdmap arrived over that
authenticated session. The name is blank because **msgr2 does not put
the sender's name on the wire**: `MOSDOp`'s sending constructor never
fills it in, and `get_reqid()` falls back to a default-constructed
`entity_name_t`, whose type 0 prints as `unknown`. The *receiver*
stamps the real name from the authenticated connection — which is
exactly why the same operation shows up as `client.25226.0:3089` when
we look at it from the OSD's side later in this section. Only the last
field moves between requests: the next op in the same run is
`unknown.0.0:2`.

**The object identity** `14:35e6b9b9:::rbd_data...:head` is a
`hobject_t`, printed by `operator<<` in [`src/common/`][src-common] as
`pool : hash : namespace : key : name : snapshot`. The two empty fields
— hence `:::` — are the namespace and the locator key, both unused
here. And `35e6b9b9` is not a different hash from Section 4.5's
`0x9d9d67ac`; it is the same number with its **bits reversed**:

```
0x9d9d67ac = 1001 1101 1001 1101 0110 0111 1010 1100
reversed   = 0011 0101 1110 0110 1011 1001 1011 1001 = 0x35e6b9b9
```

The printer calls `get_bitwise_key_u32()`, which returns
`_reverse_bits(hash)` — and, more importantly, so does the comparison
operator. Objects are *sorted* by the reversed hash, which scatters
consecutive names across the keyspace while keeping each PG's objects
contiguous. That ordering is what BlueStore's RocksDB and every PG scan
rely on.

**The op vector** is a vector because one request can carry several
operations applied atomically to a single object — a write, an xattr
update and an omap key, all committed or none. It is also the extension
point RADOS classes hook into, letting a client invoke server-side code
on the object rather than dragging it across the network.

**The epoch** is what keeps a stale client from doing damage, and it is
the interlock that makes client-side placement safe at all. Every op
carries the map version its sender used. On the receiving side:

- If the sender is behind, `OSDService::maybe_share_map` pushes the
  **incremental** maps it is missing — just the range
  `(projected_epoch, osdmap]` — back down the same connection. Nobody
  polls for map updates; they ride along with ordinary traffic.
- If the op is *misdirected* — this OSD is not the primary for that PG
  under the current map — `PrimaryLogPG::do_op` simply **returns**. No
  error reply, no redirect; the op is dropped. (It calls
  `handle_misdirected_op` on the way out, but that is a debug hook: it
  returns immediately unless `osd_debug_misdirected_ops` is set, which
  by default it is not. The dropping is the bare `return`.) The client
  resends, having just been handed the newer map by the bullet above.

So a client whose map has gone stale corrupts nothing, and this
particular mistake needs no error path at all: it sends to the OSD it
computed, receives a map update and silence, recomputes, and sends
again. Other stale-client conditions *are* answered explicitly —
`do_op` replies `-EPERM`, `-EBLOCKLISTED`, or `-EAGAIN` for a laggy PG
— so the silence is specific to "right cluster, wrong OSD", the one
case the client can fix by itself.

**Encrypted or not** is the difference between `(secure 0 0 0)` on the
monitor messages and `(crc 0 0 0)` on the OSD reply, and it is not an
accident of this lab. The defaults in `src/common/options/`:

| Option | Default | Governs |
|--------|---------|---------|
| `ms_mon_client_mode` | `secure crc` | client → monitor |
| `ms_client_mode` | `crc secure` | client → OSD/MDS |
| `ms_cluster_mode` | `crc secure` | OSD ↔ OSD |

The rule is narrower than "control plane versus data plane", and it is
worth stating exactly: **traffic to a monitor is encrypted by default;
everything else is not**. Keys and auth tickets go over AES-GCM because
they are fetched from a monitor. But plenty of control traffic never
touches one — OSD-to-OSD peering, PG state, and, most pointedly, the
incremental osdmaps that `maybe_share_map` pushes down the *client/OSD*
connection two paragraphs ago. Those ride a `crc` connection like your
data does: integrity-checked, not confidential.

The lists are preference-ordered, so flipping `ms_client_mode` to
`secure crc` — or mounting with `ms_mode=secure` — encrypts the rest,
at a real CPU cost.

**The knobs.** Most of a client's behaviour is settable, whether it is
librados reading `ceph.conf` or a kernel client taking mount options.
The ones worth knowing early:

| Option | Effect |
|--------|--------|
| `ms_mode=legacy\|crc\|secure\|prefer-crc\|prefer-secure` | kernel-client wire protocol: msgr1, or msgr2 checksummed / AES-GCM, or a preference. librados has no direct equivalent — `ms_client_mode` is an ordered preference list over `crc` and `secure` only, and cannot ask for `legacy` |
| `read_from_replica=no\|balance\|localize` | serve reads from a non-primary member of the acting set (`no` is the default) |
| `crush_location=rack:myrack\|datacenter:mydc` | tells the client where *it* sits, so `localize` can pick a near replica |
| `osd_request_timeout=`, `mount_timeout=`, `osdkeepalive=` | how long to wait on an unresponsive OSD, and session keepalive |
| `queue_depth=`, `alloc_size=` | krbd request concurrency and allocation granularity |
| `rxbounce` | receive into a bounce buffer, for servers that modify pages under I/O |
| `abort_on_full` | fail writes instead of blocking when the cluster is full |

`read_from_replica` is the interesting one, because it is the only
escape hatch from "all I/O goes to the primary". `balance` picks a
random member of the acting set; `localize` picks the nearest by
`crush_location`, where the lowest-valued matching bucket type wins —
so a matching rack beats a matching data center. Mind the location
syntax: `type:name` pairs joined by `|`, matched *independently*. It is
a set of nodes, not a path down the hierarchy.

The enforcement is in `PrimaryLogPG::do_op`, and it is stricter than
"reads may go anywhere". A non-primary accepts the op only if all
three hold: the message actually **carries** the balance or localize
flag, so a plain read sent to a replica is still misdirected; the op is
a read and neither `may_write()` nor `may_cache()`; and this OSD is in
the acting set at all, primary or not, so a stray shard is refused too.
Everything else falls into the branch the source labels "normal case;
must be primary". Writes always go to the primary, because the primary
is what *orders* them.

**The server side of the same op.** Every OSD retains a small ring of
recently completed operations with a timestamp per processing stage,
readable through its admin socket. Like
`--debug-ms`, this is **introspection, not interface** — but the line
wants drawing precisely, because op tracking is neither free nor off.
`osd_enable_op_tracker` defaults to `true`, every client op is born as
a `TrackedOp`, and each stage below costs a lock and a timestamp. What
makes it introspection is that nothing *reads* the record to make a
decision: no client consults it, no peering or replication logic
depends on it, and turning the option off leaves the cluster serving
I/O exactly as before. It is write-only bookkeeping — which is also
where the OSD's `slow request` warnings and the `SLOW_OPS` health check
come from, those being the one thing that does read it.

What it records is the real request osd.9 served, and the real times it
reached each stage. The output is JSON; this is one op from the `ops`
array, with the client-info block dropped and the event list kept whole:

```
[c24]# ceph daemon osd.9 dump_historic_ops
{
    "description": "osd_op(client.25226.0:8331 14.c
                    14:35e6b9b9:::rbd_data.626e2b7e024e.0000000000000000:head
                    [write 131072~1048576] snapc 0=[]
                    ondisk+write+known_if_redirected e198)",
    "initiated_at": "2026-07-28T23:41:33.065201+0000",
    "duration": 0.034185965,
    "type_data": {
        "flag_point": "commit sent; apply or cleanup",
        "events": [
   { "event": "initiated",                    "duration": 0        },
   { "event": "header_read",                  "duration": 0        },
   { "event": "throttled",                    "duration": 0.000005 },   (1)
   { "event": "all_read",                     "duration": 0.004022 },
   { "event": "dispatched",                   "duration": 0.000010 },
   { "event": "queued_for_pg",                "duration": 0.000024 },
   { "event": "reached_pg",                   "duration": 0.000194 },
   { "event": "started",                      "duration": 0.000092 },
   { "event": "waiting for subops from 2,13", "duration": 0.000127 },   (2)
   { "event": "op_commit",                    "duration": 0.020310 },   (3)
   { "event": "sub_op_commit_rec",            "duration": 0.005190 },   (4)
   { "event": "sub_op_commit_rec",            "duration": 0.004174 },
   { "event": "commit_sent",                  "duration": 0.000017 },   (5)
   { "event": "done",                         "duration": 0.000020 }

```

The trace earlier was a read; this is a **write**, caught mid-`dd`
against the mapped image of Section 5.1. Same message shape, same
fields — only the op vector and flags differ. Each `duration` is the
gap from the *previous* event, which makes the shape of the operation
readable at a glance.

1. Read off the wire and admitted by the throttler, which bounds how
   much unprocessed client data the messenger will buffer.
2. **Here is the replication.** osd.9 does not answer the client yet;
   it forwards the operation to osd.2 and osd.13 and waits.
3. Its own BlueStore transaction commits — 20.3 ms, and by far the
   largest single interval in the op.
4. The two replicas report their commits, 5.2 ms and 4.2 ms later;
   34.1 ms into the op, every copy is durable.
5. **17 microseconds after that**, the client is answered. There is no
   dead time between the last replica and the reply: the primary is
   waiting on exactly one thing, and it responds the moment that thing
   arrives. Total 34.2 ms, essentially all of it disk.

That sequence is the proof of a claim Section 6.1 only asserts: a write
is acknowledged once **every** copy is durable, not once the primary
is. Worth being exact about "every", because the answer is not "the
acting set" and it is definitely not `min_size`:

```
  op.waiting_for_commit.insert(
    parent->get_acting_recovery_backfill_shards().begin(),
    parent->get_acting_recovery_backfill_shards().end());
```

`ReplicatedBackend::submit_transaction` builds the wait list from the
**acting-recovery-backfill** set — the acting set *plus* any OSD
currently being recovered or backfilled onto. A shard that is midway
through receiving an old copy of this PG must also receive new writes
to it, or it would finish backfill already stale. And `min_size` never
enters this calculation at all: it decides whether the PG serves I/O
in the first place (Section 6.3), not how many commits an ack waits
for.

So the slowest copy sets the latency — which is why a single sick disk
can drag a whole pool down, why `ceph osd perf` is worth watching, and
why a cluster feels slower while it is backfilling.

# 5. Hands-on: the three interfaces

## 5.1 Block: RBD

RBD presents a virtual disk striped, 4 MiB at a time, over RADOS
objects. Create a pool for it — on the HDD class, since block storage
is the bulk consumer here — then an image:

```
[c21]# ceph osd pool create rbd 32 32 replicated hdd-rule               (1)
pool 'rbd' created
[c21]# rbd pool init rbd                                                (2)
[c21]# rbd create rbd/vol0 --size 4G                                    (3)
[c21]# rbd info rbd/vol0
rbd image 'vol0':
	size 4 GiB in 1024 objects                                      (4)
	order 22 (4 MiB objects)
	snapshot_count: 0
	id: 626e2b7e024e
	block_name_prefix: rbd_data.626e2b7e024e                        (5)
	format: 2
	features: layering, exclusive-lock, object-map, fast-diff,
	          deep-flatten
	create_timestamp: Tue Jul 28 13:32:32 2026
```

1. 32 PGs, replicated, using the class-aware rule from Section 4.2.
   The pool inherits the cluster defaults `size 3` and `min_size 2`:
   three copies, and I/O continues while at least two are available.
2. Stamps the pool with the `rbd` application tag; Ceph refuses I/O to
   untagged pools to catch pool-name typos.
3. Creating a 4 GiB image is instant — RBD is thin-provisioned. Only a
   small header object exists now; data objects appear on first write.
4. 4 GiB / 4 MiB = 1024 *potential* data objects.
5. **Remember this prefix.** Every data object of this image is named
   `rbd_data.626e2b7e024e.<16-hex-digit object index>` — the handle
   the trace in Section 6 hangs on.

Map it through the kernel RBD driver and use it like any disk:

```
[c21]# rbd map rbd/vol0
/dev/rbd0
[c21]# mkfs.xfs -q /dev/rbd0
[c21]# mount /dev/rbd0 /mnt/vol0
[c21]# echo 'hello from rbd' > /mnt/vol0/hello.txt
[c21]# sync
```

`rbd map` talks to `drivers/block/rbd.c` in the running kernel, which
speaks the RADOS protocol directly (`net/ceph/`) — no userspace daemon
and no gateway in the I/O path. Because `c21` holds no OSDs, every one
of those writes crossed the network to three of the storage nodes
before `sync` returned.

The lazily created data objects are now visible:

```
[c21]# rados -p rbd ls | sort | head -6
rbd_data.626e2b7e024e.0000000000000000                                  (1)
rbd_data.626e2b7e024e.000000000000007f                                  (2)
rbd_data.626e2b7e024e.00000000000000ff
rbd_data.626e2b7e024e.000000000000017f
rbd_data.626e2b7e024e.00000000000001ff
rbd_data.626e2b7e024e.0000000000000200
[c21]# rados -p rbd ls | wc -l
16
```

1. Object index 0 covers image bytes 0–4 MiB: the XFS superblock, the
   first allocation group's metadata — and our file's data.
2. The scattered indexes (`0x7f` = image bytes 508–512 MiB, etc.) are
   XFS metadata that mkfs placed near its allocation-group boundaries.
   Sixteen objects exist out of a possible 1024; everything mkfs and
   the file write did not touch **simply does not exist** — thin
   provisioning at the object level.

Which object holds `hello.txt`? Ask XFS where the file's data landed
in the image:

```
[c21]# xfs_bmap -v /mnt/vol0/hello.txt
/mnt/vol0/hello.txt:
 EXT: FILE-OFFSET  BLOCK-RANGE  AG AG-OFFSET  TOTAL FLAGS
   0: [0..7]:      104..111      0 (104..111)     8 001111
```

Sector 104 × 512 = byte offset 53248 — inside the first 4 MiB, so the
file's bytes live in object `rbd_data.626e2b7e024e.0000000000000000`:

```
[c21]# rados -p rbd stat rbd_data.626e2b7e024e.0000000000000000
rbd/rbd_data.626e2b7e024e.0000000000000000
    mtime 2026-07-28T13:33:00.000000+0000, size 131072                  (1)
```

1. The object's logical size is 128 KiB, not 4 MiB: XFS has only
   written the first 128 KiB of this 4 MiB stripe so far. Thin at the
   image level, thin inside each object too.

## 5.2 File: CephFS

CephFS needs two pools — data and metadata — and an MDS serving the
metadata. This is where device classes earn their keep: metadata is
small, latency-critical and heavily updated, so it goes on the fast
class, while file data goes on the slow one.

```
[c21]# ceph osd pool create cephfs.fs1.meta 16 16 replicated ssd-rule
pool 'cephfs.fs1.meta' created
[c21]# ceph osd pool create cephfs.fs1.data 32 32 replicated hdd-rule
pool 'cephfs.fs1.data' created
[c21]# ceph fs new fs1 cephfs.fs1.meta cephfs.fs1.data
new fs with metadata pool 15 and data pool 16
[c21]# ceph fs status fs1
fs1 - 0 clients
===
RANK  STATE   MDS     ACTIVITY     DNS    INOS   DIRS   CAPS
 0    active  c21  Reqs:    0 /s    10     13     12      0             (1)
      POOL         TYPE     USED  AVAIL
cephfs.fs1.meta  metadata   125k  7715M                                 (2)
cephfs.fs1.data    data       0   22.1G
STANDBY MDS
    c25                                                                 (3)
```

1. `ceph fs new` promoted one of the two standbys from Section 3.7 to
   serve rank 0. Nothing was started here.
2. The proof that the class rules took effect: the metadata pool sees
   **7.7 GiB** available and the data pool **22 GiB**, because they are
   drawing from four SSD-class devices and twelve HDD-class devices
   respectively. Same cluster, same hosts, different media.
3. The other MDS stands by. Ceph's MDS is active/standby per rank:
   only one daemon owns rank 0 at a time.

Mount it with the kernel client (`fs/ceph/`). The device string names
the user, the cluster fsid and the filesystem; the options carry the
monitor addresses and the secret:

```
[c21]# mount -t ceph \
    admin@8830b0e0-0d9f-4729-b01d-73c5dcda498e.fs1=/ /mnt/fs1 \
    -o mon_addr=10.0.0.21:3300/10.0.0.22:3300,secret=<admin key>,ms_mode=prefer-crc
[c21]# echo 'hello from cephfs' > /mnt/fs1/hello.txt
[c21]# sync
```

Both monitor addresses are listed, so the mount survives one of them
being unreachable at mount time. (`mount.ceph` can also pull all of
this from `/etc/ceph/` instead of the command line.)

The division of labor: the kernel client asks the **MDS** for metadata
operations — lookup, create, permissions, capability leases — but file
*data* goes directly to OSDs, striped into 4 MiB objects named
`<inode number in hex>.<stripe index>`:

```
[c21]# ls -i /mnt/fs1/hello.txt
1099511627776 /mnt/fs1/hello.txt                                        (1)
[c21]# rados -p cephfs.fs1.data ls
10000000000.00000000                                                    (2)
[c21]# ceph osd map cephfs.fs1.data 10000000000.00000000
osdmap e186 pool 'cephfs.fs1.data' (16) object '10000000000.00000000'
  -> pg 16.f0b56f30 (16.10) -> up ([9,6,1], p9) acting ([9,6,1], p9)    (3)
```

1. `1099511627776` = `0x10000000000` — CephFS inode numbers for user
   files start there.
2. The file's first (and only) stripe object: inode in hex, dot,
   stripe index.
3. Placed by exactly the same machinery as the RBD object — hosts
   `c24`, `c23`, `c22`. The tracing recipe of Section 6 applies
   verbatim.

Since there is a standby, it is worth making it work. `ceph mds fail`
evicts the active daemon the way a crashed host would:

```
[c21]# ceph mds fail c21
failed mds gid 24922
[c21]# ceph fs status fs1
fs1 - 1 clients
===
RANK  STATE   MDS     ACTIVITY     DNS    INOS   DIRS   CAPS
 0    active  c25  Reqs:    0 /s    11     14     12      1             (1)
      POOL         TYPE     USED  AVAIL
cephfs.fs1.meta  metadata   178k  7714M
cephfs.fs1.data    data    12.0k  22.1G
STANDBY MDS
    c21                                                                 (2)
[c21]# cat /mnt/fs1/hello.txt
hello from cephfs                                                       (3)
```

1. The standby on `c25` took over rank 0 within seconds.
2. The restarted daemon on `c21` re-registered as the new standby.
3. **The mount never broke.** The kernel client reconnected to the new
   MDS and replayed its outstanding state. This works for the reason
   Section 3.7 gave: an MDS holds no durable state of its own. The
   directory tree and inodes live in `cephfs.fs1.meta`, a normal RADOS
   pool, and the daemon is a cache and a lock manager over it. Failover
   is another daemon taking the lock and replaying the journal.

## 5.3 Object: RGW (S3)

RGW is an HTTP daemon translating the S3 (and Swift) protocol into
RADOS operations. Give it a cephx identity, tell the config store which
port to listen on, and start it:

```
[c21]# install -d -o ceph -g ceph /var/lib/ceph/radosgw/ceph-rgw.c21
[c21]# ceph auth get-or-create client.rgw.c21 mon 'allow rw' osd 'allow rwx' \
           -o /var/lib/ceph/radosgw/ceph-rgw.c21/keyring                (1)
[c21]# chown ceph:ceph /var/lib/ceph/radosgw/ceph-rgw.c21/keyring       (2)
[c21]# chmod 600 /var/lib/ceph/radosgw/ceph-rgw.c21/keyring
[c21]# ceph config set client.rgw.c21 rgw_frontends "beast port=8000"   (3)
[c21]# systemctl enable --now ceph-radosgw@rgw.c21
[c21]# radosgw-admin user create --uid=ming --display-name="Ming Lei"
{
    "user_id": "ming",
    "display_name": "Ming Lei",
    ...
    "keys": [
        {

# 6. Under the hood: from user file to raw disk bytes

Now the deep dive. We take `/mnt/vol0/hello.txt` from Section 5.1 and
follow its bytes all the way down, across the network, onto a named
machine's disk. The chain:

```
file → XFS → /dev/rbd0 byte 53248 → object rbd_data.…0000 →
PG 14.c → osd.9 (host c24) → BlueStore → device offset 151330816
```

## 6.1 Step 1: object name → PG → OSDs

`ceph osd map` answers "where does this object live?" — and it answers
*without contacting any OSD*, because placement is computed, not
looked up:

```
[c21]# ceph osd map rbd rbd_data.626e2b7e024e.0000000000000000
osdmap e186 pool 'rbd' (14)
  object 'rbd_data.626e2b7e024e.0000000000000000'
  -> pg 14.9d9d67ac (14.c)                                              (1)
  -> up ([9,13,2], p9) acting ([9,13,2], p9)                            (2)
```

1. The object *name* hashes to `0x9d9d67ac`. The pool has 32 PGs, so
   the hash is masked to 5 bits: `0x9d9d67ac & 0x1f = 0x0c` — PG `14.c`
   ("pool 14, PG 0x0c"). Every object hashing into this bucket shares
   the PG's placement and fate. (Pool ids here start at 14 because
   earlier experiments created and destroyed pools; ids are never
   reused.)
2. CRUSH maps PG `14.c` onto OSDs `[9, 13, 2]` — three replicas per the
   pool's `size 3`. `p9` marks **osd.9 as the primary**: all client I/O
   for this PG goes to osd.9, which replicates to 13 and 2 and acks
   only after all three have the write persisted. `up` equal to
   `acting` means nothing is recovering.

**There is no such thing as a "replica OSD".** This trips up almost
everyone coming from RAID or from primary/secondary databases, so it is
worth killing early: primary is a property of the *pair* (PG, OSD), not
of the OSD. It is simply position 0 in that PG's acting set — and every
OSD is position 0 for some PGs and position 1 or 2 for others:

```
[c21]# ceph pg dump pgs_brief --format=json | python3 -c '
import json,sys,collections
pgs = json.load(sys.stdin)["pg_stats"]
prim, rep = collections.Counter(), collections.Counter()
for p in pgs:
    prim[p["acting"][0]] += 1
    for o in p["acting"][1:]: rep[o] += 1
for o in sorted(prim | rep):
    print(f"osd.{o:<3} primary for {prim[o]:3}   replica for {rep[o]:3}")'
osd.0   primary for   7   replica for  11
osd.1   primary for   9   replica for  13
osd.2   primary for   6   replica for  13                               (1)
...
osd.9   primary for   8   replica for  14                               (2)
...
osd.13  primary for   7   replica for  11                               (3)
```

1. `osd.2` was a plain replica for PG 14.c above — and is primary for
   six other PGs.
2. `osd.9` leads 8 PGs and follows in 14.
3. Likewise `osd.13`, which Section 6.3 will watch *become* primary for
   14.c the instant osd.9 goes down — no reconfiguration, just the
   acting set losing its head and the next entry inheriting the role.

Not one of the sixteen OSDs is exclusively primary or exclusively
replica. That is deliberate: the primary serves every read and orders
every write for its PG, so if primaries clustered on a few OSDs those
disks would carry the whole cluster's load. Spreading PGs spreads the
primary role with them, which is what makes a Ceph cluster scale by
adding disks. (`ceph osd primary-affinity` can bias this, and the
`read_balance_score` in `ceph osd pool ls detail` reports how evenly it
worked out.)

The payoff of a multi-node cluster is in asking *where those OSDs are*:

```
[c21]# for i in 9 13 2; do ceph osd find $i \
         | python3 -c 'import json,sys; d=json.load(sys.stdin); print("osd.%s  %s" % (d["osd"], d["host"]))'; done
osd.9   c24
osd.13  c25
osd.2   c22
```

Three copies on three distinct machines — not because anything told
CRUSH to do that for this object, but because `hdd-rule` says
`chooseleaf ... type host` and the CRUSH tree built in Section 3.6
groups OSDs under hosts. Lose `c24` entirely and this PG keeps serving
from `c25` and `c22`.

Placement is a pure function of (PG, CRUSH map, rule) — ask again at a
later epoch and the answer is identical. Any client holding the current
map computes the same result. When the map changes, the function's
output changes, and exactly the affected PGs migrate. The
implementation lives in [`src/crush/`][src-crush].

## 6.3 Step 3: open the primary OSD's BlueStore offline

`ceph-objectstore-tool` opens a **stopped** OSD's BlueStore and lets
you list, dump and extract objects. That means stopping `osd.9` — on
`c24`, the machine CRUSH named — which is safe here: two other replicas
remain, one takes over as primary, and `min_size 2` is still satisfied.

First, tell the cluster not to start rebalancing during the exercise:

```
[c21]# ceph osd set noout                                               (1)
noout is set
[c24]# systemctl stop ceph-osd@9
```

1. Without `noout`, the monitor marks a down OSD *out* after
   `mon_osd_down_out_interval` (600 s by default) and CRUSH immediately
   re-places every PG that lived on it — the cluster would start
   copying data to restore the third replica. `noout` is the standard
   flag for planned maintenance: the OSD stays *in* the map, so nothing
   moves.

The cluster notices within seconds:

```

## 6.4 Step 4: extract the raw bytes and compare

```
[c24]# ceph-objectstore-tool --data-path /var/lib/ceph/osd/ceph-9 "$obj" \
         get-bytes /tmp/obj.bin
[c24]# ls -l /tmp/obj.bin
-rw-r--r-- 1 root root 131072 Jul 28 13:53 /tmp/obj.bin
[c24]# md5sum /tmp/obj.bin
acb5bbe17431b33f510aa1f37afa184e  /tmp/obj.bin                          (1)
```

1. **Identical to the hash taken through `/dev/rbd0` in step 2.** The
   bytes XFS wrote on `c21` are byte-for-byte what BlueStore stored on
   `c24`'s disk: page cache → krbd → network → RADOS write to PG 14.c's
   primary → BlueStore transaction on osd.9, replicated to osd.13 and
   osd.2 → acked.

The onode's extent map shows where on the device those bytes actually
sit:

1. The 128 KiB object is stored as two 64 KiB blobs at raw device

2. `csum_type: 4` is crc32c and `csum_chunk_order: 12` means one

   filesystem-based object store would silently pass upward.

   without the final inversion — BlueStore's convention. Those are the
   parts of the 128 KiB range XFS never wrote into.

   machinery are covered in
   [Ceph BlueStore Explained][bluestore-post].

# 7. Under the hood: authentication, from Kerberos to cephx

Section 3.2 used cephx and stated the rules; this section explains
where those rules come from.

## 7.1 Why a storage cluster needs its own auth

Every daemon in this post listens on plain TCP and speaks the RADOS
protocol; clients connect straight to OSDs on four different machines.
Without authentication, anyone who can reach `10.0.0.0/24` could claim
to be `client.admin`, enroll a rogue OSD (and have the cluster
helpfully *replicate data to it*), or replay captured writes. So the
requirements are:

- **Mutual authentication** — daemons verify clients *and* each other;
  a rogue OSD must be rejected just like a rogue client.
- **Authorization** — different principals get different rights (the
  cap strings and profiles of Sections 3.2 and 4.3).
- **No authority on the data path** — Section 6.1 showed placement is
  computed client-side precisely to avoid a central lookup server; auth
  must not sneak one back in as a per-I/O "may I?" service.
- **Secrets never cross the wire** — the network is untrusted.

This is an old problem shape: many clients, many services, one trusted
authority, hostile network. MIT solved it in the 1980s.

## 7.2 The Kerberos idea in one diagram

[Kerberos][kerberos] assumes a Key Distribution Center (KDC) that
shares a secret with every principal. Nobody ever sends a secret over
the wire — not even hashed. Instead, the KDC answers a *plaintext*
request with **two sealed boxes carrying the same freshly-minted
session key**, one openable by the client, one by the service:

```
 +--------+ (1) "alice here: a ticket    +----------+
 |        |      for service S, please"  |   KDC    |
 |        | ---------------------------> | all keys |
 | client | (2) reply: two sealed boxes  +----------+
 |        | <---------------------------
 |        |  [session key]                sealed with ALICE's key
 |        |      -> only she can open it: that IS the login
 |        |  [alice, session key, expiry] sealed with S's key
 |        |      -> the TICKET: opaque to her, forwarded as-is
 |        |
 |        | (3) ticket + authenticator   +----------+
 |        |     (encrypted w/ session k) | service  |
 |        | ---------------------------> |    S     |
 |        | (4) S unseals ticket locally +----------+
 |        | <==========================>
 +--------+   both now hold the same session key
```

This is how the client gets the session key: box one is sealed with the
*client's own* secret, so decrypting it is simultaneously the delivery
of the key and the proof of identity — an impostor without alice's
secret holds two boxes it cannot open. Box two, the **ticket**, carries
the same session key to the service by a route the client cannot read
or tamper with. In step (3) the client adds a small *authenticator*
(e.g. a timestamp) encrypted with the session key, proving it really
opened box one; the service unseals the ticket with its own key, finds
the same session key inside, and checks the authenticator and expiry —
all **without asking the KDC**. Authenticate once, then talk to many
services directly until expiry forces a background renewal.

## 7.3 cephx: Kerberos re-cast for a storage cluster

cephx keeps the architecture and changes the casting:

| Kerberos | cephx |
|----------|-------|
| KDC | the MON quorum (auth database in the MON's `store.db`) |
| principal + password | principal + keyring file |
| ticket | ticket carrying identity + **caps** + session key |
| service's secret key | *rotating* secret shared by each daemon class |
| authorization data | the cap strings and profiles of Sections 3.2, 4.3 |

```
 client                MON (key authority)              OSDs
   |  (1) handshake: prove  |                             |
   |      client.admin key  |                             |
   | ---------------------> |                             |
   |  (2) tickets + session |                             |
   | <--------------------- |                             |
   |     (sealed with the rotating service secret)        |
   |                        |                             |
   |  (3) I/O request + ticket -------------------------> |
   |      OSD unseals locally: identity, caps, skey       |
   | <=================================================== |
   |      signed traffic — no MON on the data path        |
```

Ceph-specific adaptations worth knowing:

- **Keyrings, not passwords** — a principal's key is a file
  (Section 3.2's `ceph-authtool` output, Section 4.3's tour of where
  they live); daemons authenticate to the MON exactly like clients,
  with keys minted at enrollment time.
- **Rotating service secrets** — cephx's counterpart of the Kerberos
  service key, but minted *per daemon class*: one secret for the OSDs,
  one for the MDSes, one for the MGRs.
  - *Class-wide* is forced by RADOS itself — a client cannot know which
    of the sixteen OSDs it will end up talking to as maps change, so
    the ticket it carries must be unsealable by **any** OSD.
  - *Rotating*, precisely because the key is so widely shared: it turns
    over on the ticket TTL (`auth_service_ticket_ttl`, default one
    hour), daemons holding a small overlapping set (previous / current
    / next) so a rotation or mild clock skew never invalidates a fresh
    ticket.
  - This is *not* the key in a daemon's keyring file — that one is its
    permanent login credential (how `osd.9` authenticates to the MON,
    like any client).
  - The rotating secrets live in exactly two places: authoritatively in
    the MON's auth database (inside the `store.db` of Section 4.4,
    Paxos-committed like every map), and as an in-memory ring on each
    daemon, fetched after login, refreshed before expiry, never written
    to the daemon's disk — so a stolen OSD keyring leaks one login, not
    a durable ticket-unsealing key.
  - Revocation is passive: a deleted principal simply fails its next
    renewal, and no OSD ever needs to be told.
- **Caps ride in the ticket** — authorization is enforced by each
  daemon from the unsealed ticket, no directory consulted per op.
- **Integrity, not secrecy** — cephx authenticates the parties; it does
  not encrypt payloads. Per-message protection is a separate job, done
  by the messenger in `crc` or `secure` mode, and Section 4.6 shows
  both on the wire: by default only traffic to a monitor is encrypted.
  So the tickets described here are handed out over AES-GCM, while the
  I/O they authorize is checksummed and readable.

One knob from Section 4.2's `ceph config dump` belongs here:

```
mon  advanced  auth_allow_insecure_global_id_reclaim  false
```

Every cephx session has a *global id*, and older clients could reclaim
one after reconnecting without re-proving they owned it — letting an
attacker who observed a session id impersonate it. Ceph defaults to
allowing the old behaviour (and warning loudly about it) so ancient
clients keep working; turning it off is a one-line hardening step once
you know every client is recent enough.

Seen from here, Section 3's bootstrap ritual is just KDC seeding:
`mon.` is the KDC's own identity, `client.admin` is the first enrolled
principal, `client.bootstrap-osd` is a deliberately narrow enrollment
credential — and every one of the twenty-odd principals in Section
4.3's listing joined afterwards through the front door.

# 8. Next steps for aspiring Ceph developers

## 8.1 From packages to developer builds

This post ran release binaries; for development you want to run code
you just built. The standard loop:

```
git clone https://github.com/ceph/ceph.git && cd ceph
./install-deps.sh                  # dnf-installs build deps on Fedora
./do_cmake.sh -DCMAKE_BUILD_TYPE=RelWithDebInfo
cd build && ninja                  # long; -j to taste
```

Then [`vstart.sh`][vstart] launches a throwaway cluster **from the
build tree** — conceptually exactly what Section 3 did by hand (it
generates a conf, mints the keys, starts the daemons as plain
processes), just automated onto one machine:

```
cd build
MON=1 OSD=3 MDS=1 RGW=1 ../src/vstart.sh -d -n -x
./bin/ceph -s        # note: ./bin/ceph, the freshly built CLI
```

`-n` creates a new cluster, `-d` enables debug output, and the env vars
pick the daemon counts — all of which default to sensible numbers
except `RGW`, which defaults to **0**, so a gateway only appears if you
ask for one. Edit code, `ninja`, restart — a minutes-long iteration
loop. Its sibling `cstart.sh` does the same with containers,
and `mstart.sh` runs several clusters side by side. The
[developer guide][doc-dev] documents the workflow. (For production the
tool is [cephadm][doc-cephadm] — same daemons, run as podman containers
under systemd.)

One node is enough for most code work, but not for everything above:
with all OSDs on one host the CRUSH failure domain must be lowered to
`osd`, which quietly removes the property Section 6.1 demonstrated.
Anything touching peering, recovery, backfill or CRUSH deserves real
hosts — a handful of VMs like this lab, or Ceph's `teuthology`
integration-test framework at scale.

## 8.2 Where to start reading code

Read upstream's [`doc/architecture.rst`][doc-arch] alongside the tree —
it is this same territory in prose, and it covers the RADOS behaviour
this lab did not exercise: erasure coding, scrubbing, striping
parameters, watch/notify, and RADOS classes.

Guided by the trace in Section 6, each hop has a home in the tree
(refs against [`v20.2.2`][ceph-tag]):

- [`src/crush/`][src-crush] — the placement function; small,
  self-contained, and the best first read. `mapper.c` is where
  `chooseleaf_firstn` actually walks the tree of Section 4.2.
- [`src/osd/`][src-osd] — the OSD: PG state machine, replication,
  recovery. Start at `PrimaryLogPG.cc` for the write path a client op
  takes on a primary (the `version 186'31` in Section 6.3 is its PG log
  at work), and `PeeringState.cc` for how `[9,13,2]` shrank to `[13,2]`
  and grew back.
- [`src/os/bluestore/`][src-bluestore] — the storage engine of
  Section 6.4: onodes, extent maps, blobs and the checksum arrays
  ([companion post][bluestore-post]).
- [`src/librbd/`][src-librbd] — the userspace RBD client (QEMU uses
  this); its kernel twin is [`drivers/block/rbd.c`][krbd].
- [`src/mds/`][src-mds] — the CephFS metadata server, including the
  journal replay that made Section 5.2's failover invisible; kernel
  client in [`fs/ceph/`][kcephfs].
- [`src/rgw/`][src-rgw] — the S3/Swift gateway.
- [`src/auth/`][src-auth] — the cephx protocol from Section 7: the
  MON-side `KeyServer` (mints principals and rotating secrets), the
  daemon-side `RotatingKeyRing`, tickets and the handshake.

And if kernel storage is your angle, the client side is a first-class
entry point: `net/ceph/` (the messenger), `drivers/block/rbd.c` and
`fs/ceph/` were all exercised by this lab from an ordinary distro
kernel — and all three are equally patchable and testable against any
cluster you can reach, including a one-node `vstart.sh`.
