# 1. Introduction and core terminology

Ceph is a distributed storage system that exposes three user-facing
interfaces — block, file and object — all built on a single internal
object store called **RADOS**. This post walks a complete loop for
newcomers: stand up a real (single-VM) cluster daemon by daemon, use
all three interfaces, then trace one written object down through
placement and onto the raw disk, verifying every hop with checksums.
The target reader is an engineer who wants to *use* Ceph now and *hack
on* Ceph later.

The vocabulary you need before anything else:

| Term | Meaning |
|------|---------|
| cluster | one Ceph deployment: the MONs, MGRs, OSDs, ... acting as one |
| fsid | the cluster's UUID — stamped into maps, stores, device labels |
| RADOS | Reliable Autonomic Distributed Object Store — the core cluster |
| object | RADOS's unit: name + bytes + xattrs + omap (key/value pairs) |
| OSD | Object Storage Daemon — one per disk; stores objects (BlueStore) |
| BlueStore | the OSD's storage engine: raw device, no filesystem below |
| BlueFS | BlueStore's tiny internal FS, only to host its own RocksDB |
| MON | Monitor — keeps the authoritative cluster maps, forms quorum |
| monmap | the map of the MONs themselves: who they are, where they listen |
| osdmap | the map of OSDs (which exist, up/in state) — versioned by epoch |
| MGR | Manager — metrics, orchestration modules, balancer, dashboard |
| Pool | a namespace of objects with a replication/EC policy |
| PG | Placement Group — a shard of a pool; unit of replication/recovery |
| active+clean | PG state: serving I/O, every replica current — the goal |
| peering | PG state: replicas reconciling history before serving I/O |
| degraded | PG state: serving I/O with fewer copies than `size` |
| remapped | PG state: temporarily on other OSDs than CRUSH's answer |
| CRUSH | the placement function: PG → list of OSDs, computed, not looked up |
| cephx | shared-secret auth: the MON stores all keys and issues tickets |
| principal | a named identity in cephx: `mon.`, `client.admin`, `osd.0` |
| key | a principal's secret — in a keyring file and the MON's database |
| caps | a principal's rights, per daemon type: `osd 'allow rwx'`, ... |
| ticket | Kerberos-style token: identity + caps + session key (Sec 6) |
| authenticator | timestamp sealed with the session key, proving key receipt |
| RBD | RADOS Block Device — virtual disks striped over RADOS objects |
| CephFS | POSIX filesystem on RADOS; an MDS daemon serves the metadata |
| RGW | RADOS Gateway — S3/Swift-compatible HTTP object storage |
| cephadm | production deployment tool — daemons as podman containers |

The key architectural idea: **clients compute data locations instead of
asking a central server**. An object name is hashed to a PG, and CRUSH
maps the PG to a set of OSDs using only the compact cluster map that
MONs distribute. There is no lookup table in the data path, which is
what lets Ceph scale out without a metadata bottleneck (CephFS being
the exception: POSIX semantics need a real metadata server, the MDS —
but file *data* still goes straight from client to OSDs).

```
   +-----------+    +------------+    +---------------------+
   |    RBD    |    |   CephFS   |    |    RGW  (S3 API)    |
   |  (block)  |    |   (file)   |    |      (object)       |
   +-----+-----+    +-----+------+    +----------+----------+
         |                |      \               |
   krbd or librbd   kernel client \_ MDS      radosgw daemon
         |          or libcephfs  (metadata)     |
   +-----v----------------v-----------------------v---------+
   |              librados  /  RADOS protocol               |
   +----------------------------+---------------------------+
                                |
                object name --hash--> PG --CRUSH--> OSDs
                                |
        +---------------+------+--------+----------------+
        |               |               |                |
   +----v----+     +----v----+     +----v----+      +----v----+
   |  OSD.0  |     |  OSD.1  |     |  OSD.2  |      | MON,MGR |
   |BlueStore|     |BlueStore|     |BlueStore|      | (maps,  |
   | raw disk|     | raw disk|     | raw disk|      |  quorum)|
   +---------+     +---------+     +---------+      +---------+
```

Every interface at the top decomposes user data into RADOS objects
(typically 4 MiB) at the bottom. That single fact is what Section 5
exploits to trace a file's bytes to a physical disk offset.

# 2. The lab: one Fedora VM, three loop disks

## 2.1 The test environment

Everything below runs inside one disposable VM booted by a small
harness:

```
vmtest -c vmtest.conf run shell
```

[`vmtest`][vmtest] is a light bash wrapper around [virtme-ng][vng]: it
boots the kernel built in the `KERNEL_DIR` your `vmtest.conf` points
at (here a `7.2.0-rc3` tree), exposes the host filesystem read-only
over 9p, and drops you into a root shell with guest-local tmpfs for
scratch space. Two properties make it a good fit:

- **Reproducible** — the whole cluster lives in guest-local memory; a
  fresh boot is a fresh lab. The [lab script][lab-script] replays
  everything in this post unattended in about 90 seconds of guest time.
- **Your kernel** — the RBD and CephFS *clients* used in Section 4 are
  kernel code (`drivers/block/rbd.c`, `fs/ceph/`). Booting a self-built
  kernel means you can instrument and test the kernel side of Ceph
  against a real local cluster (the kernel needs `CONFIG_BLK_DEV_RBD`
  and `CONFIG_CEPH_FS`).

The "disks" are three 4 GiB **loop devices** created inside the VM —
Ceph does not care whether an OSD's block device is a real disk, an
LVM volume, or a loop device over a sparse file:

```
# truncate -s 4G /tmp/ceph/disk0.img
# losetup /dev/loop0 /tmp/ceph/disk0.img      # likewise loop1, loop2
```

A note on **cephadm**: on a normal host the documented path is
`cephadm bootstrap --single-host-defaults`, which runs every daemon as
a podman container under systemd ([docs][doc-cephadm]). Our throwaway
virtme guest has no systemd as PID 1, so this post starts every daemon
**by hand as a plain process** instead — which is not a workaround to
apologize for: it is exactly what Ceph's own developer script
`vstart.sh` does, and you end up knowing what a "cluster" actually is:
a handful of cooperating processes and one config file.

# 3. Bootstrapping the cluster by hand

## 3.1 The config file

Everything lives under `/tmp/ceph` in the guest. The whole cluster is
described by this `ceph.conf`:

```
[global]
        fsid = 8afd54fd-8414-4306-82f4-c04865594638
        mon host = [v2:127.0.0.1:3300,v1:127.0.0.1:6789]
        auth cluster required = cephx
        auth service required = cephx
        auth client required = cephx
        keyring = /tmp/ceph/keyring
        run dir = /tmp/ceph/run
        pid file = /tmp/ceph/run/$name.pid
        admin socket = /tmp/ceph/run/$name.asok
        log file = /tmp/ceph/log/$name.log
        osd pool default size = 2                          (1)
        osd pool default min size = 1
        osd crush chooseleaf type = 0                      (2)

[mon]
        mon data = /tmp/ceph/mon

[osd]
        osd data = /tmp/ceph/osd$id
        keyring = /tmp/ceph/osd$id/keyring
        osd memory target = 1073741824                     (3)

[client.rgw.s3]
        rgw data = /tmp/ceph/rgw
        rgw frontends = beast port=8000
```

1. Two replicas per object — the same defaults cephadm's
   `--single-host-defaults` would pick.
2. The crucial single-node setting: CRUSH's failure domain is lowered
   from *host* (the default — replicas on different machines) to *OSD*,
   since all three OSDs share this VM.
3. OSDs default to a 4 GiB memory target each; cap them at 1 GiB so
   three fit comfortably in an 8 GiB VM.

(If you run the daemons from an extracted RPM tree instead of
dnf-installed packages — as the lab script can — also point
`plugin dir`, `osd class dir`, `erasure code dir` and
`mgr module path` at that tree; see the script.)

## 3.2 Two keys before the cluster exists

Identity next. cephx is Ceph's shared-secret authentication — named
principals, keys, and Kerberos-style tickets that let daemons verify
callers locally (Section 6 unpacks the machinery). What matters for
bootstrap is one fact: the **MON is the key authority**. Every later
command and every daemon will authenticate against it — but the tools
that normally create keys need a running, authenticated cluster
themselves. That circle is broken by minting exactly two keys
*offline*, as plain files, before any daemon starts.

**Key 1: `mon.` — the authority's own identity.**

```
# ceph-authtool --create-keyring /tmp/ceph/keyring \
      --gen-key -n mon. --cap mon 'allow *'
creating /tmp/ceph/keyring
```

The monitor is the daemon that will validate everyone else's keys —
but with `auth cluster required = cephx` it needs a key of its own
before it can even start (in a multi-MON cluster, this same shared
key is also how monitors trust each other in quorum). No running
cluster exists to mint it, so you generate it into a keyring file
yourself.

**Key 2: `client.admin` — your identity.**

```
# ceph-authtool /tmp/ceph/keyring --gen-key -n client.admin \
      --cap mon 'allow *' --cap osd 'allow *' \
      --cap mds 'allow *' --cap mgr 'allow *'
```

This is the principal *you* act as for the rest of the post: every
`ceph`, `rbd` and `rados` invocation, and both kernel mounts, read
this keyring and authenticate as `client.admin`. It too must exist
before the cluster does: the moment the MON is up with cephx
required, even `ceph auth get-or-create` — the command that creates
keys — demands an authenticated caller. Without a pre-seeded admin
key you would be locked out by the very auth you just enabled. The
four `allow *` caps make it the superuser across all daemon types.

And that is the complete list. Every other principal in this post —
`mgr.x`, `osd.0`–`osd.2`, `mds.a`, `client.rgw.s3` — is minted
*online* with `ceph auth get-or-create` or `ceph osd new`,
authenticated as `client.admin`; watch for those calls in the
sections that follow. Both offline keys are imported into the MON's
auth database in the next step — from then on the MON is the source
of truth, and the keyring file is just your client-side credential.

## 3.3 The MON: maps, quorum, key authority

The monitor's mkfs takes two inputs: the keyring from 3.2, and an
initial monitor map — built offline with `monmaptool`, carrying the
cluster fsid and the MON's addresses from the config file:

```
# monmaptool --create --fsid 8afd54fd-8414-4306-82f4-c04865594638 \
      --addv a '[v2:127.0.0.1:3300,v1:127.0.0.1:6789]' /tmp/ceph/monmap
monmaptool: monmap file /tmp/ceph/monmap
setting min_mon_release = tentacle
monmaptool: set fsid to 8afd54fd-8414-4306-82f4-c04865594638
monmaptool: writing epoch 0 to /tmp/ceph/monmap (1 monitors)
```

```
# ceph-mon --mkfs -i a --monmap /tmp/ceph/monmap \
      --keyring /tmp/ceph/keyring                          (1)
# ceph-mon -i a                                            (2)
```

1. mkfs builds the monitor's private store (`mon data`, here
   `/tmp/ceph/mon` — a small RocksDB) and seeds it with the monmap
   and the two offline keys. From this moment the MON's store — not
   the keyring file — is the cluster's source of truth for auth.
2. `-i a` picks the instance name, `mon.a`. Ceph daemons background
   themselves; `-d` would keep one in the foreground with debug
   output.

What the running MON actually does: it is the cluster's brain but
none of its muscle. It holds the authoritative, versioned cluster
maps — the monmap (where MONs are), the osdmap (which OSDs exist and
are up/in — `osdmap e39` in Section 5.1 is its epoch counter), the
CRUSH map, the MDS map, and the cephx key database — and distributes
them to every client and daemon, which *subscribe* to updates rather
than poll. Every `ceph` CLI call in this post is a conversation with
it. In production you run 3 or 5 MONs, and each map change is
committed by Paxos majority — our single `mon.a` is a quorum of one,
fine for a lab and a single point of failure anywhere else. What
never touches the MON: your data. It knows where everything *may* be
placed, and stores none of it.

## 3.4 The MGR: statistics, modules, balancer

```
# ceph auth get-or-create mgr.x mon 'allow profile mgr' \
      osd 'allow *' mds 'allow *' >> /tmp/ceph/keyring     (1)
# ceph-mgr -i x
# ceph balancer off                                        (2)
```

1. The first *online* key mint — the pattern promised in Section 3.2:
   an authenticated `client.admin` asks the MON to create `mgr.x`,
   and the printed keyring block is appended to our shared keyring
   file so the daemon can read its own key. `allow profile mgr` is a
   canned cap bundle — "what a manager legitimately needs" — instead
   of hand-written rules.
2. Lab-specific: the MGR's balancer actively *remaps* PGs to even out
   utilization. That is great in production and terrible for a tracing
   exercise — it can move your PG between the moment you compute its
   location and the moment you look inside an OSD (it did exactly that
   in an earlier run of this lab, turning the offline OSD's copy stale
   mid-trace).

Why a second brain? The MGR exists to keep the MON's Paxos path
lean: everything that is *reporting* rather than *authority* moved
there. OSDs stream their PG and performance statistics to the MGR,
so the `data:` section of `ceph -s`, `ceph df` and `ceph fs status`
are answered from it — with no active MGR the cluster still serves
I/O, but those numbers freeze and health complains. It also hosts
the Python modules: the pg autoscaler (which sized the differing
`PGS` counts you'll see in the final `ceph df`), the balancer we
just disabled, progress bars, the dashboard, the Prometheus
exporter, and the orchestrator API that cephadm plugs into (absent
in this hand-rolled lab — the reason Section 4.2 creates CephFS
pools manually instead of `ceph fs volume create`). Production runs
one active MGR plus standbys.

The cluster is now alive but empty — note `ceph -s` already works:

```

## 3.5 Three OSDs on loop devices

For each disk, four steps: register a new OSD id (+cephx key) with the
MON, point the OSD's data directory at the raw device, format it with
BlueStore, start the daemon. Shown for osd.0 / `/dev/loop0`:

```
# uuid=$(uuidgen)
# ceph-authtool --gen-print-key > secret
# printf '{"cephx_secret": "%s"}\n' "$(cat secret)" > secret.json
# ceph osd new $uuid -i secret.json                        (1)
0
# mkdir /tmp/ceph/osd0 && ceph auth get osd.0 -o /tmp/ceph/osd0/keyring
# ln -s /dev/loop0 /tmp/ceph/osd0/block                    (2)
# ceph-osd -i 0 --mkfs --osd-uuid $uuid                    (3)
bluestore(/tmp/ceph/osd0/block) No valid bdev label found
bluestore(/tmp/ceph/osd0) _read_fsid unparsable uuid
# ceph-osd -i 0
```

1. `ceph osd new` allocates the next free id (0) and registers the
   OSD's cephx key in one step.
2. This symlink **is** the storage configuration: BlueStore consumes
   the raw block device it points to. No filesystem is ever made on
   the loop device.
3. The two "errors" are expected first-format noise: mkfs probes for
   an existing BlueStore label, finds a blank device, and creates one.

After repeating for `/dev/loop1` and `/dev/loop2`:

```

  services:
    mon: 1 daemons, quorum a (age 34s) [leader: a]
    mgr: x(active, since 21s)
    osd: 3 osds: 3 up (since 4s), 3 in (since 8s)          (1)
  data:
    pools:   1 pools, 1 pgs                                (2)
    objects: 2 objects, 449 KiB
    usage:   80 MiB used, 12 GiB / 12 GiB avail
    pgs:     1 active+clean

# ceph osd tree
ID  CLASS  WEIGHT   TYPE NAME           STATUS  REWEIGHT  PRI-AFF
-1         0.01167  root default
-3         0.01167      host virtme-ng                     (3)
 0    ssd  0.00389          osd.0           up   1.00000  1.00000
 1    ssd  0.00389          osd.1           up   1.00000  1.00000
 2    ssd  0.00389          osd.2           up   1.00000  1.00000
```

1. `up` = daemon running; `in` = participating in data placement. An
   OSD can be up but out (draining), or down but in (briefly, before
   recovery kicks in).
2. The `.mgr` pool, auto-created for MGR module state. A pool is a set
   of PGs; `active+clean` means every PG has its full complement of
   replicas and nothing to recover.
3. The CRUSH topology tree: one root, one host, three OSDs — this is
   the map Section 5's placement math walks.

## 3.6 All the cluster's stores and files

Everything the cluster *is* now sits under one directory. A tour is
worth it: knowing which file does what turns "mysterious distributed
system" into "a directory you can read".

```
/tmp/ceph/
|-- ceph.conf        the shared config (3.1)        INI text
|-- keyring          client-side keys (3.2)         INI text
|-- monmap           MON bootstrap map (3.3)        binary, used once
|-- mon/             the MON's private store
|   `-- store.db/    maps + cephx db + Paxos        RocksDB
|-- osd0/ .. osd2/   one dir per OSD
|   |-- block -> /dev/loop0   THE data store        raw BlueStore dev
|   `-- keyring, whoami, ...  identity markers      tiny text files
|-- rgw/             RGW instance dir (empty here)
|-- run/             $name.asok, $name.pid          live plumbing
|-- log/             one log per daemon             text
`-- disk0..2.img     loop backing files (this lab's stand-in disks)
```

**`ceph.conf` — the phonebook.** Before authentication can even
start, every daemon and client must answer two questions: where are
the MONs, and where do *I* keep my files? That is all the config
file really does (Section 3.1) — plain INI text, `[global]`/
`[mon]`/`[osd]` sections, `$name`/`$id` expansion. Everything else
is learned from the MON after connecting, which is why the file is
small and rarely changes.

**`keyring` — identity as a file.** A keyring is Ceph's equivalent
of an SSH private key file: a principal's name plus the secret that
proves you *are* that name — whoever can read the file can **be**
that principal. In the cephx handshake the owner proves possession
of the secret (never sending it), the MON compares against its own
database, and the caller then speaks *as* that principal. The
format is INI text, one section per identity; ours has collected
every key appended during bootstrap:

```
# cat /tmp/ceph/keyring
[mon.]
        key = AQC7HWRqUjW1NRAAsup5gDDfVlkm7exuWWzWmQ==
        caps mon = "allow *"
[client.admin]
        key = AQC7HWRqQ0LpOBAAldOkmKKbUYGWFvvu/8Whcg==
        caps mds = "allow *"
        caps mgr = "allow *"
        caps mon = "allow *"
        caps osd = "allow *"
[mgr.x]
        key = AQC9HWRquFpECBAAQk9n165IutVFnUFT8sLVFw==
[mds.a]
        key = AQDfHWRqgLEhHRAA21psPiDzkRu04Gu5Ne6J/Q==
[client.rgw.s3]
        key = AQDnHWRqsaAIFxAAcIsg40Hmvoo6f/nHtwH7Yg==
```

Just as important is what a keyring is **not**. It is not
authorization: the `caps` lines are a cached, human-readable note,
and the MON's database alone decides what each principal may do.
It is not data or state: lose a daemon's keyring and its store is
intact — the daemon just cannot log in until an admin re-exports
the key (`ceph auth get osd.0`; the MON's copy is authoritative).
And it is deliberately not cluster-wide: one shared file is lab
convenience, while real deployments give each daemon a private
keyring holding *only its own* key, so a compromised OSD leaks "the
ability to be `osd.0`", never "the ability to be admin". Ours were
minted by `ceph osd new` with the canned OSD profile:

```
# cat /tmp/ceph/osd0/keyring
[osd.0]
        key = AQDFHWRqtFFVBRAAgxtsAZNLgX4xaMJo5KK0jg==
        caps mgr = "allow profile osd"
        caps mon = "allow profile osd"
        caps osd = "allow *"
```

**`monmap` — a one-shot bootstrap blob.** A small binary file
(epoch, fsid, monitor addresses — `monmaptool` printed those fields
as it wrote them in 3.3). Motivation: a monitor cannot ask a monitor
where the monitors are. It is read exactly once, by
`ceph-mon --mkfs`; from then on the monmap lives *inside* the MON's
store and is versioned like every other map.

**`mon/` — the cluster's memory.** A few one-line text markers
(`kv_backend`, `min_mon_release`, its own `keyring`, ...) so tools
can identify the directory, plus the real thing:

```
# ls /tmp/ceph/mon/store.db/ | head -6
000008.sst
000009.log
CURRENT
IDENTITY
LOCK
MANIFEST-000010
```

An ordinary RocksDB. Inside it: the full history of every cluster
map (that is what the epochs count), the cephx key database, and
the Paxos transaction log that makes multi-MON quorum work. Why a
transactional KV store: a map update must be committed atomically
or not at all — the same reasoning that gives BlueStore its
embedded RocksDB.

**`osdN/` — a pointer, not a store.** The most instructive listing,
because of what is *missing*:

```
# ls -l /tmp/ceph/osd0
-rw------- ... bfm_blocks, bfm_blocks_per_key,
               bfm_bytes_per_block, bfm_size      (freelist geometry)
lrwxrwxrwx ... block -> /dev/loop0                (the actual store)
-rw------- ... bluefs, kv_backend                 ("1", "rocksdb")
-rw------- ... ceph_fsid, fsid, whoami            (cluster, osd uuid, "0")
-rw-r--r-- ... keyring                            (osd.0's key only)
-rw------- ... magic, type, ready, mkfs_done      (type = "bluestore")
```

There are no data files here. The tiny text markers exist so that
`ceph-osd` (and the offline tools from Section 5) can check "this
is osd.0 of cluster X, BlueStore, fully formatted" *before* opening
the raw device — and the `block` symlink is the entire storage
configuration: everything, data and metadata and BlueStore's own
RocksDB, lives inside `/dev/loop0` (Section 5.4 reads its label).

**`run/` — talking to live daemons.** One `$name.pid` file and one
`$name.asok` UNIX socket per daemon. The admin socket is a side
door that skips the network and cephx entirely (root-only, local):
`ceph daemon osd.0 perf dump`, `ceph daemon mon.a mon_status` —
invaluable when a daemon is up but unreachable through the cluster.

**`log/` — one plain-text log per `$name`.** Where the "expected
noise" from Section 3.5's mkfs actually went; `-d` on any daemon
streams the same to the foreground instead.

**Where these live in a real deployment.** Our lab pinned every
path to `/tmp/ceph`; a normal install from Fedora packages sets
none of them — these locations are the compiled-in defaults, shaped
by the default cluster name (`ceph`) and `$cluster-$id`:

| This lab | Fedora packages |
|----------|-----------------|
| `ceph.conf` | `/etc/ceph/ceph.conf` |
| `keyring` (admin part) | `/etc/ceph/ceph.client.admin.keyring` |
| `monmap` | transient; discarded after `ceph-mon --mkfs` |
| `mon/` | `/var/lib/ceph/mon/ceph-a/` |
| `osd0/` | `/var/lib/ceph/osd/ceph-0/` |
| (mds, mgr, rgw dirs) | `/var/lib/ceph/{mds,mgr,radosgw}/ceph-*/` |
| `run/*.asok`, `*.pid` | `/var/run/ceph/` (tmpfs, from systemd) |
| `log/*.log` | `/var/log/ceph/` (+ `ceph.log` on the MON) |

Same shapes, different directories — plus a few pieces the lab
bypassed. Clients locate `/etc/ceph/ceph.client.admin.keyring` via
a built-in search order, which is why a bare `ceph -s` works on a
package host with no `keyring =` line in the conf. OSDs created by
`ceph-volume` take "a pointer, not a store" one step further: the
data directory is a *tmpfs*, regenerated on every activation from
LVM tags and the BlueStore label, with `block` aimed at an LVM
volume. Daemons run as the `ceph` user under systemd
(`ceph-osd@0.service`, ..., grouped by `ceph.target`). And per-type
`/var/lib/ceph/bootstrap-osd/ceph.keyring` keys — caps limited to
"may enroll a new OSD" — let hosts add daemons without holding the
admin key, where the lab just used `client.admin` for everything.
cephadm shifts this whole layer once more, to
`/var/lib/ceph/<fsid>/<name>/`.

The punchline of the tour: apart from three raw devices, a Ceph
cluster is a handful of INI files, tiny text markers, and two kinds
of RocksDB. Your *data* appears in none of these paths — it exists
only inside the OSDs' block devices.

# 4. Hands-on: the three interfaces

## 4.1 Block: RBD

RBD presents a virtual disk striped, 4 MiB at a time, over RADOS
objects. Create a pool for it, then an image:

```
# ceph osd pool create rbd
pool 'rbd' created
# rbd pool init rbd                                        (1)
# rbd create rbd/vol0 --size 4G                            (2)
# rbd info rbd/vol0
rbd image 'vol0':
        size 4 GiB in 1024 objects                         (3)
        order 22 (4 MiB objects)
        snapshot_count: 0
        id: 104672038b1c
        block_name_prefix: rbd_data.104672038b1c           (4)
        format: 2
        features: layering, exclusive-lock, object-map,
                  fast-diff, deep-flatten
```

1. Stamps the pool with the `rbd` application tag; Ceph refuses I/O to
   untagged pools to catch pool-name typos.
2. Creating a 4 GiB image is instant — RBD is thin-provisioned. Only a
   small header object exists now; data objects appear on first write.
3. 4 GiB / 4 MiB = 1024 potential data objects.
4. **Remember this prefix.** Every data object of this image is named
   `rbd_data.104672038b1c.<16-hex-digit object index>` — the handle
   the trace in Section 5 hangs on.

Map it through the kernel RBD driver and use it like any disk:

```
# rbd map rbd/vol0
/dev/rbd0
# mkfs.xfs -q /dev/rbd0
# mount /dev/rbd0 /mnt/vol0
# echo 'hello from rbd' > /mnt/vol0/hello.txt
# sync
```

`rbd map` talks to `drivers/block/rbd.c` in the running kernel, which
speaks the RADOS protocol directly (`net/ceph/`) — no daemon in the
I/O path. The lazily created data objects are now visible:

```
# rados -p rbd ls | grep rbd_data | sort | head -5
rbd_data.104672038b1c.0000000000000000                     (1)
rbd_data.104672038b1c.000000000000007f                     (2)
rbd_data.104672038b1c.00000000000000ff
rbd_data.104672038b1c.000000000000017f
rbd_data.104672038b1c.00000000000001ff
```

1. Object index 0 covers image bytes 0–4 MiB: the XFS superblock, the
   first allocation group's metadata — and our file's data.
2. The scattered indexes (`0x7f` = image bytes 508–512 MiB, etc.) are
   XFS metadata that mkfs placed near its allocation-group boundaries.
   Everything mkfs and the file write did not touch **simply does not
   exist** — thin provisioning at the object level.

Which object holds `hello.txt`? Ask XFS where the file's data landed
in the image:

```
# xfs_bmap -v /mnt/vol0/hello.txt
/mnt/vol0/hello.txt:
 EXT: FILE-OFFSET  BLOCK-RANGE  AG AG-OFFSET  TOTAL FLAGS
   0: [0..7]:      104..111      0 (104..111)     8 001111
```

Sector 104 × 512 = byte offset 53248 — inside the first 4 MiB, so the
file's bytes live in object `rbd_data.104672038b1c.0000000000000000`:

```
# rados -p rbd stat rbd_data.104672038b1c.0000000000000000
rbd/rbd_data.104672038b1c.0000000000000000
    mtime 2026-07-24T10:09:54.000000-0500, size 131072     (1)
```

1. The object's logical size is 128 KiB, not 4 MiB: XFS has only
   written the first 128 KiB of this 4 MiB stripe so far. Thin at the
   image level, thin inside each object too.

## 4.2 File: CephFS

CephFS needs two pools (data, metadata) and an MDS daemon serving the
metadata. (On a cephadm cluster, `ceph fs volume create fs1` does all
of this in one step through the orchestrator; here it is spelled out.)

```
# ceph osd pool create cephfs.fs1.meta
pool 'cephfs.fs1.meta' created
# ceph osd pool create cephfs.fs1.data
pool 'cephfs.fs1.data' created
# ceph fs new fs1 cephfs.fs1.meta cephfs.fs1.data
new fs with metadata pool 3 and data pool 4
# ceph auth get-or-create mds.a mon 'allow profile mds' \
      mgr 'allow profile mds' osd 'allow *' mds 'allow *' \
      >> /tmp/ceph/keyring
# ceph-mds -i a
starting mds.a at
# ceph fs status fs1
fs1 - 0 clients
===
RANK  STATE   MDS     ACTIVITY     DNS    INOS   DIRS   CAPS
 0    active   a   Reqs:    0 /s    10     13     12      0
      POOL         TYPE     USED  AVAIL
cephfs.fs1.meta  metadata  42.2k  5792M                    (1)
cephfs.fs1.data    data       0   5792M
```

1. Directory trees and inodes are a separate pool from file data — a
   real cluster puts metadata on flash and data on cheaper media.

Mount it with the kernel client (`fs/ceph/`). The device string names
user, cluster fsid and filesystem; the options carry the MON address
and the admin secret (`mount.ceph` can also pull these from
`/etc/ceph/` on a normally-installed host):

```
# mount -t ceph \
    admin@8afd54fd-8414-4306-82f4-c04865594638.fs1=/ /mnt/fs1 \
    -o mon_addr=127.0.0.1:3300,secret=<admin key>,ms_mode=prefer-crc
# echo 'hello from cephfs' > /mnt/fs1/hello.txt
# sync
```

The division of labor: the kernel client asks the **MDS** for metadata
operations (lookup, create, permissions), but file *data* goes
directly to OSDs, striped into 4 MiB objects named
`<inode number in hex>.<stripe index>`:

```
# ls -i /mnt/fs1/hello.txt
1099511627776 /mnt/fs1/hello.txt                           (1)
# rados -p cephfs.fs1.data ls
10000000000.00000000                                       (2)
```

1. `1099511627776` = `0x10000000000` — CephFS inode numbers for user
   files start there.
2. The file's first (and only) stripe object: inode in hex, dot,
   stripe index. The same tracing recipe as RBD applies verbatim.

# radosgw-admin user create --uid=ming --display-name=Ming
{
    "user_id": "ming",
    "display_name": "Ming",
    ...
    "keys": [
        {
            "user": "ming",
            "access_key": "Q0IGKXB3DP715F99P4F5",          (2)
            "secret_key": "0DyfAtAdSExBAZHMCdJ4E4C7T4Ex...",
            "active": true
        }

}
```

1. Listens on port 8000 per the `[client.rgw.s3]` config section; on

Point `s3cmd` at it and do normal S3 things:

Three interfaces, one lesson: an RBD block range, a CephFS file stripe

# 5. Under the hood: from user file to raw disk bytes

Now the deep dive. We take `/mnt/vol0/hello.txt` from Section 4.1 and
follow its bytes all the way down. The chain:

```
file → XFS → /dev/rbd0 byte 53248 → object rbd_data.…0000 →
PG 2.14 → osd.2 → BlueStore → /dev/loop2
```

## 5.1 Step 1: object name → PG → OSDs

`ceph osd map` answers "where does this object live?" — and it answers
*without contacting any OSD*, because placement is computed:

```
# ceph osd map rbd rbd_data.104672038b1c.0000000000000000
osdmap e39 pool 'rbd' (2)
  object 'rbd_data.104672038b1c.0000000000000000'
  -> pg 2.f7af1ef4 (2.14)                                  (1)
  -> up ([2,1], p2) acting ([2,1], p2)                     (2)

# ceph pg map 2.14
osdmap e41 pg 2.14 (2.14) -> up [2,1] acting [2,1]         (3)
```

1. The object *name* is hashed to `0xf7af1ef4`. The pool has 32 PGs,
   so the hash is masked to 5 bits: `0xf7af1ef4 & 0x1f = 0x14` — PG
   `2.14` ("pool 2, PG 0x14"). Every object hashing into this bucket
   shares the PG's placement and fate.
2. CRUSH maps PG `2.14` onto OSDs `[2, 1]`: two replicas, per the
   pool's `size 2`, on distinct OSDs, per our `chooseleaf type 0`.
   `p2` marks **osd.2 as the primary** — all client I/O for this PG
   goes to osd.2, which replicates to osd.1 and acks only after both
   have the write persisted.
3. Asking again two epochs later gives the same answer — placement is
   a pure function of (PG, CRUSH map, rule), not a directory lookup.
   Any client with the current map computes the same result; when the
   map changes (an OSD dies), the function's output changes, and
   exactly the affected PGs migrate. The implementation lives in
   [`src/crush/`][src-crush]. (This determinism is also why the
   balancer was turned off in Section 3.4: its pg-upmap exceptions
   are the one thing that can override CRUSH's answer.)

## 5.2 Step 2: a reference checksum through the block device

Before going below the RADOS line, record what the truth looks like
from above: unmount (so XFS flushes everything) and hash the object's
128 KiB range directly from the RBD device:

```
# umount /mnt/vol0
# dd if=/dev/rbd0 iflag=skip_bytes,count_bytes skip=0 \
     count=131072 status=none | md5sum
1674ddca3f6a7ce73a594761e80e1ff7  -
```

## 5.3 Step 3: open the primary OSD's BlueStore offline

`ceph-objectstore-tool` opens a **stopped** OSD's BlueStore and lets
you list, dump and extract objects. Stopping osd.2 is safe: osd.1
holds the other replica, takes over as primary, and the cluster just
runs degraded until we restart (`min size 1` permits I/O with a single
copy):

```
# kill $(cat /tmp/ceph/run/osd.2.pid)
# ceph-objectstore-tool --data-path /tmp/ceph/osd2 --op list \
      2>/dev/null | grep 104672038b1c.0000000000000000
["2.14",{"oid":"rbd_data.104672038b1c.0000000000000000",
         "snapid":-2,"hash":4155449076,"pool":2}]          (1)
```

1. There it is — our object, in PG `2.14` on this OSD, exactly as
   `ceph osd map` predicted from the outside. Note
   `4155449076 = 0xf7af1ef4`: the same name hash from step 1, stored
   with the object. (`$obj` in the commands below holds this JSON
   line verbatim — it is the tool's object handle.)

`dump` shows the object's replication metadata and BlueStore onode
(abridged):

```
# ceph-objectstore-tool --data-path /tmp/ceph/osd2 "$obj" dump
{
    "info": {
        "version": "42'162",                               (1)
        "size": 131072,
        "mtime": "2026-07-24T10:10:30.515441-0500",
        ...
    },
    "stat": { "size": 131072, "blksize": 4096, "blocks": 32 },
    "onode": { "nid": 1169, "size": 131072, ... }          (2)
}
```

1. "osdmap epoch 42, version 162" — the PG's log sequence for this
   object; this is what replicas compare during peering/recovery.
2. The BlueStore onode: the per-object metadata record (kept in the
   OSD's embedded RocksDB) whose extent map points at the raw-device
   blocks holding the data. The full story of onodes, extent maps and
   the RocksDB schema is in [the BlueStore post][bluestore-post].

## 5.4 Step 4: extract the raw bytes and compare

```
# ceph-objectstore-tool --data-path /tmp/ceph/osd2 "$obj" \
      get-bytes /tmp/obj.bin
# ls -l /tmp/obj.bin
-rw-r--r-- 1 root root 131072 Jul 24 10:10 /tmp/obj.bin
# md5sum /tmp/obj.bin
1674ddca3f6a7ce73a594761e80e1ff7  /tmp/obj.bin             (1)
```

1. **Identical to the hash from step 2.** The bytes XFS wrote through
   `/dev/rbd0` are byte-for-byte what BlueStore stored on osd.2's raw
   loop device: page cache → krbd → RADOS write to PG 2.14's primary
   → BlueStore transaction on osd.2 (replicated to osd.1) → done.

And the "disk" itself carries a BlueStore label instead of a
filesystem superblock — there is nothing mountable on an OSD device:

```

    "/tmp/ceph/osd2/block": {
        "osd_uuid": "f1681c2c-3701-49f6-9349-f8531fcfc5f9",

        "description": "main",

        "kv_backend": "rocksdb",

```

1. BlueStore owns the raw device outright: data extents are allocated
   directly on it, metadata lives in RocksDB, and RocksDB's own files

   [Ceph BlueStore Explained][bluestore-post].

# 6. Under the hood: authentication, from Kerberos to cephx

Section 3.2 used cephx and stated the rules; this section explains
where those rules come from.

## 6.1 Why a storage cluster needs its own auth

Every daemon in this post listens on plain TCP and speaks the RADOS
protocol; clients connect straight to OSDs. Without authentication,
anyone who can reach the network could claim to be `client.admin`,
enroll a rogue OSD (and have the cluster helpfully *replicate data
to it*), or replay captured writes. So the requirements are:

- **Mutual authentication** — daemons verify clients *and* each
  other; a rogue OSD must be rejected just like a rogue client.
- **Authorization** — different principals get different rights
  (the cap strings: `mon 'allow r'`, `osd 'allow rwx'`, profiles).
- **No authority on the data path** — Section 5.1 showed placement is
  computed client-side precisely to avoid a central lookup server;
  auth must not sneak one back in as a per-I/O "may I?" service.
- **Secrets never cross the wire** — the network is untrusted.

This is an old problem shape: many clients, many services, one
trusted authority, hostile network. MIT solved it in the 1980s.

## 6.2 The Kerberos idea in one diagram

Kerberos assumes a Key Distribution Center (KDC) that shares a
secret with every principal. Nobody ever sends a secret over the
wire — not even hashed. Instead, the KDC answers a *plaintext*
request with **two sealed boxes carrying the same freshly-minted
session key**, one openable by the client, one by the service:

```
 +--------+ (1) "alice here: a ticket    +----------+
 |        |      for service S, please"  |   KDC    |
 |        | ---------------------------> | all keys |
 | client | (2) reply: two sealed boxes  +----------+
 |        | <---------------------------
 |        |  [session key]                sealed with ALICE's key
 |        |      -> only she can open it: that IS the login
 |        |  [alice, session key, expiry] sealed with S's key
 |        |      -> the TICKET: opaque to her, forwarded as-is
 |        |
 |        | (3) ticket + authenticator   +----------+
 |        |     (encrypted w/ session k) | service  |
 |        | ---------------------------> |    S     |
 |        | (4) S unseals ticket locally +----------+
 |        | <==========================>
 +--------+   both now hold the same session key
```

This is how the client gets the session key: box one is sealed with
the *client's own* secret, so decrypting it is simultaneously the
delivery of the key and the proof of identity — an impostor without
alice's secret holds two boxes it cannot open. Box two, the
**ticket**, carries the same session key to the service by a route
the client cannot read or tamper with. In step (3) the client adds
a small *authenticator* (e.g. a timestamp) encrypted with the
session key, proving it really opened box one; the service unseals
the ticket with its own key, finds the same session key inside, and
checks the authenticator and expiry — all **without asking the
KDC**. Authenticate once, then talk to many services directly until
expiry forces a background renewal.

## 6.3 cephx: Kerberos re-cast for a storage cluster

cephx keeps the architecture and changes the casting:

| Kerberos | cephx |
|----------|-------|
| KDC | the MON quorum (auth database in the MON's store) |
| principal + password | principal + keyring file |
| ticket | ticket carrying identity + **caps** + session key |
| service's secret key | *rotating* secret shared by each daemon class |
| authorization data | the cap strings minted in Sections 3–4 |

```
 client                MON (key authority)              OSDs
   |  (1) handshake: prove  |                             |
   |      client.admin key  |                             |
   | ---------------------> |                             |
   |  (2) tickets + session |                             |
   | <--------------------- |                             |
   |     (sealed with the rotating service secret)        |
   |                        |                             |
   |  (3) I/O request + ticket -------------------------> |
   |      OSD unseals locally: identity, caps, skey       |
   | <=================================================== |
   |      signed traffic — no MON on the data path        |
```

Ceph-specific adaptations worth knowing:

- **Keyrings, not passwords** — a principal's key is a file
  (Section 3.2's `ceph-authtool` output); daemons authenticate to
  the MON exactly like clients, with keys minted at enrollment time
  (`ceph osd new`, `ceph auth get-or-create`).
- **Rotating service secrets** — all OSDs share one rotating secret
  (likewise MDS, MGR), refreshed from the MON on a TTL. Note this is
  *not* the key in a daemon's keyring file: that one is its
  permanent login credential (how `osd.0` authenticates to the MON,
  like any client); the rotating secret is fetched *after* that
  login and lives only in memory — it is how any OSD can unseal any
  client's ticket. Revocation is passive: a deleted principal simply
  fails its next renewal.
- **Caps ride in the ticket** — authorization is enforced by each
  daemon from the unsealed ticket, no directory consulted per op.
- **Integrity, not secrecy** — cephx authenticates the parties; it
  does not encrypt payloads. Per-message protection is the
  messenger's job: msgr2 (the `v2:` address flavor in Section 3.1's
  `mon host`) runs in `crc` mode — checksums, what our CephFS
  mount's `ms_mode=prefer-crc` chose — or `secure` mode, which
  encrypts everything with AES-GCM.

Seen from here, Section 3.2's bootstrap ritual is just KDC seeding:
`mon.` is the KDC's own identity, `client.admin` is the first
enrolled principal, and everything later joins through the front
door.

# 7. Next steps for aspiring Ceph developers

## 7.1 From packages to developer builds

This post ran release binaries; for development you want to run code
you just built. The standard loop:

```
git clone https://github.com/ceph/ceph.git && cd ceph
./install-deps.sh                  # dnf-installs build deps on Fedora
./do_cmake.sh -DCMAKE_BUILD_TYPE=RelWithDebInfo
cd build && ninja                  # long; -j to taste
```

Then [`vstart.sh`][vstart] launches a throwaway cluster **from the
build tree** — conceptually exactly what Section 3 did by hand
(vstart generates a conf, mints keys, starts mon/mgr/osd/mds as plain
processes), just automated:

```
cd build
MON=1 OSD=3 MDS=1 ../src/vstart.sh -d -n -x
./bin/ceph -s        # note: ./bin/ceph, the freshly built CLI
```

`-n` creates a new cluster, `-d` enables debug output, and env vars
pick the daemon counts. Edit code, `ninja`, restart — a minutes-long
iteration loop. Its sibling `cstart.sh` does the same with containers,
and `mstart.sh` runs several clusters side by side. The
[developer guide][doc-dev] documents the workflow. (For production
deployments the tool is [cephadm][doc-cephadm] — same daemons, run as
podman containers under systemd.)

## 7.2 Where to start reading code

Guided by the trace in Section 5, each hop has a home in the tree
(refs against [`v20.2.2`][ceph-tag]):

- [`src/crush/`][src-crush] — the placement function; small,
  self-contained, and the best first read.
- [`src/osd/`][src-osd] — the OSD: PG state machine, replication,
  recovery. Start at `PrimaryLogPG.cc` for the write path a client op
  takes on a primary (the `version 42'162` in Section 5.3 is its PG
  log at work).
- [`src/os/bluestore/`][src-bluestore] — the storage engine from
  Section 5.4 ([companion post][bluestore-post]).
- [`src/librbd/`][src-librbd] — the userspace RBD client (QEMU uses
  this); its kernel twin is [`drivers/block/rbd.c`][krbd].
- [`src/mds/`][src-mds] — the CephFS metadata server; kernel client in
  [`fs/ceph/`][kcephfs].
- [`src/rgw/`][src-rgw] — the S3/Swift gateway.
- [`src/auth/`][src-auth] — the cephx protocol from Section 6:
  tickets, rotating secrets, the handshake.

And if kernel storage is your angle, the client side is a first-class
entry point: `net/ceph/` (the messenger), `drivers/block/rbd.c` and
`fs/ceph/` were all exercised by this very lab — booted, and equally
patchable and testable, with nothing more than the `vmtest` VM we
started from.
