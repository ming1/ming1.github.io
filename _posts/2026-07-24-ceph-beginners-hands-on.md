# 1. Introduction and core terminology

Ceph exposes three user-facing interfaces — block, file and object —
over one internal object store, **RADOS**. This post walks the full
loop: assemble a five-node cluster daemon by daemon, read back what it
is made of, use all three interfaces, then trace one written object
through placement, across three machines, onto a raw disk, verifying
every hop with checksums. For engineers who want to *use* Ceph now and
*hack on* Ceph later.

Vocabulary first, in five groups. Every term below appears in real
output later.

**The cluster and its unit of storage:**

| Term | Meaning |
|------|---------|
| cluster | one Ceph deployment: the MONs, MGRs, OSDs, ... acting as one |
| fsid | the cluster's UUID — stamped into maps, stores, device labels |
| RADOS | Reliable Autonomic Distributed Object Store — the core cluster |
| object | RADOS's unit: name + bytes + xattrs + omap (key/value pairs) |

**Daemons, and the maps that describe them** — Section 3 starts these
one by one; keeping the maps is what the MON exists for:

| Term | Meaning |
|------|---------|
| OSD | Object Storage Daemon — one per disk; stores objects (BlueStore) |
| BlueStore | the OSD's storage engine: raw device, no filesystem below |
| BlueFS | BlueStore's tiny internal FS, only to host its own RocksDB |
| MON | Monitor — keeps the authoritative cluster maps, forms quorum |
| quorum | the MON majority that must agree before a map change commits |
| monmap | the map of the MONs themselves: who they are, where they listen |
| osdmap | the map of OSDs (which exist, up/in state) — versioned by epoch |
| epoch | a map's version number, bumped on every change (`osdmap e186`) |
| MGR | Manager — metrics, orchestration modules, balancer, dashboard |

**Placement** — how an object finds its disks (traced live in
Section 6), and the PG states `ceph -s` reports:

| Term | Meaning |
|------|---------|
| Pool | a namespace of objects with a replication/EC policy |
| PG | Placement Group — a shard of a pool; unit of replication/recovery |
| CRUSH | the placement function: PG → list of OSDs, computed, not looked up |
| failure domain | the level CRUSH spreads replicas across: OSD, host, rack |
| device class | `hdd`/`ssd`/`nvme`, auto-detected; CRUSH rules can select on it |
| up set | the OSDs CRUSH says should hold a PG right now |
| acting set | the OSDs actually serving it — differs from `up` during recovery |
| primary | the first OSD of the acting set; all client I/O for the PG goes there |
| active+clean | PG state: serving I/O, every replica current — the goal |
| degraded | PG state: at least one object has fewer copies than it should |
| undersized | PG state: the acting set is smaller than the pool's `size` |
| peering | PG state: replicas reconciling history before serving I/O |

**Authentication** — the cephx cast, first used in Section 3.2 and
unpacked in Section 7:

| Term | Meaning |
|------|---------|
| cephx | shared-secret auth: the MON stores all keys and issues tickets |
| principal | a named identity in cephx: `mon.`, `client.admin`, `osd.0` |
| key | a principal's secret — in a keyring file and the MON's database |
| caps | a principal's rights, per daemon type: `osd 'allow rwx'`, ... |
| profile | a canned cap bundle: `allow profile osd`, `profile mds`, ... |
| ticket | Kerberos-style token: identity + caps + session key (Sec 7) |
| session key | fresh per-login secret both sides share to key the talk |
| authenticator | timestamp sealed with the session key, proving key receipt |

**Interfaces and deployment** — Section 5 uses all three:

| Term | Meaning |
|------|---------|
| RBD | RADOS Block Device — virtual disks striped over RADOS objects |
| CephFS | POSIX filesystem on RADOS; an MDS daemon serves the metadata |
| MDS | Metadata Server — CephFS's directory tree and inode authority |
| RGW | RADOS Gateway — S3/Swift-compatible HTTP object storage |
| cephadm | production deployment tool — daemons as podman containers |

The key architectural idea: **clients compute data locations instead of
asking a central server**. An object name hashes to a PG, and CRUSH
maps that PG to a set of OSDs using only the compact cluster map the
MONs distribute. No lookup table in the data path, so there is no
metadata bottleneck to scale. CephFS is the partial exception — POSIX
semantics need a real metadata server, the MDS — but file *data* still
goes straight from client to OSDs.

```
   +-----------+    +------------+    +---------------------+
   |    RBD    |    |   CephFS   |    |    RGW  (S3 API)    |
   |  (block)  |    |   (file)   |    |      (object)       |
   +-----+-----+    +-----+------+    +----------+----------+
         |                |      \               |
   krbd or librbd   kernel client \_ MDS      radosgw daemon
         |          or libcephfs  (metadata)     |
   +-----v----------------v-----------------------v---------+
   |              librados  /  RADOS protocol               |
   +----------------------------+---------------------------+
                                |
                object name --hash--> PG --CRUSH--> OSDs
                                |
     +-------------+------------+------------+-------------+
     |             |                         |             |
 +---v----+   +----v---+   +--------+   +----v---+   +-----v--+
 |  c22   |   |  c23   |   |  c24   |   |  c25   |   |  c21   |
 | OSD 0-3|   | OSD 4-7|   |OSD 8-11|   |OSD12-15|   |MON,MGR |
 | MON    |   |        |   |        |   | MDS    |   |MDS,RGW |
 +--------+   +--------+   +--------+   +--------+   +--------+
   \____________ replicas land on three distinct hosts ____/
```

Every interface at the top decomposes user data into RADOS objects
(typically 4 MiB) at the bottom. That single fact is what Section 6
exploits to trace a file's bytes to a physical disk offset on a named
machine.

**why is pool introduced**

Without pools, all data in a Ceph cluster would be treated identically—stored with 
the same redundancy settings, on the same disks, with the same access permissions. 
Ceph introduced pools to solve four major operational requirements:

## Hardware Tiering & Performance Isolation

Different applications have different speed requirements. A Virtual Machine disk (RBD) 
needs low latency, while an archival backup needs cheap capacity.

Pools allow you to map specific data to specific hardware using CRUSH rules.

You can route a high-speed pool to fast NVMe SSDs, and a bulk backup pool to slow HDDs.

## Flexible Data Protection Strategies

Not all data requires the same durability model:

Replication: High performance, lower disk efficiency (e.g., 3x replication consumes 300% storage).

Erasure Coding (EC): Like RAID-5/6, offers high capacity efficiency (e.g., 8+2 EC consumes ~125% 
storage) but incurs CPU/latency overhead on small writes.
Pools allow you to mix both strategies in the same Ceph cluster.

## Multi-Tenant Security & Access Control

Using CephX, you can restrict users or services so they can only access specific pools. For 
instance, the OpenStack block storage service (Cinder) can be given access only to the 
volumes pool, preventing it from touching the CephFS metadata pool.

## Resource Management (PGs & Quotas)
Pools give administrators fine-grained control over cluster resources:

Placement Groups (PGs): Allocated on a per-pool basis based on expected data volume.

Quotas: Enforce hard limits on maximum byte usage or object count per pool.

# 2. The lab: five nodes, sixteen OSDs

## 2.1 The cluster

Everything below runs on **five Fedora 44 virtual machines** on one
virtual network (`10.0.0.0/24`), named `c21`–`c25`. Ceph comes from
ordinary Fedora packages, and every daemon runs as a plain **systemd
service on the host** — no containers, no orchestrator. That is the
point: every file, unit and command is visible with `ls` and
`systemctl`, nothing hidden inside `ceph orch` or an image. It is the
upstream [manual deployment procedure][doc-manual] carried out across
five machines.

Roles are spread the way a small production cluster would spread them:

| Node | Ceph roles | Storage |
|------|-----------|---------|
| `c21` | MON, MGR, MDS, RGW, and the admin/client host | none |
| `c22` | MON, 4 OSDs | 4 × 6 GiB |
| `c23` | 4 OSDs | 4 × 6 GiB |
| `c24` | 4 OSDs | 4 × 6 GiB |
| `c25` | MDS, 4 OSDs | 4 × 6 GiB |

Sixteen OSDs, 96 GiB raw. Every `ceph` command runs on `c21`, which
holds no data — so when Section 5 maps an RBD image and mounts CephFS
there, the I/O genuinely crosses the network. That is why a multi-node
lab is worth the trouble: on one machine, "the client computes
placement and contacts the right OSD directly" is a claim you take on
faith.

Each storage node's four disks are attached over different emulated
buses — virtio, SCSI and NVMe — because that is what decides the
**device class**:

```
[c24]# for d in vdb sda sdb nvme0n1; do
         printf "%-10s rotational=%s\n" "$d" "$(cat /sys/block/$d/queue/rotational)"
       done
vdb        rotational=1
sda        rotational=1
sdb        rotational=1
nvme0n1    rotational=0
```

Ceph reads that flag and labels each OSD `hdd` or `ssd` — three
HDD-class and one SSD-class device per host. Nothing here is really
rotating rust, but the *classes* are real to CRUSH, which is enough to
do what production clusters do: CephFS metadata on the fast class, bulk
data on the slow one (Section 5.2), via CRUSH rules that select on it
(Section 4.2).

## 2.2 What this lab is not

Three caveats, all visible in the output:

- **Two monitors is worse than one.** Quorum needs a strict majority,
  and the majority of two is two: this cluster tolerates zero MON
  failures, exactly like a single MON, while needing two machines up to
  work at all. Production runs 3 or 5. The pair here demonstrates *how*
  a monitor joins an existing quorum (Section 3.5); it buys no
  availability.
- **The disks are virtual.** All sixteen are files on one laptop SSD, so
  the cluster permanently reports `BLUESTORE_SLOW_OP_ALERT` — BlueStore
  noticing operations take longer than it expects. A true observation
  about slow storage, not a Ceph problem, and the only health warning
  left standing in every `ceph -s` below.
- **One network.** Ceph can separate a *public* network (clients ↔ OSDs)
  from a *cluster* network (OSD ↔ OSD replication and recovery); here
  both are `10.0.0.0/24`.

Without five machines, two documented paths give a real RADOS cluster
on one host: `cephadm bootstrap --single-host-defaults`
([docs][doc-cephadm]), or [`vstart.sh`][vstart] for a throwaway cluster
of plain processes out of a build tree (Sections 8.1 and 9). Sections 5–7 are
identical on all three.

# 3. Bootstrapping the cluster by hand

No `ceph orch`, no reconciliation loop, no container image — just the
commands, in order, that turn five bare Fedora machines into a Ceph
cluster. Worth reading even if you will only ever run cephadm, because
cephadm does exactly these steps for you.

The packages, installed per role:

| Package | Role | What it provides |
|---------|------|------------------|
| `ceph-common` | everywhere | `ceph`, `rbd`, `rados`, `ceph-authtool`, `mount.ceph` |
| `ceph-base` | (dependency) | `monmaptool` and the other offline map tools |
| `ceph-mon` | monitors | the monitor daemon |
| `ceph-mgr` | managers | the manager daemon and its Python modules |
| `ceph-osd` | storage | `ceph-osd`, `ceph-objectstore-tool`, `ceph-bluestore-tool` |
| `ceph-volume` | storage | provisions OSDs onto devices — **not** pulled in by `ceph-osd` |
| `ceph-mds` | metadata | the CephFS metadata server |
| `ceph-radosgw` | gateway | the S3/Swift HTTP daemon |

## 3.1 The config file

A brand-new cluster needs a `fsid` (any UUID) and a first monitor.
`/etc/ceph/ceph.conf` on the bootstrap host, and nothing more:

```
[global]
fsid = 8830b0e0-0d9f-4729-b01d-73c5dcda498e
mon initial members = c21                                          (1)
mon host = 10.0.0.21                                               (2)
public network = 10.0.0.0/24
auth cluster required = cephx                                      (3)
auth service required = cephx
auth client required = cephx
osd memory target = 1073741824                                     (4)
```

1. The quorum expected at startup. This stays pinned to the bootstrap
   set as monitors are added — growing it mid-rollout would briefly
   declare an even-numbered expected quorum, which is exactly the
   configuration that cannot form a majority.
2. Where to *find* monitors. This one does have to track the live set,
   and updating it on every host is the one piece of distributed state
   you maintain by hand (Section 3.8).
3. cephx on for daemons authenticating to the cluster, for services,
   and for clients. It is the default, and Section 7 explains what it
   buys.
4. Each OSD is told to aim for 1 GiB of memory instead of the 4 GiB
   default — four OSDs to a small VM.

Everything else these daemons need is learned from the monitor after
connecting, or lives in the MON's config store (Section 4.2), which is
why the file is short and rarely changes.

## 3.2 Three keys before the cluster exists

cephx is Ceph's shared-secret authentication: named principals, keys,
and Kerberos-style tickets that let daemons verify callers locally
(Section 7). For bootstrap, one fact matters: the **MON is the key
authority**. Every later command and daemon authenticates against it,
but the tools that create keys need a running, authenticated cluster
themselves. Breaking that circle means minting a few keys *offline*, as
plain files, before any daemon starts.

```
[c21]# ceph-authtool --create-keyring /tmp/ceph.mon.keyring \
           --gen-key -n mon. --cap mon 'allow *'                   (1)
creating /tmp/ceph.mon.keyring

[c21]# ceph-authtool --create-keyring /etc/ceph/ceph.client.admin.keyring \
           --gen-key -n client.admin \
           --cap mon 'allow *' --cap osd 'allow *' \
           --cap mds 'allow *' --cap mgr 'allow *'                 (2)

[c21]# install -d -o ceph -g ceph /var/lib/ceph/bootstrap-osd
[c21]# ceph-authtool --create-keyring /var/lib/ceph/bootstrap-osd/ceph.keyring \
           --gen-key -n client.bootstrap-osd \
           --cap mon 'profile bootstrap-osd' --cap mgr 'allow r'    (3)

[c21]# ceph-authtool /tmp/ceph.mon.keyring \
           --import-keyring /etc/ceph/ceph.client.admin.keyring     (4)
[c21]# ceph-authtool /tmp/ceph.mon.keyring \
           --import-keyring /var/lib/ceph/bootstrap-osd/ceph.keyring
```

1. **`mon.` — the authority's own identity.** The monitor validates
   everyone else's keys, but with `auth cluster required = cephx` it
   needs a key of its own before it can start. In a multi-monitor
   cluster this same shared key is also how monitors trust each other
   in quorum — note in Section 3.5 that the second monitor is given
   *this* key, not one of its own.
2. **`client.admin` — your identity.** The principal every `ceph`, `rbd`
   and `rados` invocation and both kernel mounts act as. It must exist
   before the cluster does: once the MON is up with cephx required, even
   `ceph auth get-or-create` — the command that creates keys — demands
   an authenticated caller. Without a pre-seeded admin key you are
   locked out by the auth you just enabled.
3. **`client.bootstrap-osd` — a deliberately weak key.** Its single cap
   registers new OSDs and does nothing else, so a storage host can
   create its own OSD identities (Section 3.6) without ever holding an
   admin key. Generating it by hand is belt and braces: the monitor
   mints the whole family itself on first startup
   (`AuthMonitor::_generate_bootstrap_keys` in [`src/mon/`][src-mon],
   from `create_initial()`), so `bootstrap-osd`, `-mds`, `-mgr`, `-rgw`,
   `-rbd` and `-rbd-mirror` all appear in Section 4.3's listing even
   though only this one was used.
4. `--import-keyring` merges the other two into the mon keyring,
   because `ceph-mon --mkfs` seeds its auth database from exactly one
   file. After mkfs, the MON's own store is the source of truth and
   these files are just client-side credentials.

Everything else in the cluster — `mgr.c21`, `osd.0`–`osd.15`,
`mds.c21`, `mds.c25`, `client.rgw.c21` — is minted **online** with
`ceph auth get-or-create` or by `ceph-volume`, authenticated as
`client.admin`. Watch for those calls in the sections that follow.

## 3.3 The first monitor

A monitor cannot ask a monitor where the monitors are, so the very
first one is built from a **monmap constructed offline**:

```
[c21]# monmaptool --create --fsid 8830b0e0-0d9f-4729-b01d-73c5dcda498e \
           --addv c21 '[v2:10.0.0.21:3300,v1:10.0.0.21:6789]' /tmp/monmap
monmaptool: monmap file /tmp/monmap
setting min_mon_release = tentacle
monmaptool: set fsid to 8830b0e0-0d9f-4729-b01d-73c5dcda498e
monmaptool: writing epoch 0 to /tmp/monmap (1 monitors)
```

Use `--addv` with **both** addresses, not `--add` with a bare IP. A
bare IP records only the legacy msgr1 address (port 6789), so the
bootstrap monitor comes up without msgr2 — a permanent
`MON_MSGR2_NOT_ENABLED` warning, and, worse, `rbd map` fails outright
because krbd defaults to msgr2. Monitors that join later inherit both
addresses from the live monmap, so **only the first monitor can have
this defect**, which is precisely what makes it easy to miss.

Then build the store and start the daemon:

```
[c21]# install -d -o ceph -g ceph /var/lib/ceph/mon/ceph-c21          (1)
[c21]# sudo -u ceph ceph-mon --mkfs -i c21 \
           --monmap /tmp/monmap --keyring /tmp/ceph.mon.keyring       (2)
[c21]# systemctl enable --now ceph-mon@c21                            (3)
[c21]# rm -f /tmp/monmap /tmp/ceph.mon.keyring                        (4)
```

1. The directory name is `<cluster>-<id>`; the daemon derives it from
   its own id, which is why one templated unit file serves every
   monitor.
2. mkfs builds the monitor's private store — a small RocksDB — and
   seeds it with the monmap and the three keys. Run it **as the `ceph`
   user**: a root-owned store leaves the daemon unable to open its own
   files, and the resulting error names permissions on a path, not the
   mistake.
3. `ceph-mon@c21` — the templated unit instantiated for this id.
4. Staging files, done with. That keyring holds the `mon.`, admin and
   bootstrap secrets in one world-visible path; nothing needs it after
   mkfs.

The monitor is now the cluster. It holds the authoritative, versioned
maps — monmap, osdmap, CRUSH map, MDS map, cephx key database — and
distributes them to clients and daemons, which *subscribe* rather than
poll. Every `ceph` command is a conversation with it. Your data never
touches it: it knows where everything *may* be placed and stores none
of it.

## 3.4 The manager

```
[c21]# ceph auth get-or-create mgr.c21 \
           mon 'allow profile mgr' osd 'allow *' mds 'allow *'        (1)
[c21]# install -d -o ceph -g ceph /var/lib/ceph/mgr/ceph-c21
[c21]# ceph auth get mgr.c21 > /var/lib/ceph/mgr/ceph-c21/keyring     (2)
[c21]# chown ceph:ceph /var/lib/ceph/mgr/ceph-c21/keyring
[c21]# chmod 600 /var/lib/ceph/mgr/ceph-c21/keyring                   (3)
[c21]# systemctl enable --now ceph-mgr@c21
```

1. The first *online* key mint — the pattern promised in 3.2: an
   authenticated `client.admin` asks the MON to create `mgr.c21`.
   `allow profile mgr` is a canned cap bundle meaning "what a manager
   legitimately needs", maintained upstream; hand-writing the
   equivalent is verbose and a security bug waiting to happen.
2. The MON is now the source of truth for that key; `ceph auth get`
   exports a copy in keyring format for the daemon to read.
3. Not optional. A shell redirection creates the file at `0666 & ~umask`
   = `0644`, so without this the manager's key is world-readable on the
   host. The same applies to every `ceph auth get > ...` below.

Why a second brain? The MGR exists to keep the MON's Paxos path lean:
everything that is *reporting* rather than *authority* moved there.
OSDs stream their PG and performance statistics to the MGR, so the
`data:` section of `ceph -s`, `ceph df` and `ceph fs status` are
answered from it — with no active MGR the cluster still serves I/O, but
those numbers freeze and health complains. It also hosts the Python
modules: the PG autoscaler, the balancer, progress bars, the dashboard,
the Prometheus exporter, and the orchestrator API that cephadm plugs
into (absent here, which is why Section 5.2 creates CephFS pools by
hand instead of using `ceph fs volume create`). Production runs one
active MGR plus standbys.

The cluster is now alive and empty: `ceph -s` reports a one-member
quorum, an active manager, `0 osds: 0 up, 0 in`. Two daemons on one
machine are a Ceph cluster; there is just nowhere to put anything yet.

## 3.5 A second monitor joins

The difference between bootstrapping a monitor and adding one is the
whole lesson: **a joining monitor is built from the running cluster's
monmap, not a new one.**

```
[c21]# ceph mon getmap -o /tmp/monmap                                 (1)
[c21]# ceph auth get mon.                                             (2)
[mon.]
	key = <the shared mon. secret>
	caps mon = "allow *"
        ... copy both files to c22 ...

[c22]# install -d -o ceph -g ceph /var/lib/ceph/mon/ceph-c22
[c22]# sudo -u ceph ceph-mon --mkfs -i c22 \
           --monmap /tmp/monmap --keyring /tmp/ceph.mon.keyring       (3)
[c22]# systemctl enable --now ceph-mon@c22
```

1. Not `monmaptool --create`. The live monmap already carries the fsid,
   the existing member and its v2/v1 addresses, so the new monitor
   knows who to contact and joins the quorum on start. This is also why
   only the first monitor can be missing its msgr2 address.
2. All monitors share the single `mon.` key from 3.2 — it is how they
   authenticate to *each other*, so a joining monitor gets a copy of it
   rather than an identity of its own. It is the one principal in the
   cluster that is not per-daemon.
3. Same mkfs as before, same `ceph` user, same reasons.

Once quorum has two members, every host's `ceph.conf` needs the new
`mon host` line (Section 3.8), or its daemons will keep dialling a
one-member list.

## 3.6 Sixteen OSDs

An OSD host is given the weak `client.bootstrap-osd` key from 3.2 and
nothing else:

```
[c23]# install -d -m 750 -o ceph -g ceph /var/lib/ceph/bootstrap-osd
        ... copy client.bootstrap-osd's keyring here, mode 600 ...
```

Then one command per device does everything:

```
[c23]# ceph-volume lvm create --data /dev/vdb
[c23]# ceph-volume lvm create --data /dev/sda
[c23]# ceph-volume lvm create --data /dev/sdb
[c23]# ceph-volume lvm create --data /dev/nvme0n1
```

That single invocation, per disk:

1. creates an LVM volume group and one logical volume spanning the
   device, tagged with the cluster fsid and the OSD's uuid;
2. asks the monitor — authenticating as `client.bootstrap-osd` — for
   the next free OSD id and registers a freshly generated cephx key for
   it;
3. writes the BlueStore label onto the volume and formats it
   (Section 6.4 reads that label back);
4. creates `/var/lib/ceph/osd/ceph-N` with the identity markers and the
   `block` symlink;
5. adds the OSD to the CRUSH map under this host, with a weight derived
   from its capacity and a class derived from `rotational`;
6. enables `ceph-osd@N` and starts it.

Two things to know when scripting this. The host's CRUSH bucket does
not appear in `ceph osd tree` until its *first* OSD reports in, so a
host looks absent for a while despite the command succeeding. And
`ceph-volume` returns once the daemon is started, but an OSD takes
another 25–35 seconds to boot into the osdmap — "the command printed
success" and "the OSD is up" are half a minute apart. Poll `ceph osd
stat`.

After all four storage hosts:

```
[c21]# ceph osd tree

 -1         0.09424  root default                                     (1)
 -3         0.02356      host c22

## 3.7 Two MDS daemons

```
[c21]# ceph auth get-or-create mds.c21 \
           mon 'profile mds' mgr 'profile mds' mds 'allow *' osd 'allow *'
[c21]# install -d -o ceph -g ceph /var/lib/ceph/mds/ceph-c21
[c21]# ceph auth get mds.c21 > /var/lib/ceph/mds/ceph-c21/keyring
[c21]# chown ceph:ceph /var/lib/ceph/mds/ceph-c21/keyring
[c21]# chmod 600 /var/lib/ceph/mds/ceph-c21/keyring
[c21]# systemctl enable --now ceph-mds@c21
        ... and the same on c25 ...
```

`profile mds` rather than `allow *` on mon and mgr: the profile grants
exactly what an MDS needs — notably the right to add itself to the MDS
map — and nothing else.

Both daemons come up in **standby** and stay there, because there is no
filesystem yet. Not a failure state: an MDS holds no durable data of
its own, so starting one costs and moves nothing. `ceph fs new`
(Section 5.2) promotes one to serve rank 0 — which is why that command
appears to conjure a metadata server out of nowhere.

## 3.8 What you maintain by hand

Without an orchestrator there is no reconciliation loop, and exactly
one piece of state has to be pushed around by hand: **`mon host` in
`/etc/ceph/ceph.conf`, on every host, whenever the monitor set
changes**. A host left with a stale list cannot find quorum, and the
symptom — daemons that start and then hang — names nothing useful. So
after each monitor is added, the file is regenerated from the live
`ceph mon dump` and written to every member:

```
[global]
fsid = 8830b0e0-0d9f-4729-b01d-73c5dcda498e
mon initial members = c21                                          (1)
mon host = 10.0.0.21,10.0.0.22                                     (2)
public network = 10.0.0.0/24
auth cluster required = cephx
auth service required = cephx
auth client required = cephx
osd memory target = 1073741824
```

1. Still pinned to the bootstrap set, as in 3.1.
2. Now both monitors.

The other manual step is credential distribution, worth being
deliberate about: the admin keyring goes only to hosts meant to
administer the cluster. `c21` and `c22` have it. `c23`, `c24` and `c25`
store and serve real user data — each is primary for a share of the
PGs — and hold no admin credential at all. Section 4.3 shows the
difference on disk.

Two habits this teaches. `systemctl enable --now` returns when systemd
has *forked* the daemon, not when the daemon has registered with the
cluster, so an MDS that never joins looks exactly like success. And
"the command printed success" is not "the state is correct": check
`ceph -s`, `ceph osd stat`, `ceph node ls` afterwards. Doing this for
you is the entire job of cephadm's orchestrator.

## 4.2 The maps

Each map has an **epoch** that bumps on every change. The **monmap**
first, the one map that must be known before anything else can be
learned:

```
[c21]# ceph mon dump
epoch 2
fsid 8830b0e0-0d9f-4729-b01d-73c5dcda498e
last_changed 2026-07-28T03:43:07.068818+0000
created 2026-07-28T03:43:03.174021+0000
min_mon_release 20 (tentacle)
election_strategy: 1
0: [v2:10.0.0.21:3300/0,v1:10.0.0.21:6789/0] mon.c21                    (1)
1: [v2:10.0.0.22:3300/0,v1:10.0.0.22:6789/0] mon.c22                    (2)
```

1. Both addresses, as Section 3.3 insisted: **msgr2** (`v2:`, port
   3300, the modern protocol with framing and CRC or AES-GCM modes) and
   legacy **msgr1** (`v1:`, port 6789). Clients prefer v2 and fall back.
2. Epoch 2 — the map changed once, when `mon.c22` joined.

Device classes cost nothing at placement time, and the implementation
is why. CRUSH does not filter by class while computing; the monitor
maintains a **shadow tree per class**, and a class-aware rule starts
from a different root:

```
[c21]# ceph osd crush tree --show-shadow
ID   CLASS  WEIGHT   TYPE NAME
 -6    ssd  0.02356  root default~ssd                                   (1)
 -5    ssd  0.00589      host c22~ssd
  3    ssd  0.00589          osd.3
 -9    ssd  0.00589      host c23~ssd
  7    ssd  0.00589          osd.7
-12    ssd  0.00589      host c24~ssd
 11    ssd  0.00589          osd.11
-15    ssd  0.00589      host c25~ssd
 15    ssd  0.00589          osd.15
 -2    hdd  0.07068  root default~hdd                                   (2)
 -4    hdd  0.01767      host c22~hdd
  0    hdd  0.00589          osd.0
  1    hdd  0.00589          osd.1
  2    hdd  0.00589          osd.2
  ...
 -1         0.09424  root default                                       (3)
  ...
```

1. `default~ssd` is a synthetic root holding only the SSD-class OSDs,
   with the same host structure — so a rule over it still spreads
   replicas across four machines.
2. Likewise `default~hdd`, with three devices per host.
3. The real tree, unchanged, for rules that do not care.

The rules themselves are tiny programs. Two are added here, one per
class:

```
[c21]# ceph osd crush rule create-replicated hdd-rule default host hdd
[c21]# ceph osd crush rule create-replicated ssd-rule default host ssd
[c21]# ceph osd crush rule ls
replicated_rule
hdd-rule
ssd-rule
[c21]# ceph osd crush rule dump ssd-rule
{
    "rule_id": 2,
    "rule_name": "ssd-rule",
    "type": 1,
    "steps": [
        { "op": "take", "item": -6, "item_name": "default~ssd" },       (1)
        { "op": "chooseleaf_firstn", "num": 0, "type": "host" },        (2)
        { "op": "emit" }
    ]
}
```

1. `take` the shadow root — the entirety of "only use SSDs".
2. `chooseleaf_firstn 0 type host`: pick as many hosts as the pool's
   `size` requires, one leaf OSD from each. **This is the failure
   domain**, and it is why a pool with `size 3` on this cluster
   survives losing any one machine. On a single-host cluster this must
   be lowered to `type osd`, which quietly gives up that property.

Finally, the **config store**. Modern Ceph keeps most configuration in
the monitor rather than `ceph.conf`, so changing an option does not
mean touching every host:

```
[c21]# ceph config dump
WHO             MASK  LEVEL     OPTION                                 VALUE            RO
mon                   advanced  auth_allow_insecure_global_id_reclaim  false
osd.3                 basic     osd_mclock_max_capacity_iops_ssd       10209.030373
osd.7                 basic     osd_mclock_max_capacity_iops_ssd       11026.548956
osd.11                basic     osd_mclock_max_capacity_iops_ssd       6224.827446
osd.15                basic     osd_mclock_max_capacity_iops_ssd       11231.329389
client.rgw.c21        basic     rgw_frontends                          beast port=8000  *
```

The `osd_mclock_max_capacity_iops_ssd` entries were not set by hand:
each SSD-class OSD benchmarks itself on first start and stores the
result, which the mClock QoS scheduler uses to divide throughput
between client I/O and background work like recovery and scrub.
Daemons write to the config store too, not just admins. One practical
consequence: OSD ids are reused, so purging an OSD without clearing its
config section leaves a measured capacity the *next* osd.N silently
inherits.

1. `profile mds` and `allow profile osd` are the same construct written
   two ways — the bare form is what Section 3.7 typed, the `allow`
   prefix is what `ceph-volume` emits. Both parse identically.
2. `client.admin` is the superuser. **Treat its keyring like a root SSH

   `-mds`, `-mgr`, `-rgw`, `-rbd` and `-rbd-mirror` exist here despite

   monitor, `rwx` on OSDs, no admin rights.

What does `c23` actually hold? Ask the PG map rather than guessing:

```
[c21]# ceph pg dump pgs_brief --format=json | python3 -c '

pgs = json.load(sys.stdin)["pg_stats"]
c23 = {4,5,6,7}
print("total PGs           :", len(pgs))

1. Not all 87. With `size 3` and a failure domain of `host`, CRUSH
   picks **three of the four** storage hosts for each PG — so every
   host sits out roughly a quarter of them. No single machine in this
   cluster holds a copy of everything, which is rather the point.
2. And for 24 PGs `c23` is not a passive copy but the **primary**:
   clients send their reads and writes for those straight to it, and it
   is the OSD that orders the write and replicates onward. "Storage
   node" does not mean "backup node".

That machine nonetheless has **no admin keyring at all**. Its daemons
authenticate with their own per-OSD keys, kept beside their data:

```
[c23]# cat /var/lib/ceph/osd/ceph-4/keyring
[osd.4]
key = <osd.4's secret>

[c23]# ls -l /var/lib/ceph/bootstrap-osd/
-rw------- 1 ceph ceph 129 Jul 28 03:43 ceph.keyring                    (1)
```

1. The only other credential the host ever received — the weak
   bootstrap key of Section 3.6.

That is least privilege made concrete: compromising `c23` yields "the
ability to be `osd.4`–`osd.7`", never "the ability to be admin".

Two commonly misread properties of keyrings. A keyring is **not
authorization**: the `caps` lines in a keyring file are a cached,
human-readable note, and the monitor's database alone decides what a
principal may do. And it is **not state**: lose a daemon's keyring and
its data is intact — the daemon just cannot log in until an admin
re-exports the key with `ceph auth get osd.4`.

Under `/var/lib/ceph`, each role gets a directory named

Apart from sixteen block devices, this cluster is a handful of INI
files, tiny text markers and two kinds of RocksDB. Your *data* appears
in none of those paths; it exists only inside the OSDs' volumes.

## 4.5 How a client finds its data

A client bootstraps the way Section 3.1's config file implies: read
`mon host`, connect, complete the cephx handshake with the keyring,
receive the current **monmap**. A stale address list repairs itself as
long as one listed monitor answers. (Modern Ceph can also discover
monitors via DNS SRV records, making the file optional.)

The client then subscribes to the **osdmap**, which carries the OSD
list and the CRUSH map. From then on, locating an object is pure local
computation — no network lookup, ever:

1. **Hash the object name.** The name is the only input; nothing about
   the file, image or bucket it came from matters.
   `hash("rbd_data.626e2b7e024e.0000000000000000") = 0x9d9d67ac`
2. **Mask to a PG.** The hash is reduced modulo the pool's PG count
   (a power of two, so it is a mask): with 32 PGs,
   `0x9d9d67ac & 0x1f = 0x0c` → PG `14.c` in pool 14.
3. **Run CRUSH.** Feed the PG id and the current CRUSH map to the
   algorithm; out comes a deterministic, ordered list of OSDs.
   `CRUSH(14.c, map, hdd-rule) = [9, 13, 2]`

Because the name is the only input to placement, an object name must be
unique within its pool; two objects with the same name in different
pools are unrelated.

The list is ordered, and the first entry is the **primary** — the OSD
the client talks to. (Reads can be pointed at a replica instead; writes
never are, since the primary is what orders them.) So this object's I/O
is destined for `osd.9`.

But `9` is an **integer**, and you cannot open a TCP connection to an
integer. So there is a fourth step, and it is the osdmap's other job:
the same map that feeds CRUSH is also the `osd id → address` table.

```
[c21]# ceph osd find 9
{
    "osd": 9,
    "addrs": {
        "addrvec": [
            { "type": "v2", "addr": "10.0.0.24:6815", "nonce": 1589244358 },  (1)
            { "type": "v1", "addr": "10.0.0.24:6818", "nonce": 1589244358 }
        ]
    },
    "osd_fsid": "9398eea9-6ba2-490d-b664-cda03a075324",
    "host": "c24",
    "crush_location": { "host": "c24", "root": "default" }                    (2)
}
```

1. There is the resolution the client needed: **`osd.9` →
   `10.0.0.24:6815`** over msgr2, or `:6818` for a legacy client. The
   **nonce** distinguishes this incarnation of the daemon from a
   restarted one at the same address.
2. And its place in the CRUSH tree, which is what let CRUSH pick it in
   the first place.

Note what the client did *not* do: no name service, no lookup RPC, no
broker. The address table arrived once with the map and refreshes only
when the map changes. That is why the osdmap is worth distributing to
every client — it collapses discovery and placement into one cached
object.

## 4.6 How a client talks to an OSD

Nothing in Section 4.5 needs a kernel. The ordinary Ceph client is a
**userspace library**, `librados` — what RGW is built on, what QEMU
links against to give a VM a virtual disk, and what the `rados` CLI is.
krbd and the CephFS kernel client are a *second*, independent
implementation of the same protocol that happens to live in the kernel.

So watch a client work with no kernel Ceph code in the picture: fetch
the object this post traces, with the messenger's log level raised.

```

1. It dials **both** monitors from `mon host` at once and races them —
   `--2-` is msgr2. These two addresses are the only thing the client
   knew when it started.
2. `10.0.0.21:0/2081066956` is the client's `entity_addr_t`: address,
   port 0 because it is not listening, and a random **nonce** so two
   clients on one host are never confused. It then *subscribes* rather
   than polls — the monitor pushes updates for the life of the session.
3. `(secure 0 0 0)` is the connection mode: this one is **encrypted**,
   while the OSD reply at the bottom is `(crc 0 0 0)`, checksummed
   only. That split is the default — Ceph secures traffic to monitors
   and CRC-protects the rest (Section 7.3).
4. 13 KB carrying the OSD list, their addresses and the CRUSH map.
   `198..198 src has 1..198` — the client asked for the latest and got
   epoch 198; the monitor advertises that it can supply the history
   back to epoch 1 for anyone needing incrementals.
5. **The whole point.** Having received the map, the client computed
   `14.c → [9,13,2]`, resolved `osd.9` to `10.0.0.24:6815` and
   connected *directly* — over ordinary TCP, to one of the ports OSDs
   bind upward from 6800. It never asked anybody where the object was.
   No lookup message appears in this trace because none exists.
6. The read request itself, dissected next.

**The request.** That `osd_op(...)` line is the entire client/OSD
interface — not a byte range on a device, but a small structured
message against a named object:

| Field | Meaning |
|-------|---------|
| `unknown.0.0:1` | entity name, client incarnation, transaction id. `unknown` only because msgr2 leaves the sender's name off the wire; the receiver stamps it, which is why the OSD side prints `client.25226` below |
| `14.c` | the target PG, exactly as the client computed it in 4.5 |
| `14:35e6b9b9:::...:head` | the object's full identity: pool, hash, namespace, key, name, snapshot. The hash is 4.5's `0x9d9d67ac` with its bits reversed, which is the order objects are stored in |
| `[read 0~4194304]` | the **op vector** — offset and length here, but a vector because one request can carry several operations applied atomically to the object |
| `ondisk+read+known_if_redirected+supports_pool_eio` | flags |
| `e198` | the osdmap epoch the client used |

That last field is the safety interlock that makes client-side
placement workable. If the sender is behind,
`OSDService::maybe_share_map` pushes the missing incremental maps down
the same connection — nobody polls for map updates, they ride along
with ordinary traffic. If the op is *misdirected*, because this OSD is
not the primary for that PG under the current map,
`PrimaryLogPG::do_op` simply returns: no error reply, no redirect, op
dropped. The client resends, having just been handed the newer map. A
stale client corrupts nothing and needs no error path — it computes, is
corrected, and computes again.

**The server side.** Every OSD keeps a ring of recently completed
operations, stamped per stage. This is introspection rather than
interface — nothing reads it back to make a decision — though not free:
op tracking is on by default. Here is the same object being written,
caught mid-`dd`, with the event list abridged:

```
[c24]# ceph daemon osd.9 dump_historic_ops
{
    "description": "osd_op(client.25226.0:8331 14.c
                    14:35e6b9b9:::rbd_data.626e2b7e024e.0000000000000000:head
                    [write 131072~1048576] snapc 0=[]
                    ondisk+write+known_if_redirected e198)",
    "duration": 0.034185965,
    "type_data": {
        "events": [
   { "event": "initiated",                    "duration": 0        },
   { "event": "started",                      "duration": 0.000092 },
   { "event": "waiting for subops from 2,13", "duration": 0.000127 },   (1)
   { "event": "op_commit",                    "duration": 0.020310 },   (2)
   { "event": "sub_op_commit_rec",            "duration": 0.005190 },   (3)
   { "event": "sub_op_commit_rec",            "duration": 0.004174 },
   { "event": "commit_sent",                  "duration": 0.000017 },   (4)
   { "event": "done",                         "duration": 0.000020 }
        ]
    }
}
```

Each `duration` is the gap from the previous event.

1. **The replication.** osd.9 does not answer the client yet; it
   forwards the operation to osd.2 and osd.13 and waits.
2. Its own BlueStore transaction commits — 20 ms, by far the largest
   interval in the op.
3. The two replicas report their commits, 5.2 ms and 4.2 ms later.
4. **17 microseconds after the last of them**, the client is answered.

A write is acknowledged once *every* copy is durable, not once the
primary is — proof of a claim Section 6.1 only asserts. Be exact about
"every": `ReplicatedBackend::submit_transaction` waits on the acting
set *plus* any OSD currently being backfilled onto, so a shard midway
through receiving this PG does not finish already stale. `min_size`
never enters it — that decides whether the PG serves I/O at all
(Section 6.3), not how many commits an ack waits for. The slowest copy
sets the latency, which is why one sick disk drags a whole pool down
and why a cluster feels slower while backfilling.

# 5. Hands-on: the three interfaces

## 5.1 Block: RBD

RBD presents a virtual disk striped, 4 MiB at a time, over RADOS
objects. Create a pool for it — on the HDD class, since block storage
is the bulk consumer here — then an image:

```
[c21]# ceph osd pool create rbd 32 32 replicated hdd-rule               (1)
pool 'rbd' created
[c21]# rbd pool init rbd                                                (2)
[c21]# rbd create rbd/vol0 --size 4G                                    (3)
[c21]# rbd info rbd/vol0
rbd image 'vol0':
	size 4 GiB in 1024 objects                                      (4)
	order 22 (4 MiB objects)
	snapshot_count: 0
	id: 626e2b7e024e
	block_name_prefix: rbd_data.626e2b7e024e                        (5)
	format: 2
	features: layering, exclusive-lock, object-map, fast-diff,
	          deep-flatten
	create_timestamp: Tue Jul 28 13:32:32 2026
```

1. 32 PGs, replicated, using the class-aware rule from Section 4.2.
   The pool inherits the cluster defaults `size 3` and `min_size 2`:
   three copies, and I/O continues while at least two are available.
2. Stamps the pool with the `rbd` application tag; Ceph refuses I/O to
   untagged pools to catch pool-name typos.
3. Creating a 4 GiB image is instant — RBD is thin-provisioned. Only a
   small header object exists now; data objects appear on first write.
4. 4 GiB / 4 MiB = 1024 *potential* data objects.
5. **Remember this prefix.** Every data object of this image is named
   `rbd_data.626e2b7e024e.<16-hex-digit object index>` — the handle
   the trace in Section 6 hangs on.

Map it through the kernel RBD driver and use it like any disk:

```
[c21]# rbd map rbd/vol0
/dev/rbd0
[c21]# mkfs.xfs -q /dev/rbd0
[c21]# mount /dev/rbd0 /mnt/vol0
[c21]# echo 'hello from rbd' > /mnt/vol0/hello.txt
[c21]# sync
```

`rbd map` talks to `drivers/block/rbd.c`, which speaks the RADOS
protocol directly (`net/ceph/`) — no userspace daemon, no gateway in
the I/O path. Since `c21` holds no OSDs, every one of those writes
crossed the network to three storage nodes before `sync` returned.

The lazily created data objects are now visible:

```
[c21]# rados -p rbd ls | sort | head -6
rbd_data.626e2b7e024e.0000000000000000                                  (1)
rbd_data.626e2b7e024e.000000000000007f                                  (2)
rbd_data.626e2b7e024e.00000000000000ff
rbd_data.626e2b7e024e.000000000000017f
rbd_data.626e2b7e024e.00000000000001ff
rbd_data.626e2b7e024e.0000000000000200
[c21]# rados -p rbd ls | wc -l
16
```

1. Object index 0 covers image bytes 0–4 MiB: the XFS superblock, the
   first allocation group's metadata — and our file's data.
2. The scattered indexes (`0x7f` = image bytes 508–512 MiB, etc.) are
   XFS metadata that mkfs placed near its allocation-group boundaries.
   Sixteen objects exist out of a possible 1024; everything mkfs and
   the file write did not touch **simply does not exist** — thin
   provisioning at the object level.

Which object holds `hello.txt`? Ask XFS where the file's data landed
in the image:

```
[c21]# xfs_bmap -v /mnt/vol0/hello.txt
/mnt/vol0/hello.txt:
 EXT: FILE-OFFSET  BLOCK-RANGE  AG AG-OFFSET  TOTAL FLAGS
   0: [0..7]:      104..111      0 (104..111)     8 001111
```

Sector 104 × 512 = byte offset 53248 — inside the first 4 MiB, so the
file's bytes live in object `rbd_data.626e2b7e024e.0000000000000000`:

```
[c21]# rados -p rbd stat rbd_data.626e2b7e024e.0000000000000000
rbd/rbd_data.626e2b7e024e.0000000000000000
    mtime 2026-07-28T13:33:00.000000+0000, size 131072                  (1)
```

1. The object's logical size is 128 KiB, not 4 MiB: XFS has only
   written the first 128 KiB of this 4 MiB stripe so far. Thin at the
   image level, thin inside each object too.

## 5.2 File: CephFS

CephFS needs two pools — data and metadata — and an MDS serving the
metadata. Device classes earn their keep here: metadata is small,
latency-critical and heavily updated, so it goes on the fast class;
file data on the slow one.

```
[c21]# ceph osd pool create cephfs.fs1.meta 16 16 replicated ssd-rule
pool 'cephfs.fs1.meta' created
[c21]# ceph osd pool create cephfs.fs1.data 32 32 replicated hdd-rule
pool 'cephfs.fs1.data' created
[c21]# ceph fs new fs1 cephfs.fs1.meta cephfs.fs1.data
new fs with metadata pool 15 and data pool 16
[c21]# ceph fs status fs1
fs1 - 0 clients
===
RANK  STATE   MDS     ACTIVITY     DNS    INOS   DIRS   CAPS
 0    active  c21  Reqs:    0 /s    10     13     12      0             (1)
      POOL         TYPE     USED  AVAIL
cephfs.fs1.meta  metadata   125k  7715M                                 (2)
cephfs.fs1.data    data       0   22.1G
STANDBY MDS
    c25                                                                 (3)
```

1. `ceph fs new` promoted one of the two standbys from Section 3.7 to
   serve rank 0. Nothing was started here.
2. The proof that the class rules took effect: the metadata pool sees
   **7.7 GiB** available and the data pool **22 GiB**, because they are
   drawing from four SSD-class devices and twelve HDD-class devices
   respectively. Same cluster, same hosts, different media.
3. The other MDS stands by. Ceph's MDS is active/standby per rank:
   only one daemon owns rank 0 at a time.

Mount it with the kernel client (`fs/ceph/`). The device string names
the user, the cluster fsid and the filesystem; the options carry the
monitor addresses and the secret:

```
[c21]# mount -t ceph \
    admin@8830b0e0-0d9f-4729-b01d-73c5dcda498e.fs1=/ /mnt/fs1 \
    -o mon_addr=10.0.0.21:3300/10.0.0.22:3300,secret=<admin key>,ms_mode=prefer-crc
[c21]# echo 'hello from cephfs' > /mnt/fs1/hello.txt
[c21]# sync
```

Both monitor addresses are listed, so the mount survives one of them
being unreachable at mount time. (`mount.ceph` can also pull all of
this from `/etc/ceph/` instead of the command line.)

The division of labour: the kernel client asks the **MDS** for metadata
operations — lookup, create, permissions, capability leases — while
file *data* goes directly to OSDs, striped into 4 MiB objects named
`<inode number in hex>.<stripe index>`:

```
[c21]# ls -i /mnt/fs1/hello.txt
1099511627776 /mnt/fs1/hello.txt                                        (1)
[c21]# rados -p cephfs.fs1.data ls
10000000000.00000000                                                    (2)
[c21]# ceph osd map cephfs.fs1.data 10000000000.00000000
osdmap e186 pool 'cephfs.fs1.data' (16) object '10000000000.00000000'
  -> pg 16.f0b56f30 (16.10) -> up ([9,6,1], p9) acting ([9,6,1], p9)    (3)
```

1. `1099511627776` = `0x10000000000` — CephFS inode numbers for user
   files start there.
2. The file's first (and only) stripe object: inode in hex, dot,
   stripe index.
3. Placed by exactly the same machinery as the RBD object — hosts
   `c24`, `c23`, `c22`. The tracing recipe of Section 6 applies
   verbatim.

Since there is a standby, it is worth making it work. `ceph mds fail`
evicts the active daemon the way a crashed host would:

```
[c21]# ceph mds fail c21
failed mds gid 24922
[c21]# ceph fs status fs1
fs1 - 1 clients
===
RANK  STATE   MDS     ACTIVITY     DNS    INOS   DIRS   CAPS
 0    active  c25  Reqs:    0 /s    11     14     12      1             (1)
      POOL         TYPE     USED  AVAIL
cephfs.fs1.meta  metadata   178k  7714M
cephfs.fs1.data    data    12.0k  22.1G
STANDBY MDS
    c21                                                                 (2)
[c21]# cat /mnt/fs1/hello.txt
hello from cephfs                                                       (3)
```

1. The standby on `c25` took over rank 0 within seconds.
2. The restarted daemon on `c21` re-registered as the new standby.
3. **The mount never broke.** The kernel client reconnected to the new
   MDS and replayed its outstanding state — for the reason Section 3.7
   gave: an MDS holds no durable state of its own. The directory tree
   and inodes live in `cephfs.fs1.meta`, a normal RADOS pool; the daemon
   is a cache and lock manager over it. Failover is another daemon
   taking the lock and replaying the journal.

# 6. Under the hood: from user file to raw disk bytes

Take `/mnt/vol0/hello.txt` from Section 5.1 and follow its bytes down,
across the network, onto a named machine's disk. The chain:

```
file → XFS → /dev/rbd0 byte 53248 → object rbd_data.…0000 →
PG 14.c → osd.9 (host c24) → BlueStore → device offset 151330816
```

## 6.1 Step 1: object name → PG → OSDs

`ceph osd map` answers "where does this object live?" — and it answers
*without contacting any OSD*, because placement is computed, not
looked up:

```
[c21]# ceph osd map rbd rbd_data.626e2b7e024e.0000000000000000
osdmap e186 pool 'rbd' (14)
  object 'rbd_data.626e2b7e024e.0000000000000000'
  -> pg 14.9d9d67ac (14.c)                                              (1)
  -> up ([9,13,2], p9) acting ([9,13,2], p9)                            (2)
```

1. The object *name* hashes to `0x9d9d67ac`. The pool has 32 PGs, so
   the hash is masked to 5 bits: `0x9d9d67ac & 0x1f = 0x0c` — PG `14.c`
   ("pool 14, PG 0x0c"). Every object hashing into this bucket shares
   the PG's placement and fate. (Pool ids here start at 14 because
   earlier experiments created and destroyed pools; ids are never
   reused.)
2. CRUSH maps PG `14.c` onto OSDs `[9, 13, 2]` — three replicas per the
   pool's `size 3`. `p9` marks **osd.9 as the primary**: all client I/O
   for this PG goes to osd.9, which replicates to 13 and 2 and acks
   only after all three have the write persisted. `up` equal to
   `acting` means nothing is recovering.

**There is no such thing as a "replica OSD".** Primary is a property of
the *pair* (PG, OSD), not of the OSD: it is position 0 in that PG's
acting set, and every OSD is position 0 for some PGs and position 1 or
2 for others. Anyone arriving from RAID or primary/secondary databases
expects otherwise:

```
[c21]# ceph pg dump pgs_brief --format=json | python3 -c '
import json,sys,collections
pgs = json.load(sys.stdin)["pg_stats"]
prim, rep = collections.Counter(), collections.Counter()
for p in pgs:
    prim[p["acting"][0]] += 1
    for o in p["acting"][1:]: rep[o] += 1
for o in sorted(prim | rep):
    print(f"osd.{o:<3} primary for {prim[o]:3}   replica for {rep[o]:3}")'
osd.0   primary for   7   replica for  11
osd.1   primary for   9   replica for  13
osd.2   primary for   6   replica for  13                               (1)
...
osd.9   primary for   8   replica for  14                               (2)
...
osd.13  primary for   7   replica for  11                               (3)
```

1. `osd.2` was a plain replica for PG 14.c above — and is primary for
   six other PGs.
2. `osd.9` leads 8 PGs and follows in 14.
3. Likewise `osd.13`, which Section 6.3 will watch *become* primary for
   14.c the instant osd.9 goes down — no reconfiguration, just the
   acting set losing its head and the next entry inheriting the role.

No OSD is exclusively primary or exclusively replica, deliberately: the
primary serves every read and orders every write for its PG, so
primaries clustered on a few OSDs would put the cluster's whole load on
those disks. Spreading PGs spreads the primary role with them, which is
what makes a Ceph cluster scale by adding disks. (`ceph osd
primary-affinity` biases this; `read_balance_score` in `ceph osd pool
ls detail` reports how evenly it worked out.)

The payoff of a multi-node cluster is asking *where those OSDs are*:

```
[c21]# for i in 9 13 2; do ceph osd find $i \
         | python3 -c 'import json,sys; d=json.load(sys.stdin); print("osd.%s  %s" % (d["osd"], d["host"]))'; done
osd.9   c24
osd.13  c25
osd.2   c22
```

Three copies on three distinct machines — not because anything told
CRUSH so for this object, but because `hdd-rule` says `chooseleaf ...
type host` and the CRUSH tree from Section 3.6 groups OSDs under hosts.
Lose `c24` entirely and this PG keeps serving from `c25` and `c22`.

Placement is a pure function of (PG, CRUSH map, rule) — ask again at a
later epoch and the answer is identical. Any client holding the current
map computes the same result. When the map changes, the function's
output changes, and exactly the affected PGs migrate. The
implementation lives in [`src/crush/`][src-crush].

## 6.3 Step 3: open the primary OSD's BlueStore offline

`ceph-objectstore-tool` opens a **stopped** OSD's BlueStore to list,
dump and extract objects. So stop `osd.9`, on `c24`, the machine CRUSH
named. Safe here: two replicas remain, one takes over as primary, and
`min_size 2` is still satisfied.

First, tell the cluster not to start rebalancing during the exercise:

```
[c21]# ceph osd set noout                                               (1)
noout is set
[c24]# systemctl stop ceph-osd@9
```

1. Without `noout`, the monitor marks a down OSD *out* after
   `mon_osd_down_out_interval` (600 s by default) and CRUSH immediately
   re-places every PG that lived on it — the cluster would start
   copying data to restore the third replica. `noout` is the standard
   flag for planned maintenance: the OSD stays *in* the map, so nothing
   moves.

The cluster notices within seconds:

```
[c21]# ceph -s
  cluster:
    health: HEALTH_WARN
            13 OSD(s) experiencing slow operations in BlueStore
            noout flag(s) set
            1 osds down
            Degraded data redundancy: 18/849 objects degraded (2.120%),
                7 pgs degraded
  services:
    osd: 16 osds: 15 up (since 20s), 16 in (since 10h)
         flags noout
  data:
    pgs:     18/849 objects degraded (2.120%)
             65 active+clean
             15 active+undersized
             7  active+undersized+degraded

[c21]# ceph pg ls | grep '^14.c '
PG    OBJECTS DEGRADED ... STATE                      VERSION ... UP        ACTING
14.c        1        1 ... active+undersized+degraded  186'31 ... [13,2]p13 [13,2]p13   (1)
```

1. Read the state names precisely, because they mean different things.
   **active** — still serving reads and writes. **undersized** — the
   acting set has 2 members where the pool wants 3. **degraded** — at
   least one object has fewer copies than it should. And `p13`: osd.13
   on `c25` was promoted to primary the moment osd.9 went away. Client
   I/O never stopped; it started going to a different machine. Note
   also `849 = 283 × 3`: the "objects degraded" percentage counts
   *replicas*, not objects.

Now open the stopped OSD's store directly:

```
[c24]# ceph-objectstore-tool --data-path /var/lib/ceph/osd/ceph-9 --op list \
         | grep 626e2b7e024e.0000000000000000

# 7. Under the hood: authentication, from Kerberos to cephx

Section 3.2 used cephx and stated the rules; this section explains
where those rules come from.

## 7.1 Why a storage cluster needs its own auth

Every daemon in this post listens on plain TCP and speaks the RADOS
protocol; clients connect straight to OSDs on four different machines.
Without authentication, anyone who can reach `10.0.0.0/24` could claim
to be `client.admin`, enroll a rogue OSD (and have the cluster
helpfully *replicate data to it*), or replay captured writes. So the
requirements are:

- **Mutual authentication** — daemons verify clients *and* each other;
  a rogue OSD must be rejected just like a rogue client.
- **Authorization** — different principals get different rights (the
  cap strings and profiles of Sections 3.2 and 4.3).
- **No authority on the data path** — Section 6.1 showed placement is
  computed client-side precisely to avoid a central lookup server; auth
  must not sneak one back in as a per-I/O "may I?" service.
- **Secrets never cross the wire** — the network is untrusted.

An old problem shape — many clients, many services, one trusted
authority, hostile network — that MIT solved in the 1980s.

## 7.2 The Kerberos idea in one diagram

[Kerberos][kerberos] assumes a Key Distribution Center (KDC) that
shares a secret with every principal. Nobody ever sends a secret over
the wire — not even hashed. Instead, the KDC answers a *plaintext*
request with **two sealed boxes carrying the same freshly-minted
session key**, one openable by the client, one by the service:

```
 +--------+ (1) "alice here: a ticket    +----------+
 |        |      for service S, please"  |   KDC    |
 |        | ---------------------------> | all keys |
 | client | (2) reply: two sealed boxes  +----------+
 |        | <---------------------------
 |        |  [session key]                sealed with ALICE's key
 |        |      -> only she can open it: that IS the login
 |        |  [alice, session key, expiry] sealed with S's key
 |        |      -> the TICKET: opaque to her, forwarded as-is
 |        |
 |        | (3) ticket + authenticator   +----------+
 |        |     (encrypted w/ session k) | service  |
 |        | ---------------------------> |    S     |
 |        | (4) S unseals ticket locally +----------+
 |        | <==========================>
 +--------+   both now hold the same session key
```

Box one is sealed with the *client's own* secret, so decrypting it is
simultaneously delivery of the key and proof of identity — an impostor
without alice's secret holds two boxes it cannot open. Box two, the
**ticket**, carries the same session key to the service by a route the
client can neither read nor tamper with. In step (3) the client adds an
*authenticator* — a timestamp encrypted with the session key — proving
it really opened box one. The service unseals the ticket with its own
key, finds the same session key inside, and checks authenticator and
expiry, all **without asking the KDC**. Authenticate once, then talk to
many services directly until expiry forces a background renewal.

## 7.3 cephx: Kerberos re-cast for a storage cluster

cephx keeps the architecture and changes the casting:

| Kerberos | cephx |
|----------|-------|
| KDC | the MON quorum (auth database in the MON's `store.db`) |
| principal + password | principal + keyring file |
| ticket | ticket carrying identity + **caps** + session key |
| service's secret key | *rotating* secret shared by each daemon class |
| authorization data | the cap strings and profiles of Sections 3.2, 4.3 |

```
 client                MON (key authority)              OSDs
   |  (1) handshake: prove  |                             |
   |      client.admin key  |                             |
   | ---------------------> |                             |
   |  (2) tickets + session |                             |
   | <--------------------- |                             |
   |     (sealed with the rotating service secret)        |
   |                        |                             |
   |  (3) I/O request + ticket -------------------------> |
   |      OSD unseals locally: identity, caps, skey       |
   | <=================================================== |
   |      signed traffic — no MON on the data path        |
```

Ceph-specific adaptations worth knowing:

- **Keyrings, not passwords** — a principal's key is a file
  (Section 3.2's `ceph-authtool` output, Section 4.3's tour of where
  they live); daemons authenticate to the MON exactly like clients,
  with keys minted at enrollment time.
- **Rotating service secrets** — cephx's counterpart of the Kerberos
  service key, but minted *per daemon class*: one secret for the OSDs,
  one for the MDSes, one for the MGRs.
  - *Class-wide* is forced by RADOS itself — a client cannot know which
    of the sixteen OSDs it will end up talking to as maps change, so
    the ticket it carries must be unsealable by **any** OSD.
  - *Rotating*, precisely because the key is so widely shared: it turns
    over on the ticket TTL (`auth_service_ticket_ttl`, default one
    hour), daemons holding a small overlapping set (previous / current
    / next) so a rotation or mild clock skew never invalidates a fresh
    ticket.
  - This is *not* the key in a daemon's keyring file — that one is its
    permanent login credential (how `osd.9` authenticates to the MON,
    like any client).
  - The rotating secrets live in exactly two places: authoritatively in
    the MON's auth database (inside the `store.db` of Section 4.4,
    Paxos-committed like every map), and as an in-memory ring on each
    daemon, fetched after login, refreshed before expiry, never written
    to the daemon's disk — so a stolen OSD keyring leaks one login, not
    a durable ticket-unsealing key.
  - Revocation is passive: a deleted principal simply fails its next
    renewal, and no OSD ever needs to be told.
- **Caps ride in the ticket** — authorization is enforced by each
  daemon from the unsealed ticket, no directory consulted per op.
- **Integrity, not secrecy** — cephx authenticates the parties; it does
  not encrypt payloads. Per-message protection is a separate job, done
  by the messenger in `crc` or `secure` mode, and Section 4.6 shows
  both on the wire: by default only traffic to a monitor is encrypted.
  So the tickets described here are handed out over AES-GCM, while the
  I/O they authorize is checksummed and readable.

One knob from Section 4.2's `ceph config dump` belongs here:

```
mon  advanced  auth_allow_insecure_global_id_reclaim  false
```

Every cephx session has a *global id*, and older clients could reclaim
one after reconnecting without re-proving they owned it — so an
attacker who observed a session id could impersonate it. Ceph defaults
to allowing the old behaviour, warning loudly, so ancient clients keep
working. Turning it off is a one-line hardening step once every client
is recent enough.

Seen from here, Section 3's bootstrap ritual is just KDC seeding:
`mon.` is the KDC's own identity, `client.admin` is the first enrolled
principal, `client.bootstrap-osd` is a deliberately narrow enrollment
credential — and every one of the twenty-odd principals in Section
4.3's listing joined afterwards through the front door.

# 8. Next steps for aspiring Ceph developers

## 8.1 From packages to developer builds

This post ran release binaries. For development you want to run code
you just built:

```
git clone https://github.com/ceph/ceph.git && cd ceph
./install-deps.sh                  # dnf-installs build deps on Fedora
./do_cmake.sh -DCMAKE_BUILD_TYPE=RelWithDebInfo
cd build && ninja                  # long; -j to taste
```

Then [`vstart.sh`][vstart] launches a throwaway cluster **from the
build tree** — conceptually exactly what Section 3 did by hand (it
generates a conf, mints the keys, starts the daemons as plain
processes), just automated onto one machine:

```
cd build
MON=1 OSD=3 MDS=1 RGW=1 ../src/vstart.sh -d -n -x
./bin/ceph -s        # note: ./bin/ceph, the freshly built CLI
```

`-n` creates a new cluster, `-d` enables debug output, and the env vars
pick daemon counts — all defaulting sensibly except `RGW`, which
defaults to **0**, so a gateway appears only if you ask. Edit code,
`ninja`, restart: a minutes-long loop. `cstart.sh` does the same with
containers; `mstart.sh` runs several clusters side by side. The
[developer guide][doc-dev] documents the workflow. For production the
tool is [cephadm][doc-cephadm] — same daemons, run as podman containers
under systemd.

One node is enough for most code work but not for everything above:
with all OSDs on one host the CRUSH failure domain must drop to `osd`,
which quietly removes the property Section 6.1 demonstrated. Anything
touching peering, recovery, backfill or CRUSH deserves real hosts — a
handful of VMs like this lab, or `teuthology` at scale.

Section 9 expands this loop into the full developer workflow: the four
environments a change passes through, and how to debug in each.

## 8.2 Where to start reading code

Read upstream's [`doc/architecture.rst`][doc-arch] alongside the tree —
it is this same territory in prose, and it covers the RADOS behaviour
this lab did not exercise: erasure coding, scrubbing, striping
parameters, watch/notify, and RADOS classes.

Guided by the trace in Section 6, each hop has a home in the tree
(refs against [`v20.2.2`][ceph-tag]):

- [`src/crush/`][src-crush] — the placement function; small,
  self-contained, and the best first read. `mapper.c` is where
  `chooseleaf_firstn` actually walks the tree of Section 4.2.
- [`src/osd/`][src-osd] — the OSD: PG state machine, replication,
  recovery. Start at `PrimaryLogPG.cc` for the write path a client op
  takes on a primary (the `version 186'31` in Section 6.3 is its PG log
  at work), and `PeeringState.cc` for how `[9,13,2]` shrank to `[13,2]`
  and grew back.
- [`src/os/bluestore/`][src-bluestore] — the storage engine of
  Section 6.4: onodes, extent maps, blobs and the checksum arrays
  ([companion post][bluestore-post]).
- [`src/librbd/`][src-librbd] — the userspace RBD client (QEMU uses
  this); its kernel twin is [`drivers/block/rbd.c`][krbd].
- [`src/mds/`][src-mds] — the CephFS metadata server, including the
  journal replay that made Section 5.2's failover invisible; kernel
  client in [`fs/ceph/`][kcephfs].
- [`src/rgw/`][src-rgw] — the S3/Swift gateway.
- [`src/auth/`][src-auth] — the cephx protocol from Section 7: the
  MON-side `KeyServer` (mints principals and rotating secrets), the
  daemon-side `RotatingKeyRing`, tickets and the handshake.

If kernel storage is your angle, the client side is a first-class entry
point. `net/ceph/` (the messenger), `drivers/block/rbd.c` and
`fs/ceph/` were all exercised by this lab from an ordinary distro
kernel, and all three are patchable and testable against any cluster
you can reach, including a one-node `vstart.sh`.

`ceph.conf` pointing under `build/`. Everything below follows from
that, and it is why installing Ceph on real nodes is the last step of a
change rather than the first.

> Commands and outputs captured on Fedora 42 (12 cores, 15 GB RAM)

## 9.1 Four environments

| Tier | What runs | Install | Iterate | Use for |
|---|---|---|---|---|
| **0** | BlueStore as a library — gtest, fio engine, offline tools | none | seconds | data structures, allocators, write path, micro-benchmarks |
| **1** | `vstart.sh` — mon/mgr/osd forked from `build/bin`, one host | none | ~1 min | PGs, replication, RADOS clients |
| **2** | `cstart.sh` — real cephadm cluster of containers, one host | image build | ~1 min | orchestrator behaviour |
| **3** | Real nodes, N hosts; teuthology | yes | minutes–hours | performance numbers, multi-node failure, release validation |

## 9.3 Tier 0: no cluster

BlueStore is a library; linking it directly skips mon, PGs and

### The startup warning that sets your device class

File-backed OSDs log three of these at startup, one per device
(`block`, `block.db`, `block.wal`):

```
-1 bdev(0x55e94815a300 .../build/dev/osd2/block.wal) unable to get device
   name for .../build/dev/osd2/block.wal: (22) Invalid argument
```

The cluster reaches `HEALTH_OK` regardless, but the next line of source
is the one that matters
([`KernelDevice.cc:285-296`](https://github.com/ceph/ceph/blob/v21.3.0/src/blk/kernel/KernelDevice.cc#L285)):

```cpp
if ((r = blkdev_buffered.partition(partition, PATH_MAX)) ||
    (r = blkdev_buffered.wholedisk(devname, PATH_MAX))) {
  derr << "unable to get device name for " << path << ": " ... ;
  rotational = true;                      // <-- the fallback
} else {
  rotational      = blkdev_buffered.is_rotational();
  support_discard = blkdev_buffered.support_discard();
  optimal_io_size = blkdev_buffered.get_optimal_io_size();
}
```

Detection does not assume rotational for files; it fails to identify
the device and defaults to rotational. For a non-block file
[`BlkDev::get_devid()`](https://github.com/ceph/ceph/blob/v21.3.0/src/common/blkdev.cc#L110)
returns `st_dev` — the filesystem's device, not the file's — and passes
it to `blkid_devno_to_devname()`. Resolution therefore depends on the
filesystem holding `build/`:

| Build dir on | `st_dev` | Resolves | Result |
|---|---|---|---|
| btrfs (Fedora's default) | `0:34` — anonymous major, no `/dev` node | no | warning, `rotational = true` |
| ext4 / XFS | `253:2` — the real partition | yes | silent, inherits the disk's flags |

btrfs gives each subvolume an anonymous block device, and major 0 has
no node to find:

```console
$ stat -c "%d" build/dev/osd2/block.wal     # build dir on btrfs
34                                          # major 0, minor 34
$ ls /dev/block/0:34
ls: cannot access '/dev/block/0:34': No such file or directory

$ stat -c "%d" /boot/.                      # same box, ext4
64770                                       # major 253, minor 2 = /dev/vda2
```

So the OSD is classified HDD:

```console
$ ./bin/ceph osd metadata 0 | jq '{osd_objectstore, bluestore_bdev_type,
                                   bluestore_min_alloc_size, rotational}'
{
  "osd_objectstore": "bluestore",
  "bluestore_bdev_type": "hdd",
  "bluestore_min_alloc_size": "4096",
  "rotational": "1"
}
```

`min_alloc_size` is 4 K either way at this version
(`bluestore_min_alloc_size_hdd` and `_ssd` are both `4_K`), but
`bluestore_prefer_deferred_size_hdd` is `64_K` against `0` for ssd. The
OSD sends every sub-64 KiB write down the deferred double-write path an
SSD-classified OSD skips — on your NVMe workstation, decided by the
filesystem you cloned onto. Use `--bluestore-devs` with a real device
before concluding anything about the small-write path.

### vstart is not a benchmark

vstart numbers are not measurements: Debug builds, lockdep, all daemons
sharing one host's page cache and CPUs, file-backed devices. Use it for
correctness and code paths; measure in Tier 0 or Tier 3.
[`run-cbt.sh`](https://github.com/ceph/ceph/blob/v21.3.0/src/script/run-cbt.sh)
drives [CBT](https://github.com/ceph/cbt) against a vstart cluster (or
an existing one, `--use-existing`) from YAML workload definitions.

### vstart --cephadm is local, and still needs an SSH key

`vstart.sh --cephadm` is a hybrid: mon/mgr/osd stay vstart-forked host
processes, with the orchestrator enabled on top to deploy *additional*
daemons as containers. It remains entirely local — the host it adds is
`$(hostname)`
([`vstart.sh:1458-1473`](https://github.com/ceph/ceph/blob/v21.3.0/src/vstart.sh#L1458)):

```bash
ceph_adm config-key set mgr/cephadm/ssh_identity_key -i ~/.ssh/id_rsa
ceph_adm config-key set mgr/cephadm/ssh_identity_pub -i ~/.ssh/id_rsa.pub
ceph_adm mgr module enable cephadm
ceph_adm orch set backend cephadm
ceph_adm orch host add "$(hostname)"        # exactly one host: this one
ceph_adm config set mgr mgr/cephadm/allow_ptrace true
```

SSH is cephadm's only transport, even to itself — the module has no
local-execution shortcut
([`src/pybind/mgr/cephadm/ssh.py:207`](https://github.com/ceph/ceph/blob/v21.3.0/src/pybind/mgr/cephadm/ssh.py#L207)):

```python
conn = await asyncssh.connect(addr, username=self.mgr.ssh_user,
                              client_keys=[self.mgr.tkey.name], ...)
```

Every managed host, localhost included, is reached by opening an
`asyncssh` connection (as `root` by default) and running `cephadm` on
the far end. So `~/.ssh/id_rsa` must be passphraseless and its public
half in `root@$(hostname)`'s `authorized_keys`. Two consequences:
orchestrator-deployed daemons are containers while vstart's own are
not, which is why cephadm reports the latter as **stray daemons**; and
`allow_ptrace` is set so gdb still works inside those containers.

# 10. Inside ceph-osd: threads, shards and queues

Section 4.6 watched an OSD from the wire and Section 6 read one from
the disk; this section maps the machinery between the two — which
thread picks a message up, which thread runs the PG, and which thread
waits on the device. Scope: the classic `ceph-osd` of
[`v20.2.2`][ceph-tag] with BlueStore, not the Crimson rewrite; thread
counts are defaults and vary by release and configuration.

## 10.1 The thread map

There is no single "OSD worker thread". `ceph-osd` is a set of
specialised thread groups handing work to each other through queues —
names as `top -H` shows them:

```
      clients              peer OSDs             MON / MGR
         └─────────────────────┼─────────────────────┘
                               │ TCP
 ┌─────────────────────────────┼───────────────── ceph-osd ──┐
 │                             ▼                             │
 │  msgr-worker-0..2   event loops: RX/TX, framing,   §10.3  │
 │  ms_dispatch        fast + slow dispatch                  │
 │                             │ enqueue_op()                │
 │                             ▼                             │
 │  tp_osd_tp          OSDShard queues → mClock       §10.2  │
 │                     → PG::do_request()                    │
 │                             │ queue_transactions()        │
 │                             ▼                             │
 │  bstore_aio         disk I/O completions           §10.4  │
 │  bstore_kv_sync     fdatasync + RocksDB commit            │
 │  bstore_kv_final    hand completions to the shard         │
 │                             │ on_commit, requeued on      │
 │                             ▼ the op's shard              │
 │                     reply out through the messenger       │
 └───────────────────────────────────────────────────────────┘
```

Supporting cast, off the data path: `osd_srv_heartbt` plus dedicated
heartbeat messengers (peer liveness, §10.5), `safe_timer` (timeouts),
`rocksdb:low` (compaction).

## 10.2 Shards: the queue in front of every PG

```
                        OSD
                         │   PG → shard:  pg_id.ps() % num_shards
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
    OSDShard 0       OSDShard 1       OSDShard 2   ...
        │                │                │
      queue            queue            queue      OpSchedulerItems
        │                │                │
     workers          workers          workers     tp_osd_tp
        │                │                │
       PGs              PGs              PGs       PG lock while running
```

Each PG belongs to one shard — `ps() % num_shards`, the PG number
itself, so PGs land on shards round-robin — and every shard owns a
queue plus a few `tp_osd_tp` workers. The defaults come from the same
rotational detection Section 9.4 met, and the HDD pair is inverted
from what older documentation shows:

| class | shards | threads/shard |
|-------|--------|---------------|
| HDD | 1 (`osd_op_num_shards_hdd`) | 5 (`osd_op_num_threads_per_shard_hdd`) |
| SSD | 8 (`osd_op_num_shards_ssd`) | 2 (`osd_op_num_threads_per_shard_ssd`) |

Tentacle is the release that flipped HDD from 5 × 1 to 1 × 5
([`0d81e721`][ceph-hdd-shards], [tracker 66289][tracker-66289]): at
scale mClock scheduled poorly across several independent queues —
inconsistent client throughput, slow requests during node failures —
while one queue with five workers behaved. So sharding still buys
parallelism on flash, but on spinning disks the current answer is one
queue and many workers.

The queue entries are not raw messages. A family of `enqueue_*` calls
wraps each into an `OpSchedulerItem` — `enqueue_op()` for client ops
and recovery messages, `enqueue_peering_evt()` for peering, siblings
for scrub and snap trim — and a scheduler (mClock by default) decides
what a worker dequeues next. This is the seat of QoS: client I/O and
background work compete here, weighted by `osd_mclock_profile`.

The rule that makes it safe:

> No thread mutates PG state except a shard worker that dequeued an
> item for that PG, and it holds the PG lock while doing so.

Messenger threads only enqueue; timers and peering events arrive as
queue items too. The consequences: ops on one object are ordered
(same object → same PG → same shard queue), two workers never run the
same PG at once (PG lock), and different PGs proceed in parallel.
When reading `src/osd/`, the synchronization to study is this funnel —
`enqueue_op → dequeue_op → do_request` — not per-field mutexes.

Why more than one worker per shard: BlueStore commits asynchronously,
so a worker does not sit through the disk wait — but it can be held
for milliseconds of CPU (checksums, encode/decode), on a contended PG
lock, or inside `queue_transactions()` itself when BlueStore's
throttle is full and in-flight bytes must drain. A second worker keeps
the shard's *other* PGs moving meanwhile.

## 10.3 The messenger never runs an op

Every connection — client, peer OSD, MON, MGR — is multiplexed onto a
few `msgr-worker-*` event loops (three by default). Their RX contract
is strict: decode, hand off, return to `epoll`:

```
 msgr-worker-N                                   tp_osd_tp
      │
   RX bytes → decode MOSDOp
   ms_fast_dispatch() → enqueue_op()
      │──────────── OpSchedulerItem ──────────►  shard queue
      │                                             ⋮
   back to epoll — never touches               (runs later, §10.2)
   PG or BlueStore state
```

If the loop thread executed ops synchronously, one slow storage op
would stall every connection multiplexed behind it. Latency-critical
types (`MOSDOp`, repop replies) take this **fast dispatch** path,
straight from the messenger thread into the shard queue; rare control
traffic (new osdmaps, commands) goes through a `DispatchQueue` and the
`ms_dispatch` thread instead. TX mirrors RX: a worker hands the reply
to the connection, the messenger writes it out when the socket allows.

The glue between lanes is everywhere the same pair of primitives: a
mutex+condvar queue to move work forward, and a `Context` callback —
Ceph's completion object — to signal completion back. Note where a
commit `Context` actually *runs*: not on the thread that fires it.
`bstore_kv_final` drops it into the owning shard's `context_queue`,
and a `tp_osd_tp` worker runs it — after the dequeue path has already
dropped the PG lock, so the `BlessedContext` wrapper retakes it first.

## 10.4 One write, lane by lane

The write Section 4.6 caught in `dump_historic_ops`, spread across the
lanes — the right column is the event the op tracker stamps at that
hop:

```
 msgr-worker-*             tp_osd_tp                bstore_*
      │
  RX MOSDOp,
  enqueue_op() ──────────► shard queue                        initiated
      ⋮                    mClock dequeue, PG lock              started
      ⋮                    PG::do_request()
      ⋮                    PrimaryLogPG::do_op()
      ⋮                    issue_repop():
  TX MOSDRepOp ◄────────── send to osd.2, osd.13     waiting for subops
      ⋮                    queue_transactions() ──► aio submitted
      ⋮                    PG lock dropped,         bstore_aio: I/O done
      ⋮                    worker moves on          bstore_kv_sync: fsync
      ⋮                        ⋮                    bstore_kv_final: ctx
      ⋮                    ◄── on_commit requeued ────┘       op_commit
  RX 2× MOSDRepOpReply ──► shard queue                sub_op_commit_rec
      ⋮                    all copies durable →
  TX MOSDOpReply ◄──────── reply to client                  commit_sent
```

So the 20 ms Section 4.6 measured between `waiting for subops` and
`op_commit` is not a thread blocking anywhere: the worker dropped the
PG lock and moved on, and the time lives in the `bstore_*` lane (the
[companion post][bluestore-post] walks that lane in depth). The two
`sub_op_commit_rec` gaps are the same lanes running on the replicas,
plus the network.

This chain is also the recommended way into the source: follow this
one write through `OSD::ms_fast_dispatch → enqueue_op →
ShardedOpWQ::_process → dequeue_op → PG::do_request →
PrimaryLogPG::do_op → issue_repop → BlueStore::queue_transactions`.
Beyond the files Section 8.2 listed, that adds
[`src/osd/OSD.{h,cc}`][src-osd] (dispatch, `OSDShard`,
`ShardedOpWQ`), [`src/osd/scheduler/`][src-sched] (mClock) and
[`src/msg/async/`][src-msg] (the messenger).

## 10.5 Four conversations and a socket

```
               MON                            MGR
      OSDMap ↓  ↑ MOSDBeacon,                  ↑ MMgrReport (counters)
             ↓  ↑ failure reports              ↑ MPGStats  (PG stats)
             ↓  ↑                              ↑
 clients ── MOSDOp ──►   ceph-osd   ◄──► MOSDRepOp, peering, recovery,
                         │      ▲        backfill ─────────── peer OSDs
                         │      └─────── heartbeats (own sockets)
                         └── admin socket (local UNIX socket, §9.7)
```

- **Clients** reach the primary OSD directly — no gateway, no lookup
  service — exactly the trace of Sections 4.5–4.6.
- **Peer OSDs** exchange replication (`MOSDRepOp`/`MOSDRepOpReply` —
  the "subops" of the event names; the old `MOSDSubOp` class is gone),
  peering, recovery and backfill traffic. Heartbeats get dedicated
  front and back messengers on their own sockets, and `MSG_OSD_PING`
  is fast-dispatched *inline on the messenger thread* — a ping is
  answered without ever entering a shard queue, so liveness never
  waits behind data. What is dedicated is the socket pair and the
  `osd_srv_heartbt` thread that sends pings and times peers out; those
  messengers still share the process-wide `msgr-worker` pool, since
  every `AsyncMessenger` draws from one `NetworkStack` singleton.
- **MON**: authoritative maps down, beacons and failure reports up.
  Map handling is itself asynchronous — an incoming `MOSDMap` is
  persisted and published, then each PG catches up through the same
  shard queues — alongside the `maybe_share_map` piggyback path of
  Section 4.6.
- **MGR** receives `MMgrReport` (perf counters, daemon status) and,
  separately, `MPGStats` (PG stats) — the material behind the
  dashboard and the `ceph -s` throughput line.
- **Local processes** get exactly one door: the admin socket of
  Section 9.7. `ceph tell osd.N` arrives over the normal messenger as
  a command message.

## 10.6 Old maps, and why this shape scales

Older documentation draws an unsharded OSD over FileStore; don't port
that mental model:

```
 Older docs' OSD + FileStore        v20.2.2 + BlueStore
 ───────────────────────────        ───────────────────
 Messenger                          Messenger, fast dispatch
     ↓ DispatchQueue                    ↓ enqueue_op()
 OSD OpWQ (one queue)               OSDShard queues, mClock
     ↓                                  ↓ tp_osd_tp workers
 PG                                 PG / PrimaryLogPG
     ↓ journal queue                    ↓ queue_transactions()
 FileStore OpWQ (tp_fstore_op)      BlueStore TXC state machine
     ↓ apply into the page cache        ↓ aio + kv_sync / kv_final
 write twice (journal + files)      write once (small writes twice)
```

Two caveats on that left column. The stages are not contemporaries —
fast dispatch and the sharded op WQ landed years before FileStore was
removed in Reef, so the two coexisted for most of a decade; and you
cannot read FileStore at `v20.2.2`, because `src/os/filestore/` is
already gone. The right column's "write once" is also only the common
case: BlueStore's deferred path is a genuine double write, and on an
HDD-classified OSD every write under `bluestore_prefer_deferred_size`
(64 KiB, Section 9.4) takes it. The win is that the double write
became the exception rather than the rule.

The parallelism stacks: many OSDs per cluster × shards per OSD ×
workers per shard × PGs per shard, with storage asynchronous
underneath and replication fanning out across machines — no global
lock or single thread on the object data path.

> One sentence: messenger threads receive and send, shard workers run
> the PG state machines, BlueStore threads make it durable, queues and
> `Context`s glue the lanes together — and the PG is the unit that
> keeps it all ordered.


# 11. Crimson: the same PG, without the threads

`crimson-osd` is a rewrite of Section 10 on top of
[Seastar][seastar] — shared-nothing, one pinned reactor thread per
core, run-to-completion continuations, no blocking calls anywhere.
Every structure Section 10 spent its length on (the shard queue, the
worker pool, the PG lock, the requeued `Context`) is gone, and the
ordering they provided has to be rebuilt out of something else.

Upstream's own framing, from [`doc/glossary.rst`][doc-glossary] rather
than the Crimson docs, which state no motivation at this tag:

> "A next-generation OSD architecture whose aim is the reduction of
> latency costs incurred due to cross-core communications. A re-design
> of the OSD reduces lock contention by reducing communication between
> shards in the data path. Crimson improves upon the performance of
> classic Ceph OSDs by eliminating reliance on thread pools."

Status matters before the architecture: at `v20.2.2` Crimson is a
**tech preview and explicitly not for production** (§11.5), and it
moves fast enough that several option names in this section have
already been renamed on `main`. Squid shipped the first preview;
Tentacle is the release where SeaStore became deployable alongside it.

## 11.1 What replaces what

```
 classic ceph-osd (§10)             crimson-osd
 ──────────────────────             ───────────
 msgr-worker-0..2                   reactor thread per core
     ↓ enqueue_op()                     ↓ continuation, same core
 OSDShard queue + mClock            pipeline stages — no queue
     ↓ tp_osd_tp worker                 ↓ still the same reactor
 PG lock across do_request          no PG lock: per-PG and per-object
     ↓ queue_transactions()             ↓   pipelines (§11.2)
 BlueStore + bstore_* threads       SeaStore: same reactor, no hop
     ↓ Context requeued on shard    AlienStore: thread pool (§11.4)
 reply                              reply
```

Shared-nothing is enforced at compile time, not by convention. Under
`WITH_CRIMSON`, `ceph::mutex`, `ceph::recursive_mutex` and
`ceph::shared_mutex` become empty structs whose `lock()`/`unlock()`
compile to nothing, and `ceph_mutex_is_locked()` is `#define`d to
`true` (`src/common/ceph_mutex.h`). Shared Ceph code that still calls
`ceph::make_mutex()` therefore gets no mutual exclusion at all, so
touching an object from the wrong core is a data race rather than
contention — which is why `seastar::this_shard_id()` assertions guard
shard-local state, and `PerShardState` wraps its own in an
`assert_core()`. Process-global state (OSDMap, monclient, superblock)
lives in `OSDSingletonState` on `PRIMARY_CORE = 0`, reached by
explicit `invoke_on(0, …)`.

Threads in a `crimson-osd` process:

- **reactors** — `crimson_seastar_num_threads` (max 32, and defaulted
  to `0`, which aborts at startup) or `crimson_seastar_cpu_cores`; one
  of the two must always be set. One reactor per dedicated core;
  pinning happens only in the cpuset form.
- **`alien-store-tp`** — `crimson_alien_op_num_threads` plain
  `std::thread`s, default **6**, present only with AlienStore.
- **BlueStore's own threads, unchanged.** The alienstore target is
  compiled *without* `WITH_CRIMSON`, so with the default objectstore
  every thread from Section 10's BlueStore lane — `bstore_kv_sync`,
  `bstore_kv_final`, `bstore_aio`, the Finisher, RocksDB's background
  threads — is still in the process, now behind a thread pool.

## 11.2 Ordering without a PG lock

Section 10's serialization came from one rule: only a shard worker
holding the PG lock mutates a PG. Crimson has no such lock. Ordering
is a property of **pipelines** — chains of stages an operation walks,
where each stage is a per-core object that admits ops either
exclusively (at most one in the stage, entered in arrival order) or
concurrently (many in-stage, still FIFO on entry).

```
 ConnectionPipeline  per connection  await_active, await_map,
                                     get_pg_mapping
 PerShardPipeline    per reactor     create_or_wait_pg
 CommonPGPipeline    per PG          wait_pg_ready [concurrent], get_obc
 CommonOBCPipeline   per OBJECT      process, wait_repop [concurrent],
                                     send_reply
 PGRepopPipeline     per PG          process, wait_commit [concurrent],
                                     send_reply
 PGPeeringPipeline   per PG          await_map, process
```

The granularity is the point, and upstream's
[`doc/dev/crimson/pipeline.rst`][doc-pipeline] says so directly:

> "Because CommonOBCPipeline is per-object rather than per-connection
> or per-pg, multiple requests on different objects may be in the same
> CommonOBCPipeline stage concurrently. This allows us to serve
> multiple reads in the same PG concurrently. We can also process
> writes on multiple objects concurrently up to the point at which the
> write is actually submitted."

So a PG is no longer the unit of mutual exclusion — an object is. What
holds the chain in order is `PipelineHandle`: entering the next stage
is queued *before* the previous stage's barrier is released, and that
deliberate overlap is what stops ops from reordering between stages. A
head object and its clones share one pipeline through an `Orderer`
holding the head's `ObjectContext`, while unrelated objects in the
same PG proceed in parallel. The remaining locks in `pg.h` are narrow:
a `shared_mutex` for background work (snaptrim, scrub) against client
I/O, and one around transaction submission. Per-object exclusion is a
`tri_mutex` on the `ObjectContext` — reads pipeline, writes pipeline,
but never both at once.

Two more Section 10 mechanisms have no counterpart:

- **The op scheduler is effectively inert for client I/O.** mClock
  exists in `src/crimson/osd/scheduler/`, but its throttle has exactly
  one caller in the tree — recovery, always at
  `background_best_effort` — and it is disabled by default anyway
  (`crimson_osd_scheduler_concurrency` is `0`, meaning unlimited).
  Back-pressure comes from the store's concurrent-transaction limit,
  the messenger's byte throttler and the pipeline stages, not from
  QoS. §10.2's "seat of QoS" has no equivalent here.
- **Peering changes are an exception thrown into the chain**, not a
  requeue from a queue. The op body runs under an interruptor that
  checks whether the interval changed since it started, and injects
  `actingset_changed` if so.

## 11.3 One client op, across cores

```
 socket, reactor A
   │  ms_dispatch → do_ms_dispatch → handle_osd_op
   ▼
 ConnectionPipeline           [core A]
   await_active → await_map → get_pg_mapping
                                  │  miss → invoke_on(0), least-loaded
 ═══ cross-core hop: leave pipeline, move registry entry, ═══
 ═══ foreign_ptr the connection, reorder by sequence no.  ═══
                                  ▼
 PerShardPipeline             [core B]
   create_or_wait_pg
   ▼
 CommonPGPipeline             [per PG]
   wait_pg_ready → get_obc
   ▼
 CommonOBCPipeline            [per OBJECT — parallel inside one PG]
   process → wait_repop → send_reply
      │          │
      │       PGRepopPipeline: process → wait_commit → send_reply
      │       ReplicatedBackend::submit_transaction
      ▼
   FuturizedStore::Shard::do_transaction
      ├─ SeaStore   same reactor, no thread hop
      └─ AlienStore queue → alien-store-tp → BlueStore → eventfd back
```

A PG belongs to a core, but not by the arithmetic of §10.2. The
mapping is dynamic and load-balanced: a miss is proxied to core 0,
which picks the core with the fewest PGs, then broadcasts the result
to every core's local copy. A disagreement is fatal —
`ceph_abort("The pg mapping is inconsistent!")`.

The hop is unavoidable and common, because a connection's reactor is
wherever Seastar's socket landed and there is no connection-to-PG
affinity. Its cost, per op that crosses: exit the source pipeline,
deregister from the source core's operation registry, convert the
connection to a `foreign_ptr`, `submit_to` the target core,
re-register, then wait for the cross-core sequence number to come up
in order — `smp::submit_to` does not preserve order, so Crimson
re-establishes it by hand. Ops that already know their PG is active
(replica ops, recovery subops) take a shorter path that skips the
connection pipeline entirely.

Introspection replaces the op tracker. Every op is an `Operation` with
a type code and a compile-time tuple of `BlockingEvent`s: entering a
stage timestamps it and records which `Blocker` it waited on, so "why
is this op stuck" is answered by the blocker rather than by a thread
backtrace. Which is the honest reason `dump_historic_ops` still exists
here but is not the tool it was in Section 4.6 — the per-request data
is real, while the `num_ops` field is a hardcoded `0`. One more trap
when reading that output: `PGRepopPipeline`'s member is `wait_commit`,
but the name it reports is `PGRepopPipeline::wait_repop`.

## 11.4 The store: three backends, two worlds

The backend factory recognises exactly two names — `cyanstore` and
`seastore` — and falls through to AlienStore for everything else,
which is how `bluestore` (the default, via `crimson_osd_objectstore`)
is reached. Upstream's split:

> "native" backends "perform I/O operations using the Seastar
> reactor"; non-native ones "operate through a thread pool proxy,
> which interfaces with object stores running in alien threads —
> worker threads not managed by Seastar."

**AlienStore** is the compromise that lets Crimson run today, and its
cost is concrete. There is exactly one AlienStore for the whole
process — one `ObjectStore`, one classic `CephContext`, one thread
pool — and every reactor calls into it. Per read: a semaphore wait, a
heap allocation plus **an eventfd created per in-flight op**, a
lockfree-queue push, a futex wakeup into the pool, the blocking
BlueStore call, then a `write(2)` on that eventfd to wake the reactor
back up. Two cross-thread hops and two different wakeup mechanisms.
Writes cross a third time, since BlueStore's commit `Context` fires on
its own Finisher thread and posts back through
`seastar::alien::submit_to`. Two details show how thin the bridge is:
thread choice for non-collection ops is `rand() % n_threads` — a
locking glibc call on the reactor — and any `dout` from BlueStore
blocks its alien worker until the reactor drains it, with the source's
own comment conceding the wait is "indeterministic".

**SeaStore** is the native answer, and it is a different design from
BlueStore rather than a port of it:

```
 BlueStore (§10, §6.4)              SeaStore
 ─────────────────────              ────────
 RocksDB for all metadata           no KV store at all — B-trees on the
   over BlueFS                        journal: LBA, backref, onode, omap
 deferred WAL for small writes      one journal; a transaction *is* a
                                      record
 allocator + freelist in RocksDB    segments + host-driven cleaning
 in-place overwrite of blobs        copy-on-write extents, remap by
                                      default
 device GC trusted / discard        GC driven above the device, on
                                      flash-segment boundaries
```

The reasoning upstream gives is that flash is internally segmented and
the device cannot know what is still live, so the host should own the
layout and the cleaning: "we can design an on-disk layout that is
friendly to GC at lower layers and drive garbage collection at higher
layers", noting "in practice discard is poorly implemented in the
device and intervening software layers". The design is "based heavily
on both f2fs and btrfs", and each reactor manages its own root — a
separate store per core, not a shared one.

Mechanically: extents are copy-on-write and addressed logically
through a refcounted LBA B-tree (which is what makes clone and
remap-based partial overwrite cheap), with a second backref tree
mapping physical back to logical purely so the cleaner can ask what is
still live in a segment. Transactions are **optimistic** — read set,
write set, retired set; at commit, if every extent in the read set is
still valid it lands, otherwise it fails with `eagain` and an
unbounded retry loop runs it again. Rewrites climb a generation ladder
so similarly-aged extents share segments, and cleaning runs as its own
tracked transaction type.

Worth knowing before you benchmark it: the segment cleaner's
availability thresholds are compile-time constants, not tunables
(still constants on `main`, though the cleaner now re-derives them at
runtime from observed usage); the random-block journal is visibly
incomplete — its `flush()` is a TODO stub and the matching cleaner is
inert; and ZNS support exists in the tree but is build-gated off by
default.
CyanStore is memory-only, loses everything on crash, and exists "only
for measuring OSD overhead, without the cost of actually storing
data".

## 11.5 What it costs, and what is missing

The costs are the direct price of the model:

- **Reactors busy-poll.** The tuning knobs say so in as many words:
  `crimson_reactor_idle_poll_time_us` is documented as "Longer reactor
  poll time will result in larger CPU utilization."
- **Sizing is rigid.** CPU allocation "cannot be changed after
  deployment", and with AlienStore the reactor and alien cpusets must
  be mutually exclusive.
- **Cross-core hops are the common case** (§11.3), not the exception.
- **Nothing may block**, so classic code either becomes futures or
  goes behind the alien pool at the cost in §11.4.
- **Debugging is different.** No human-readable backtrace on SIGSEGV
  or SIGABRT — you run the output through
  `src/seastar/scripts/seastar-addr2line`. Logs go to stdout, not
  `log_file`. Section 9.7's admin socket does still work, including
  per-PG `query` and `scrub`, plus `dump_metrics` and a real
  Prometheus endpoint under `--prometheus_port`.

Maturity, stated plainly by upstream: "Crimson is in a tech preview
stage and is **not suitable for production use**", and the monitor
makes you say so three times — enable an experimental feature, `ceph
osd set-allow-crimson --yes-i-really-mean-it` (irrevocable), then
`osd_pool_default_crimson`. Its own warning says crimson-osd "will
likely cause crashes or data corruption".

Verified restrictions at `v20.2.2`:

| | |
|---|---|
| PG autoscale | must be `off`; pools get `NOPGCHANGE`, which cannot be cleared |
| PG split/merge | blocked by that same flag — and the error tells you to unset `nopgchange`, which a crimson pool will not let you do. On `main` split is allowed by default, merge is opt-in per pool |
| Cache tiering | refused for crimson pools |
| Erasure coding | **not refused — but `ECBackend` is a 37-line stub** whose reads return empty and whose `submit_transaction` does nothing |
| librados/librbd | 239 `SKIP_IF_CRIMSON()` call sites in the test tree |
| QA suites | RADOS and RBD only — no RGW or CephFS suite exists at this tag |

Implemented and non-trivial: recovery, backfill, snapshots, scrub,
watch/notify. The EC entry is the one to internalise: the monitor's
own comment says crimson "requires that the pool be replicated" and
then never checks it, while `pg_backend.cc` happily constructs the
stub backend for `TYPE_ERASURE`. The failure mode is silence, not an
error.

That theme extends to the plumbing. In `MonCommands.h` two argument
descriptors are missing the separator between them, so C string
concatenation fuses them into `…req=falsename=crimson` — meaning
`osd pool create … --crimson` is not a parseable flag at all, and
`osd_pool_default_crimson` is the only working route to a crimson
pool. Still true on `main`.

## 11.6 Running it

Crimson is not in the release binaries this post used; it needs its
own build, and a newer toolchain than the rest of Ceph (GCC ≥ 13, for
C++20 coroutines, against GCC ≥ 11 otherwise):

```
WITH_CRIMSON=true ./install-deps.sh
./do_cmake.sh -DWITH_CRIMSON=ON
cd build && ninja crimson-osd
```

Then Section 9.4's loop, with the Crimson flags:

```
MON=1 OSD=3 ../src/vstart.sh -d -n -x --crimson --crimson-smp 2

# SeaStore: one device per OSD, and vstart zeroes the first 1 MiB of each
MON=1 OSD=1 ../src/vstart.sh -d -n -x --crimson --seastore \
      --seastore-devs /dev/nvme0n1
../src/stop.sh --crimson
```

`--seastore-devs` takes a comma-separated list matched to OSDs by
index, so asking for three OSDs and naming one device silently gives
osd.0 the device and the other two files.

`--crimson` swaps the binary and forces msgr2; `--crimson-smp` sets
reactors per OSD; `--crimson-alien-num-threads` sizes the alien pool;
`--crimson-balance-cpu osd|socket` runs `assign_crimson_cores.py` to
carve the two cpusets apart. vstart sets `allow_crimson` and forces
autoscale off for you. One gotcha: unlike `ceph-osd`, `crimson-osd`
does not daemonize even when told to, which is why `--crimson`
implies `nodaemon`.

Reading order, once §10's chain is familiar:
[`src/crimson/osd/osd_operation.h`][src-crimson-op] for every pipeline
stage in one file, then `pg_shard_manager.h`'s `start_pg_operation`,
which holds the entire lifecycle of §11.3 — cross-core hop included —
in a single function. Then `common/operation.h` for the pipeline
machinery, and either `os/alienstore/thread_pool.h` or
`os/seastore/cache.h` depending on which store you care about.

> One sentence: Crimson keeps RADOS and throws away the threading —
> a reactor per core, ordering rebuilt from per-object pipelines
> instead of a PG lock, and a store that either runs on the reactor
> (SeaStore) or is bridged to it by a thread pool (BlueStore).

A caution on version: `crimson-osd` moves faster than the rest of
Ceph. Against `v20.2.2`, `main` has already turned `ECBackend` into a
real implementation, allowed PG split by default, made the segment
cleaner's GC formula a config option and its thresholds self-tuning,
and renamed most of the `crimson_*` CPU options
(`crimson_seastar_num_threads` → `crimson_cpu_num`, and similarly for
the rest). The execution model above — pipelines,
`PGShardMapping`, the cross-core hop, the alien bridge — is unchanged
between the two, but check the option names before copying a command.
