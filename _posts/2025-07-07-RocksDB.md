## High-level architecture

RocksDB is a storage-engine library exposing a key-value store interface, where
keys and values are arbitrary byte streams. It keeps all data in sorted order,
and the common operations — [`Get`, `NewIterator`, `Put`, `Delete`,
`SingleDelete`][db-h] — are all declared on `DB` in `include/rocksdb/db.h`.

The three basic constructs are the **memtable**, the **SST file** and the
**log file**:

- The [memtable][memtable-h] is an in-memory data structure (a
  [skiplist][skiplist] by default). New writes are inserted into the memtable
  and optionally appended to the log file (the Write-Ahead Log, WAL).
- The [WAL][log-writer] is a sequentially-written file on storage that provides
  durability for writes still living only in the memtable.
- When the memtable fills up it is flushed to an [SST file][sst-builder] on
  storage, after which the corresponding WAL segment can be safely deleted.
  Data inside an SST file is sorted to make key lookup easy.

## Metadata storage

A **MANIFEST** log file records all database state changes. Compaction adds new
files and deletes existing ones; it makes those changes persistent by recording
them (as [`VersionEdit`][version-edit] records applied by the
[`VersionSet`][version-set]) in the MANIFEST.

## Features

- [**Column Families**][column-family] — independent key spaces inside a single
  database. They share one WAL (so writes across families can be atomic) but
  have their own memtables and SST files, so each can be tuned and compacted
  independently.

# Compression

## Block-based compression

The key thing to understand is that RocksDB compresses at the **block** level,
not at the individual value level.

An SST file is not a single compressed blob. It is composed of many smaller
*data blocks*, each holding a group of sorted, contiguous key-value pairs. The
compression flow is:

1. When RocksDB flushes a memtable or runs a compaction, it takes a chunk of
   sorted key-value pairs.
2. That chunk becomes a data block (size configurable via
   [`block_size`][block-size], typically 4 KB to 32 KB, default 4 KB).
3. The chosen [compression algorithm][compression-type] (Snappy,
   [ZSTD][zstd], etc.) is applied to the whole block.
4. The compressed block is written to the SST file by the [block-based table
   builder][sst-builder].

Compressing a block at a time amortizes the per-call overhead of the compressor
over many key-value pairs — far more efficient than compressing each value
individually, especially for small values.

## A concrete walkthrough

Assume `options.block_size = 4 KB` (4096 bytes) and `options.compression =
kZSTD`. Where data lives at each stage:

- **Memtable** — uncompressed; live in a skiplist for fast reads/writes.
- **WAL** — uncompressed by default; it is a durability log.
- **SST file** — compressed; this is where data lives permanently on disk.

### Writing and compressing (the flush)

This runs when a memtable becomes full and is flushed to a new Level-0 SST file.

1. **Read from the memtable.** The flush creates an iterator over the whole
   memtable and reads key-value pairs sequentially, in sorted order.
2. **Form a data block.** It reads just enough consecutive pairs to fill a
   ~4 KB buffer. If the average pair is 100 bytes, that is roughly 40 pairs:
   `[key1, value1, key2, value2, ... key40, value40]`.
3. **Compress the block.** The 4 KB buffer is passed to ZSTD. Assuming a 3:1
   ratio, the output is a ~1.3 KB chunk of compressed bytes.
4. **Write to the SST file.** The ~1.3 KB block is written to disk, and RocksDB
   records metadata (the block's offset and size) in the file's index.

The loop repeats — read the next ~40 pairs, compress to ~1.3 KB, write —
until the entire memtable has been written out as a series of compressed blocks.

### Reading and decompressing (the Get)

This runs when you call `db->Get("my_key", &value)`.

1. **Find the right SST file.** RocksDB checks the memtables first. If the key
   isn't there, it uses metadata and [Bloom filters][filter-policy] to narrow
   down to the SST file that might contain `my_key`.
2. **Find the right block.** RocksDB does not read the whole SST file. At the
   end of every SST file is an [index block][index-builder] mapping key ranges
   to block locations; from it the [table reader][table-reader] learns that
   `my_key`, if present, lives in (say) block #73 at some offset.
3. **Read the compressed block.** RocksDB seeks to that offset and reads the
   entire compressed block (~1.3 KB in our example) into memory. The block is
   placed in the [**block cache**][block-cache], so later reads of nearby keys
   are served from RAM with no disk I/O.
4. **Decompress the block.** The ~1.3 KB is passed to ZSTD decompression,
   inflating it back to the original 4 KB uncompressed block.
5. **Find the key.** RocksDB binary-searches within the 4 KB uncompressed block
   to locate `my_key` and return its value.


# Optimization ideas

## Fixed-length key optimization: `prefix_extractor`

A [`prefix_extractor`][slice-transform] lets RocksDB build a separate index on
a *prefix* of the keys, which unlocks prefix-seek performance. For fixed-length
keys the prefix concept is a perfect fit — you can treat the entire key as the
prefix.

Implement it with [`NewFixedPrefixTransform(N)`][fixed-prefix], where `N` is the
exact key length.

## Skip the WAL when data loss is acceptable

Setting [`WriteOptions::disableWAL = true`][disable-wal] skips the WAL write on
the put path. Safe only when losing recent, not-yet-flushed writes on a crash
is acceptable (e.g. rebuildable caches or scratch data).

## Using RocksDB as storage for a block device

Basic idea:

- Use the 64-bit LBA as the key.
- The value is a byte stream whose length is the fixed *logical block size* of
  the device.
- Enable compression. Because compression is done per block —
  `[key0, value0, key1, value1, ..., keyN-1, valueN-1]` — packing many adjacent
  LBAs into one data block lets the compressor exploit redundancy across
  neighboring blocks.
