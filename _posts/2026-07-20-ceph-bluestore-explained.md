# Overview

BlueStore is the storage engine of Ceph: the code inside every OSD daemon
that takes replicated object writes and persists them onto a **raw block
device** — no filesystem in between — with metadata kept in an embedded
RocksDB. This post explains BlueStore twice: first from the outside (what
Ceph is for, where BlueStore sits, how to deploy and verify it on a Fedora
VM), then from the inside (its components, data structures, and the read /
write / transaction paths through the code). The target reader knows
storage and kernel programming but is new to Ceph.

# Terms and abbreviations

Skim once, refer back as needed; groups run top-down — cluster level

### Ceph cluster level

| Term | Meaning |
|------|---------|
| RADOS | Reliable Autonomic Distributed Object Store — Ceph's core object store |
| OSD | Object Storage Daemon — one daemon per disk; BlueStore lives inside it |
| MON / MGR | Monitor (cluster maps, quorum) / Manager (metrics, orchestration) |

| CRUSH | the hash-based placement algorithm — clients compute object locations |
| RBD / CephFS / RGW | block / file / S3-object interfaces, all layered on RADOS |
| object | RADOS's unit: name + byte data + xattrs + omap (typically 4 MiB for RBD) |
| omap | per-object sorted key/value pairs (like a small per-object database) |
| cephadm | the deployment tool — runs daemons as podman containers under systemd |

### BlueStore objects

| Term | Meaning |
|------|---------|
| ObjectStore | the backend API BlueStore implements (`src/os/ObjectStore.h`) |
| Transaction | an op batch (write + attrs + omap + ...) that must commit atomically |
| onode | per-object metadata record (size, attrs, extent map) — RocksDB `O` key |
| extent | a *logical* byte range of an object, pointing into a blob |
| blob | a unit of *physical* allocation: device extents + checksum + flags |
| pextent | one physical device range (offset, length) inside a blob |
| SharedBlob | refcounted blob state shared between clones/snapshots (COW) |
| collection | BlueStore's container for one PG's objects |
| TransContext | one in-flight transaction walking the write-path state machine |
| deferred write | small overwrite whose payload commits via RocksDB (`L` key) first, reaches its final location later |

### Persistence and devices

| Term | Meaning |
|------|---------|
| RocksDB | embedded LSM key/value store holding ALL BlueStore metadata |
| WAL | write-ahead log — RocksDB's journal; its fsync is the commit point |
| BlueFS | mini-filesystem BlueStore implements just to host RocksDB's files |
| block / block.db / block.wal | the OSD's data / RocksDB / WAL devices |
| min_alloc_size | smallest allocation unit on the data device (4 KiB default) |
| allocator | in-memory free-space policy (default `hybrid`) |
| FreelistManager | persistent free-space record, stored in RocksDB |
| NCB | source-code tag for null-freelist mode: skip per-commit freelist updates, rebuild the allocator map on unclean startup |
| csum | per-blob-chunk checksum (crc32c default), verified on every read |

# Part 1: the user view

## What Ceph is, and where BlueStore sits

Ceph is a distributed storage system that presents three interfaces on top
of one object store called **RADOS** (Reliable Autonomic Distributed Object
Store): block devices (RBD), a POSIX filesystem (CephFS), and S3-compatible
object storage (RGW). RADOS spreads objects across many **OSD daemons**
(Object Storage Daemon, one per disk) using the CRUSH hash-based placement
algorithm — clients compute where data lives, there is no central lookup
table, so the cluster scales horizontally and heals itself when disks die.

BlueStore is the *bottom layer of the OSD*: everything above it decides
**where** an object goes and **how many copies** exist; BlueStore's only job
is to store objects **on this one disk**, transactionally, as fast as the
disk allows.

```
            VM / container      app        s3cmd, awscli
                 │                │              │
             /dev/rbd0        mount -t ceph   S3 / Swift REST
                 │                │              │

            │   RBD   │      │ CephFS  │    │   RGW   │   3 user interfaces

            └────┬────┘      └────┬────┘    └────┬────┘

                                  ▼
```

## Why BlueStore exists (the motivation)

Before BlueStore, OSDs used **FileStore**: every RADOS object was a file in
an XFS filesystem. That design paid a double tax:

- **Double journaling.** Ceph needs transactional writes (data + several
  metadata updates commit atomically). FileStore implemented this with its
  own write-ahead journal — every data byte hit the journal first and its
  file second, and XFS journaled its own metadata on top (the three
  arrows in the diagram below).
- **Impedance mismatch.** POSIX offers no atomic
  "write data + update omap + bump version" primitive, so FileStore
  simulated transactions with fsync ordering games; directory lookups,
  dentry caches and inode limits all throttled object workloads they were
  never designed for.

BlueStore's answer (2016, default since the Luminous release; the design is
written up in the SOSP '19 paper): **own the raw block device**. Data
extents are allocated by BlueStore itself directly on the disk; all
metadata goes into RocksDB, whose write-ahead log provides the transaction
semantics; the filesystem disappears from the picture entirely.

```
   FileStore (old)                        BlueStore (new)
   ──────────────                         ──────────────
   write ──> FileStore journal (write 1)  write ──┬─> data: raw disk (write 1)
         ──> XFS journal       (write 2)          └─> metadata: RocksDB
         ──> XFS file          (write 3)              (WAL is the only journal)

   transactions: emulated on POSIX        transactions: native (RocksDB batch)
   metadata: dentries/inodes/xattrs       metadata: ordered KV records
   allocator: XFS's, invisible            allocator: BlueStore's own, tunable
```

The practical wins users see: roughly 2x write throughput on HDD versus
FileStore, checksums on every read (silent bitrot is detected, not served),
inline compression, and the ability to split data / metadata / WAL across
three device tiers (slow HDD + fast NVMe) without any filesystem tuning.

## Deploying BlueStore on a Fedora VM

Every modern Ceph deployment tool (cephadm, Rook) creates BlueStore OSDs by
default — deploying "Ceph with BlueStore" is just deploying Ceph. The
realistic minimal lab is one Fedora VM running a **cephadm** single-host
cluster: the daemons run as podman containers under systemd, exactly like
production, and BlueStore consumes block devices — spare virtual disks if
the VM has them, or loopback-backed LVM volumes if not.

The turn-key script:
[`code/ceph-bluestore-fedora-deploy.sh`]({{ site.baseurl }}/code/ceph-bluestore-fedora-deploy.sh)
— run it as root on a Fedora VM (4 GB+ RAM):

```bash
./ceph-bluestore-fedora-deploy.sh                        # 3 loop-backed OSDs
NUM_OSDS=1 OSD_SIZE_GB=20 ./ceph-bluestore-fedora-deploy.sh
OSD_DEVICES="/dev/vdb /dev/vdc" ./ceph-bluestore-fedora-deploy.sh  # real disks
```

What it does, step by step:

```
 dnf install cephadm podman lvm2 ─┐
                                  ▼
 cephadm bootstrap --mon-ip .. --single-host-defaults
                                  │   pulls the ceph container image,
                                  │   starts mon + mgr under systemd
                                  ▼

                                  │   loop-file -> LV is the no-spare-disk trick
                                  ▼

                                  │   ceph-volume runs `bluestore mkfs`
```

# Part 2: inside BlueStore

## Component boundary and block diagram

BlueStore lives in `src/os/bluestore/` and implements the backend-neutral
`ObjectStore` interface defined in `src/os/ObjectStore.h`. Its neighbours:
**above** sits the OSD's PG layer, which owns replication, recovery and
ordering across nodes — BlueStore never sees another machine. **Below**
sits `src/blk/`, a small block-device abstraction (Linux AIO/io_uring,
SPDK, PMEM). BlueStore does *not* do networking, replication, or POSIX —
and RocksDB does not store object *data*, only metadata.

```
                    OSD PG layer (replication, recovery)
                          │ ObjectStore API:
                          │ queue_transactions() / read() / omap_*()
        ══════════════════╪══════════════════════ src/os/ObjectStore.h
                          ▼
   ┌──────────────────────────────────────────────────────────────┐
   │ BlueStore                       src/os/bluestore/            │
   │                                                              │
   │  ┌────────────────────┐   ┌──────────────────────────────┐   │
   │  │ metadata layer     │   │ transaction engine           │   │
   │  │ Onode / ExtentMap  │   │ TransContext state machine,  │   │
   │  │ / Blob (+ caches)  │   │ kv_sync_thread, deferred wr. │   │
   │  └─────────┬──────────┘   └──────────────┬───────────────┘   │
   │            │ metadata KV ops             │                   │
   │            ▼                             │                   │
   │  ┌────────────────────┐  ┌───────────┐   │  ┌─────────────┐  │
   │  │ RocksDB (embedded) │  │ Allocator │◄──┼──│ Freelist    │  │
   │  │  onodes, omap,     │  │ (hybrid)  │   │  │ Manager     │  │
   │  │  WAL, freelist     │  └───────────┘   │  └─────────────┘  │
   │  └─────────┬──────────┘                  │                   │
   │            ▼ rocksdb::Env                │                   │
   │  ┌────────────────────┐                  │                   │
   │  │ BlueFS (mini-FS    │                  │ data aio_write /  │
   │  │ just for RocksDB)  │                  │ aio_read          │
   │  └─────────┬──────────┘                  │                   │
   └────────────┼─────────────────────────────┼───────────────────┘
                ▼                             ▼
   ┌──────────────────────────────────────────────────────────────┐
   │ BlockDevice (src/blk/): KernelDevice (O_DIRECT +             │
   │ io_uring/libaio), NVMEDevice (SPDK), PMEMDevice              │
   └──────────────────────────────────────────────────────────────┘
                          raw block device(s)
```

Two facts orient everything else:

- **Data** goes straight from BlueStore to raw disk extents that BlueStore
  allocated itself.
- **Metadata** (which extents belong to which object, checksums, omap,
  the free list) goes into RocksDB — and RocksDB's own files live on the
  same raw disk through BlueFS, a ~6k-line purpose-built filesystem.

Why can data bypass RocksDB entirely? Because on a write, RocksDB is
*written to, never read from*: the free-space decision comes from the
in-memory allocator (loaded once at mount), the destination is fresh
extents (big writes are copy-on-write, so no existing state needs
reading), and the onode/freelist updates are constructed in memory and
*put* into RocksDB after the data lands — an LSM put needs no read. The
only KV read on the write path is an onode-cache miss (one point-get of
the object's metadata), and the deliberate exception is small deferred
writes, whose payload rides *inside* the RocksDB commit (details in the
write-path section).

## On-disk layout

A BlueStore OSD is one to three raw block devices, named by symlinks in
the OSD data dir (`block`, optional `block.db`, optional `block.wal`):

```
 single device (all-flash / lab)      hybrid HDD + NVMe
 ──────────────────────────────       ─────────────────────────────────
 /dev/sdb = "block"                   /dev/sdb       = block      (data)
 ┌──────────────────────────┐         /dev/nvme0n1p1 = block.db   (RocksDB)
 │ bdev label (first 4 KiB) │         /dev/nvme0n1p2 = block.wal  (RocksDB WAL)
 ├──────────────────────────┤
 │ extents owned by BlueFS  │         BlueFS device tiers (BlueFS.h:269):
 │  └─ RocksDB .sst / .log  │           BDEV_WAL  -> block.wal  (fastest)
 ├──────────────────────────┤           BDEV_DB   -> block.db
 │ object data extents,     │           BDEV_SLOW -> block      (spillover)
 │ allocated in             │
 │ min_alloc_size units     │         RocksDB picks the fastest tier that
 │ (4 KiB default)          │         has room; metadata "spills over" to
 └──────────────────────────┘         the slow device only when db is full.
```

There is no filesystem: the "label" is a small encoded struct at offset 0,
and everything after it is extents handed out by the allocator — some to
BlueFS for RocksDB's files, the rest to object data.

## Core data structures (the nouns)

The metadata layer answers one question: *given (object, logical offset),
which disk blocks hold the bytes?* Four structures form the chain, each an
in-memory class in `BlueStore.h` wrapping a persisted `_t` struct from
`bluestore_types.h`:

```
 Onode  ("one object")                              BlueStore.h:1379
 │  key: RocksDB "O..." key encoding the object id
 │  bluestore_onode_t (bluestore_types.h:1160): nid, size, attrs,
 │      extent-map shard index, omap flags
 └─ ExtentMap                                       BlueStore.h:965
    │  logical offset -> Extent; big maps are split into shards,
    │  each shard a separate RocksDB value, loaded lazily
    ├─ Extent {logical_off, blob_off, len} ─► Blob  BlueStore.h:864
    ├─ Extent {...} ────────────────────────► Blob
    │
    Blob                                            BlueStore.h:658
    │  bluestore_blob_t (bluestore_types.h:507):
    │    extents: vector<bluestore_pextent_t>   ◄── PHYSICAL disk ranges
    │    csum_type/csum_data  (crc32c per chunk)
    │    flags: COMPRESSED | CSUM | SHARED | HAS_UNUSED
    └─ SharedBlob (only if cloned)                  BlueStore.h:554
         bluestore_shared_blob_t: sbid + extent refcount map,
         stored under RocksDB prefix "X" — supports RBD snapshots/clones
```

Design notes a storage developer will care about:

- **Extent vs Blob split.** An `Extent` maps a *logical* range; a `Blob`
  owns *physical* extents plus checksum/compression state. Several logical
  extents can point into one blob (small sequential writes get packed),
  and after a clone two onodes' extents share blobs via `SharedBlob`
  refcounting — copy-on-write without copying.
- **Sharding.** A 4 MiB RBD object with 4 KiB random overwrites grows a
  large extent map; storing it as one RocksDB value would make every
  metadata update rewrite the whole map. `ExtentMap` therefore splits into
  shards (`bluestore_onode_t::shard_info`), each a separate `O` key,
  loaded and dirtied independently (`BlueStore.h:965`).
- **Lifetime.** Onodes/Blobs are refcounted (`nref`) and live in
  per-collection caches (a *collection* == one placement group,
  `BlueStore.h:1716`); nothing is ever freed on disk except through a
  transaction that updates the freelist atomically with the metadata.

## The RocksDB schema

All metadata shares one ordered keyspace, distinguished by one-letter
prefixes (`BlueStore.cc:134`). Key layouts and values per prefix
(integers are encoded big-endian so bytewise sort equals numeric sort):

| Prefix | Key (after the prefix byte) | Value |
|--------|------------------------------|-------|
| `S` | field name: `nid_max`, `blobid_max`, `min_alloc_size`, `freelist_type`, `ondisk_format`, `per_pool_omap`, ... | one encoded scalar/string each — the store's superblock, read once in `_open_super_meta` |
| `T` | `bluestore_statfs` (global) or pool id | int64 array: allocated / stored / compressed bytes... updated via a *merge operator* (deltas, no read-modify-write) |
| `C` | collection name, e.g. `2.1f_head` | `bluestore_cnode_t` — essentially the PG's hash-bit count |
| `O` | shard + pool + **bit-reversed hash** + namespace + name + snap + gen | encoded `bluestore_onode_t` (+ inline extent map while small) |
| `O` (shard) | the same onode key + u32 shard offset + suffix byte `'x'` (`BlueStore.cc:201`) | one encoded extent-map shard — big objects split their map across adjacent keys |
| `M` / `P` | u64 **nid** + omap key (`P`: same, for the pgmeta collection) | the user's omap value, verbatim |
| `m` | s64 pool + u64 nid + omap key | ditto (per-pool accounting era) |
| `p` | u64 pool + u32 hash + u64 nid + omap key | ditto (current; sorts omap in PG order for scrub) |
| `L` | u64 sequence number | encoded `deferred_transaction_t`: target device extents **plus the payload bytes**; deleted after replay |
| `B` | meta field names: `bytes_per_block`, `blocks_per_key`, `blocks`, `size` | bitmap-freelist geometry (`BitmapFreelistManager.cc:97`) |
| `b` | u64 device offset (one key per `blocks_per_key` chunk) | allocation bitmap chunk, flipped via an XOR merge operator |
| `X` | u64 shared-blob id (sbid) | `bluestore_shared_blob_t` — the extent refcount map for clones |

Three encoding tricks are worth pausing on:

- **The `O` key sorts like CRUSH places.** `get_object_key`
  (`BlueStore.cc:496`) packs shard + pool + *bit-reversed* object hash +
  name + snapshot. PG membership is decided by the *low* bits of the
  hash, so reversing the bits makes all objects of one PG a contiguous
  key range — PG enumeration, split, and deletion become range scans.
  Extent-map shards extend the same key with their offset, so an onode
  and all its shards are physically adjacent in the SST files.
- **omap keys use the nid, not the object name.** Every onode gets a
  monotonic numeric id (`nid`, allocated from `nid_max` in `S`); omap
  keys embed that instead of the (long, mutable) object name. Renames
  and clones never rewrite omap data — only the onode's pointer to its
  nid — and omap keys stay short regardless of object-name length.
- **Hot counters are merges, not writes.** statfs (`T`) and the
  allocation bitmap (`b`) are updated through RocksDB merge operators —
  an append-only "+delta" / "XOR these bits" record that compaction
  folds in later. That keeps the commit path write-only (no
  read-modify-write of the old value), the same principle as the data
  path bypassing RocksDB reads.

A worked example — `rados put` of a fresh 4 MiB object touches, in one
atomic batch: one `O` put (new onode + extent map), one `b` merge
(bitmap bits for the allocated extents), one `T` merge (statfs deltas) —
and nothing else; the 4 MiB payload went straight to disk.

## Interface 1: transactions — the write path

The OSD hands BlueStore a `ceph::os::Transaction`
(`src/os/Transaction.h:107`): an encoded list of ops (`OP_WRITE`,
`OP_SETATTR`, `OP_OMAP_SETKEYS`, `OP_CLONE`, ... ) that must commit
**atomically** — this is the contract FileStore struggled to fake on
POSIX and BlueStore gets natively from a RocksDB write batch.

`queue_transactions()` wraps the batch in a `TransContext`, which walks a
state machine (`state_t`, `BlueStore.h:1909`; driver `_txc_state_proc`,
`BlueStore.cc:14634`):

```
 queue_transactions()
   _txc_add_transaction(): decode ops -> _do_write()/_do_omap_setkeys()/...
        │  big/new writes: allocate fresh extents, prepare aio           (COW)
        │  small overwrites: pack data INTO the kv batch as an "L" record (WAL)
        ▼
 STATE_PREPARE ──aio pending──► STATE_AIO_WAIT      data hits disk first
        │                            │ (io_uring/libaio completion)
        └── no data aio ─────────────▼
                              STATE_IO_DONE
                                     ▼
                              STATE_KV_QUEUED       kv_sync_thread batches
                                     ▼              many txcs into one
                    rocksdb submit + WAL fsync      synced RocksDB commit
                                     ▼
                              STATE_KV_SUBMITTED ══► client gets COMMIT ACK
                                     ▼
                              STATE_KV_DONE
                    no deferred ─────┴───── deferred payload pending
                         ▼                        ▼
                  STATE_FINISHING          STATE_DEFERRED_QUEUED
                         ▼                 (batched aio_write of payload
                    STATE_DONE              to its real location, then
                                            delete "L" key)
                                                  ▼
                                           STATE_DEFERRED_CLEANUP
                                                  ▼
                                           STATE_DEFERRED_DONE
                                                  ▼
                                           STATE_FINISHING -> STATE_DONE
```

The two write strategies (chosen in `_do_write_small` /
`_do_write_big`, `BlueStore.cc:16566` / `:17077`):

- **Big or new writes** never overwrite live data: allocate new blocks,
  `aio_write` them, and only then flip the metadata in RocksDB. Crash at
  any point leaves either the old or the new object — torn writes are
  structurally impossible. One data write, one metadata commit.
- **Small overwrites** (below `bluestore_prefer_deferred_size` — 64 KiB
  on HDD, **0 on SSD**, i.e. disabled) would force a
  read-modify-write of a live blob. Instead the payload is embedded in
  the RocksDB commit itself as a deferred record (`L` prefix) — the ack
  rides the WAL fsync, and the payload is written to its final location
  lazily, batched, later. Double write, but the latency-critical fsync
  is one sequential WAL append — exactly the HDD-friendly trade.

The **commit point is the RocksDB WAL fsync** (`STATE_KV_SUBMITTED`): a
single ordered journal serializes data placement, metadata, freelist and
omap changes. `kv_sync_thread` aggregates concurrent TransContexts into
one `submit_transaction_sync`, so queue depth amortizes the fsync.

## Interface 2: the read path

`read()` → `_do_read()` (`BlueStore.cc:13138`): look up the Onode (cache
first, else RocksDB `O` key), load the extent-map shards covering the
range, then per blob: serve from the buffer cache if resident, else
`aio_read` the physical extents, **verify the checksum**
(`_verify_csum`, `BlueStore.cc:13299`), and decompress if the blob is
compressed. A checksum mismatch returns EIO to the PG layer — which then
repairs the replica from another OSD; this is how BlueStore turns silent
media corruption into self-healing.

Default checksum is crc32c per blob chunk (`bluestore_csum_type`,
`global.yaml.in:4643`); compression (`bluestore_compression_mode`,
default `none`) is decided per write hint and marked in the blob flags.

## BlueFS and BlueRocksEnv: RocksDB without a filesystem

RocksDB expects a POSIX-ish filesystem for its `.sst`, `MANIFEST` and WAL
files. Instead of keeping XFS around just for that, BlueStore implements
`BlueRocksEnv` (`BlueRocksEnv.h:19`, a `rocksdb::EnvWrapper`) backed by
**BlueFS** — a minimal, journaled, extent-based userspace filesystem
whose entire feature set is "what RocksDB needs": create/append/read
files, rename, fsync, three directories.

```
 RocksDB ──rocksdb::Env──► BlueRocksEnv ──► BlueFS ──► BlockDevice
                                            │
                    metadata = one replayed journal of
                    bluefs_transaction_t (bluefs_types.h:347);
                    file -> extent map rebuilt on every mount
```

BlueFS is why the multi-device layout works: it owns the `BDEV_WAL` /
`BDEV_DB` / `BDEV_SLOW` tiers and places each RocksDB file on the fastest
tier with space. The recursion (RocksDB's metadata needs a filesystem,
BlueFS's own metadata is just a journal) bottoms out because BlueFS never
needs random metadata lookups — it replays its log into memory at mount.

## Inside BlueFS: superblock, journal, and compaction

BlueFS has no allocation bitmap, no inode table, no directory blocks on
disk. Its entire persistent metadata is **one superblock plus one
journal file**; everything else is rebuilt in memory at mount. For a
kernel reader: imagine a log-structured filesystem that never checkpoints
anything *except* the log itself.

```
 DB device (BDEV_DB), 2nd 4 KiB block (_open_super, BlueFS.cc:1323)
 ┌────────────────────────────────────────────────────────────┐
 │ bluefs_super_t (bluefs_types.h:316)                        │
 │   uuid, block sizes, ...                                   │
 │   log_fnode ────────────┐  inode of THE journal file       │
 └─────────────────────────┼──────────────────────────────────┘
                           ▼
 journal file = sequence of bluefs_transaction_t (types.h:347)
 ┌──────────────────────────────────────────────────────────────┐
 │ OP_INIT                                                      │
 │ OP_DIR_CREATE "db"          OP_DIR_LINK "db/000123.sst" ino  │
 │ OP_FILE_UPDATE {ino, size, extents[(bdev,off,len)...]}       │
 │ OP_FILE_UPDATE_INC {fnode delta}    OP_FILE_REMOVE ino       │
 │ OP_JUMP seq/offset          ... appended forever ...         │
 └──────────────────────────────────────────────────────────────┘
                           │ _replay() at mount (BlueFS.h:800)
                           ▼
 in-memory only: dir map {"db" -> {name -> File}}, ino -> File,
                 per-bdev allocators rebuilt from every fnode's extents
```

The moving parts, top-down:

- **A file is just an fnode.** `bluefs_fnode_t` (`bluefs_types.h:140`):
  ino, size, mtime, and a vector of raw extents — each tagged with which
  device tier it lives on. Directories are flat (`db/`, `db.wal/`,
  `db.slow/`); no nesting, because RocksDB never asks for it.
- **The journal is the metadata.** Every namespace or fnode mutation is
  an op appended to the journal (`op_dir_link`, `op_file_update`, ...;
  the op set at `bluefs_types.h:349-362` is the complete metadata
  "schema"). `fsync` of a RocksDB file = flush its data extents, then
  append the file's new fnode as `OP_FILE_UPDATE_INC` and flush the
  journal. There is deliberately no other durable structure to update.
- **Bootstrap chicken-and-egg.** The journal is itself a file described
  by an fnode — stored inside the superblock (`log_fnode`), which lives
  at a fixed 4 KiB slot on the DB device. Mount reads the superblock,
  follows `log_fnode`'s extents, replays ops in sequence, and the whole
  filesystem exists in RAM. Free-space allocators for each tier are
  derived by subtracting every live fnode's extents from the device —
  which is why BlueFS needs no persistent freelist at all.
- **Compaction bounds the journal.** An append-forever journal would
  replay ever slower, so when it exceeds a threshold
  (`_should_start_compact_log_L_N`, `BlueFS.h:732`) BlueFS writes a
  fresh journal containing just a snapshot of current metadata and jumps
  to it — either stop-the-world (`_compact_log_sync_LNF_LD`,
  `BlueFS.h:745`) or the default async variant
  (`_compact_log_async_LD_LNF_D`, `:746`) that builds the new log while
  writers continue, then atomically flips `log_fnode` via a superblock
  rewrite. The cryptic suffixes (`_LNF_LD`) encode the lock order —
  log/nodes/file locks — a hint that this path is the concurrency
  hotspot of BlueFS.
- **Observability.** `ceph tell osd.N bluefs stats` shows per-tier usage
  and spillover; `ceph-bluestore-tool bluefs-export` dumps the whole
  BlueFS namespace to a directory, and `bluefs-bdev-expand` grows it
  after a device resize — the operator-facing corners of everything
  above.

The design trade is explicit: mount-time replay cost and a periodic
compaction stall risk, in exchange for a metadata write path that is a
single sequential append — on the same device RocksDB is already
fsyncing anyway.

## Allocator and FreelistManager

Free space is managed twice, deliberately:

- **Allocator** (`Allocator.cc:38`) — the *in-memory* policy deciding
  where new writes land. Pluggable: `hybrid` (default,
  `global.yaml.in:5327` — AVL interval tree for the common case, falling
  back to bitmap under fragmentation), plus `avl`, `btree`, `bitmap`,
  `stupid`, `hybrid_btree2`.
- **FreelistManager** (`FreelistManager.cc:7`) — the *persistent* record
  of free space, stored transactionally in RocksDB (`B`/`b` keys) so that
  allocation state commits atomically with the metadata that consumed it.

On non-rotational devices, current code defaults to the **"null"
freelist / NCB mode** (`_open_fm`, `BlueStore.cc:7357`): skip per-commit
freelist updates entirely, destage the allocator's map to a file on clean
shutdown, and after a crash rebuild it by scanning all onodes
(`read_allocation_from_drive_on_startup`, `BlueStore.cc:21041`) — trading
rare recovery cost for zero steady-state overhead.

## The block device layer (src/blk/)

`BlockDevice::create` picks `KernelDevice` by default (SPDK `NVMEDevice`
and `PMEMDevice` exist for kernel-bypass setups). `KernelDevice`
(`src/blk/kernel/KernelDevice.cc`) is comfortable territory for a kernel
reader: the device is opened `O_RDWR|O_DIRECT` (`:185`), submission
prefers **io_uring** with libaio fallback (`:48`, `:96`), durability is
`fdatasync` — skipped when no writes happened since the last flush
(`io_since_flush`, `:517`) — and TRIM runs on dedicated discard threads
(`KernelDevice.h:86`). BlueStore is effectively a userspace driver stack:
its own page-cache substitute, its own scheduler decisions, its own
barriers.

## Caching and memory

With no kernel page cache (O_DIRECT), BlueStore caches in-process,
sharded to avoid lock contention:

- **Onode cache** — `LruOnodeCacheShard` (`BlueStore.cc:1093`): decoded
  metadata; an onode miss costs a RocksDB point-get plus decode.
- **Buffer cache** — `TwoQBufferCacheShard` (2Q, `BlueStore.cc:1343`;
  plain LRU selectable via `bluestore_cache_type`): object data buffers.
- **RocksDB block cache** — SSTable blocks, inside RocksDB.

A `MempoolThread` (`BlueStore.h:2595`) rebalances the three pools
continuously against `osd_memory_target` (default 4 GiB per OSD) using
`PriorityCache` — cache ratios are workload-adaptive, not static.

## mkfs and mount

`BlueStore::mkfs()` (`BlueStore.cc:8662`) writes the bdev label, carves
out BlueFS, creates RocksDB, initializes freelist + allocator, persists
the superblock. `_mount()` (`:9556`) reverses it: open devices →
replay BlueFS journal → open RocksDB → read `S` superblock keys →
initialize the allocator (from freelist or NCB file) → **replay any
pending `L` deferred writes** — the crash-recovery half of the deferred
path.

## Where to hack: a feature-work map

| You want to... | Look at |
|---|---|
| change write/read behavior | `_do_write_small/_big`, `_do_read`, `WriteContext` in `BlueStore.cc` |
| add on-disk metadata | `bluestore_types.h` (bump `encode/decode` versions!), new `PREFIX_*` in `BlueStore.cc:134` |
| new allocation policy | subclass `Allocator`, register in `Allocator.cc:38` factory |
| new device backend | `src/blk/BlockDevice.cc` factory + new device class |
| add a config knob | `src/common/options/global.yaml.in` (not a header) |
| add observability | perf counters in `_init_logger` (`BlueStore.cc:6336`), `ceph tell osd.N bluestore ...` asok commands |
| test it | `src/test/objectstore/store_test.cc` (gtest, runs against BlueStore), `ceph_test_objectstore` |

One hard rule inherited from the encoding layer: every persisted struct
uses Ceph's versioned `encode`/`decode`; changing one without bumping
versions breaks upgrades of existing OSDs — mixed-version clusters are
the norm, not the exception.

# Summary

**Main advantages**

- **Transactions are native, not emulated** — one RocksDB WAL fsync
  commits data placement, metadata, omap and freelist atomically; this is
  the single biggest simplification over FileStore's POSIX gymnastics.
- **Half the writes of FileStore** — big writes go to disk exactly once
  (copy-on-write into fresh extents); only small overwrites pay a double
  write, deliberately, to make the ack latency one sequential WAL append.
- **End-to-end checksums by default** — every read verifies crc32c, so
  media corruption becomes a repairable EIO instead of silently served
  garbage; scrub + replication turn that into self-healing.
- **Device-tier awareness built in** — BlueFS places RocksDB metadata on
  NVMe while data stays on HDD, with automatic spillover; no filesystem
  tuning, no dm-cache.
- **Every layer is owned and tunable** — allocator, cache, compression,
  checksums, deferred-write threshold are all in-process and pluggable;
  nothing hides behind a filesystem's opaque policies.

**Main problems / limitations**

- **RocksDB is both the engine and the bottleneck** — compaction causes
  write amplification and latency spikes on metadata-heavy workloads
  (omap-hungry RGW bucket indexes are the classic victim), and it caps
  small-object throughput.
- **BlueStore reimplements kernel machinery in userspace** — page cache,
  allocator, I/O scheduling; the OSD must be told its memory budget
  (`osd_memory_target`) and misconfiguration means OOM or wasted RAM,
  since the kernel can no longer arbitrate.
- **Deferred-write knobs are subtle** — the 64 KiB-vs-0 HDD/SSD defaults
  encode a latency model; wrong settings silently double write traffic or
  inflate small-write latency, and few operators know the knob exists.
- **Fragmentation over time** — long-lived clusters see allocator
  fragmentation degrade large-write performance; `ceph tell osd.N
  bluestore allocator score block` measures it, but defragmentation
  tooling is still limited.
- **A crashed OSD in NCB mode pays a full metadata scan** to rebuild the
  allocator map — startup after unclean shutdown on a big NVMe OSD is
  measurably slower.
